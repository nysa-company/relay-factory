## Description

Add a zero-dependency, read-only Node command that counts persisted Relay
approvals whose job identifier and proposal timestamp exactly match supplied
strings. This supports narrow offline approval checks without starting Relay
or exposing approval bodies. The command reuses the state-validity algorithm,
error-envelope style, and module restrictions already established by
`app/tools/approval-count.js` and `app/tools/approval-reason-count.js`
(read-only `node:fs` CLI tools operating on the four-collection Relay state
shape), and the CLI argument shape (`<state-file> <filter-arg...>`, usage
error on arity mismatch) established by `app/tools/approval-state.js` and
`app/tools/outbox-approval-count.js`.

## Acceptance criteria

1. `node app/tools/approval-job-proposed-count.js <state-file> <job-id> <proposed-at>`
   (exactly 3 positional arguments) emits compact JSON to stdout containing
   exactly one key, `approvalsWithJobAndProposedAt`, whose value is a
   non-negative integer, followed by `\n`; stderr is empty; exit code is 0.
   [Frozen contract §2]
2. Zero, one, two, or four-or-more positional arguments each fail
   identically: stdout is empty, stderr is exactly the frozen usage string,
   exit code is 2, and the state-file path (if any was supplied) is never
   accessed (its existence/absence and byte content are unchanged by the
   invocation). [Frozen contract §3]
3. An empty-string job-id argument or an empty-string proposed-at argument
   (with exactly 3 arguments present) fails identically to case 2: frozen
   usage string on stderr, exit code 2, no state-file access. [Frozen
   contract §3]
4. An unreadable state-file path (absent path or a directory path) fails
   with the frozen read-error string on stderr, exit code 1, empty stdout,
   and leaves the filesystem at that path unchanged. [Frozen contract §3]
5. A state file that is not valid JSON fails with the frozen parse-error
   string on stderr, exit code 1, empty stdout, and never echoes any byte of
   the malformed content. [Frozen contract §3]
6. Every structurally-invalid state fixture in the frozen S1-S29 corpus (§4)
   fails with the frozen invalid-state string on stderr, exit code 1, empty
   stdout, and leaves the fixture file's bytes unchanged. This includes an
   approval missing, or with a wrong-typed or empty, `id`/`jobId`/
   `proposedAt`/`status`/`action.to`/`action.subject`/`action.body`, an
   `action` that is not a plain object, a `status` outside the frozen enum,
   and two approvals sharing one `id`. [Frozen contract §3, §4]
7. Job ID and proposed-at matching are each exact and case-sensitive
   (`===`), with no timestamp parsing, trimming, normalization, or coercion:
   an approval whose stored `jobId` or `proposedAt` differs from the
   supplied argument only in letter case, or only in ISO-instant formatting,
   never counts. Both fields must match on the same approval record
   simultaneously (matching `jobId` alone, or `proposedAt` alone, does not
   count). [Frozen contract §5]
8. A fixture with 3+ valid approvals of mixed matching/non-matching
   `jobId`/`proposedAt` combinations produces the exact frozen count integer
   summing only the approvals matching both conditions; a fixture with zero
   approvals matching either field, and separately a fixture with an empty
   `approvals` array, both produce `0` via the success path (exit 0), never
   an error path. An approval's `status`, `action` field values, and
   optional `reason` never influence the count (field independence).
   [Frozen contract §2, §5]
9. Running the tool twice in immediate succession against the same fixture
   file produces byte-identical stdout both times and leaves the fixture
   file's bytes and parent directory listing unchanged, proving the

10. The production file `app/tools/approval-job-proposed-count.js` contains

    `WebSocket`, `node:http`, `node:https`, `node:net`,

11. Tests in `app/tests/approval-job-proposed-count.test.js` are committed

    `app/tools/approval-job-proposed-count.js`. `node --test

  only check arity). Resolved by Planner convention (CLI error taxonomy, not
  product behavior — not escalated): reuse the exact same frozen usage

  already frozen on sibling ticket T-255
  (`app/tools/event-type-payload-key-count.js`, contract §1/§3), keeping the

### §2. Invocation and success output

```
node app/tools/approval-job-proposed-count.js <state-file> <job-id> <proposed-at>
```

Exactly 3 positional arguments (`process.argv.slice(2)`). On success: exit
0, stderr empty, stdout is exactly:

```
{"approvalsWithJobAndProposedAt":<N>}\n
```

where `<N>` is the decimal count with no leading zeros (standard
`JSON.stringify` integer formatting) and no other keys are present.

### §3. Error envelope (checked in this exact order, each short-circuiting)

| Condition | stdout | stderr (exact) | exit |
|---|---|---|---|
| `argv.length !== 3`, OR `argv[1] === ""`, OR `argv[2] === ""` | `""` | `usage: node app/tools/approval-job-proposed-count.js <state-file> <job-id> <proposed-at>\n` | 2 |
| `readFileSync(argv[0], "utf8")` throws (absent path, directory, permission, etc.) | `""` | `approval-job-proposed-count: cannot read state file\n` | 1 |
| `JSON.parse(contents)` throws | `""` | `approval-job-proposed-count: state file is not valid JSON\n` | 1 |
| parsed state fails §4 validity | `""` | `approval-job-proposed-count: invalid Relay state\n` | 1 |

The usage check runs before any filesystem access (no `readFileSync` call
occurs for arity/empty-argument failures).

### §4. State validity (`isValidState`)

Identical algorithm to `app/tools/approval-count.js`'s `isValidState`,
reused verbatim:

- `state` is a plain object (not `null`, not an array).
- `state.events`, `state.jobs`, `state.approvals`, `state.outbox` are each
  present own-properties and arrays (contents of `events`/`jobs`/`outbox`
  are never otherwise inspected).
- Each entry of `state.approvals` is a plain object with:
  - `id`: non-empty own string, unique across all approvals in the array.
  - `jobId`: non-empty own string.
  - `proposedAt`: non-empty own string.
  - `status`: own property, value in `{"pending", "sent", "rejected",
    "blocked_recipient"}` exactly.
  - `action`: own property, a plain object owning `to`, `subject`, and
    `body` (any value, including `null`/`false`/numbers — only presence via
    `Object.prototype.hasOwnProperty` is checked, not type).
  - `reason` (if present) is unconstrained by validity (not checked).

The structurally-invalid fixture corpus is the S1-S29 set already defined
in `app/tests/approval-count.test.js` (byte-for-byte reusable as a fixture
source since the validity algorithm is unchanged), adapted so each
fixture's designated approval-array content is exercised through this
tool's 3-argument CLI instead of `approval-count.js`'s 1-argument CLI. Test
fixtures for this ticket must additionally include the derived-fixture
distinctness proof already established for S26 (casing-derived `status`
value byte-distinct from the valid status) and S29 (a valid approval
followed by a structurally-invalid sibling missing its own `proposedAt`),
matching AC6.

### §5. Matching and counting

`approvalsWithJobAndProposedAt` is the count of entries in `state.approvals`
where, simultaneously:

1. `approval.jobId === argv[1]` (exact `===`, no normalization).
2. `approval.proposedAt === argv[2]` (exact `===`, no timestamp parsing,
   normalization, or coercion).

Zero is a valid, successful (§2) result — never an error. No other approval
field (`status`, `action`, `reason`, `id`) affects the match.

### §6. Determinism and module boundary

- No writes anywhere; two consecutive invocations against one fixture file
  produce byte-identical stdout and leave the fixture file and its parent
  directory listing byte-for-byte unchanged.
- `app/tools/approval-job-proposed-count.js`: exactly one `require`
  specifier, `"node:fs"`; exactly one `node:fs` member used,
  `readFileSync`; source contains none of `server.js`, `fetch(`,
  `WebSocket`, `node:http`, `node:https`, `node:net`, `node:child_process`,
  `setTimeout`, `setInterval`.
- `app/tests/approval-job-proposed-count.test.js`: module specifiers
  exactly `["node:assert", "node:child_process", "node:fs", "node:os",
  "node:path", "node:test"]` (same closed set as
  `app/tests/approval-count.test.js`).
- Every spawned child invocation completes within a 5000ms timeout
  (`spawnSync(..., { timeout: 5000 })`), proving self-termination.
