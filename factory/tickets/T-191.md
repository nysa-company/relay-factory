## Spec'd description

Add one zero-dependency Node 18+ command,
`node app/tools/job-attempts.js <state-file> <job-id>`, that reads a persisted
Relay state file without starting the service, validates every stored job,
selects one job by exact case-sensitive ID, and emits only `jobId`, cumulative
`attempts`, and `attemptsSinceRetry`. This gives an operator both the lifetime
attempt count and the current retry-window count while withholding `eventId`,
`status`, `retries`, `lastError`, event payloads, approval content, outbox
content, and unrelated state.

Product-doc sources:

- [`SPEC.md` behavior 2](../../SPEC.md#behavior-spec) defines durable job
  attempts, retries, and the three-attempt dead-letter boundary.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the complete
  persisted state file Relay's durable source of truth; this command reads that
  artifact without participating in service startup or crash recovery.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) makes job attempts
  operator-visible, while
  [`SPEC.md` conformance cases 3-4](../../SPEC.md#test-cases-the-conformance-suite)
  establish successful and dead job outcomes with recorded attempts.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/` as the
  zero-dependency conformance product and Factory controls outside application
  work. [`AGENTS.md` Verification](../../AGENTS.md#verification) defines the
  later full-app and immutability checks.

The current counter semantics come from
[`app/server.js`](../../app/server.js): every processing attempt increments
both counters, while an accepted retry preserves cumulative `attempts` and
resets `attemptsSinceRetry` to zero. The shipped
[`job-progress` acceptance seam](../../app/tests/job-progress.test.js) supplies
the exact persisted job shape and representative counter values.

### Command-line interface

- Repository-root invocation:
  `node app/tools/job-attempts.js <state-file> <job-id>`.
- Exactly two positional arguments are accepted. `<job-id>` is used verbatim;
  it is not trimmed, case-folded, decoded, normalized, or prefixed.
- Any other arity exits `2`, writes empty stdout, reads no state path, and
  writes exactly this single LF-terminated stderr line:

  ```text
  usage: node app/tools/job-attempts.js <state-file> <job-id>
  ```

- After arity validation, the command synchronously establishes that
  `<state-file>` is a readable regular file, reads it as UTF-8, parses it with
  `JSON.parse`, validates the complete frozen structure below, and only then
  selects the job whose stored `id` is strictly equal to `<job-id>`.
- Success exits `0`, writes empty stderr, and writes one compact JSON object
  plus exactly one LF to stdout. The object has exactly these keys in this
  order:

  ```json
  {"jobId":<stored id>,"attempts":<stored attempts>,"attemptsSinceRetry":<stored attemptsSinceRetry>}
  ```

  The two counters are copied without transformation. No other input field is
  emitted.
- A valid state with no exact ID match exits `1`, writes empty stdout, and
  writes exactly:

  ```text
  job-attempts: no such job
  ```

- The command computes its result in memory and exits. It does not import,
  require, spawn, or start `app/server.js`; open a socket or listener; issue a
  request; or leave a timer or child process running.

### Valid state and failure protocol

A valid state is a parsed, non-null, non-array JSON object with exactly four
own properties: `events`, `jobs`, `approvals`, and `outbox`, each an array.
Entries in `events`, `approvals`, and `outbox` are opaque because this command
does not consume them. Every element of `jobs` must be a non-null, non-array
object with:

- a non-empty string `id`;
- a non-empty string `eventId`;
- `status` exactly `pending`, `done`, or `dead`;
- integer `attempts`, `retries`, and `attemptsSinceRetry`, each greater than or
  equal to zero; and
- `lastError` equal to `null` or a string.

Job IDs must be pairwise distinct. Additional job properties are allowed and
ignored. The validator does not impose a relationship among the three
counters beyond their individual nonnegative-integer rules. It validates every
job and ID uniqueness before lookup; a valid requested job does not override
an invalid sibling.

After arity validation, failures have this exact precedence:

1. A filesystem failure while establishing a readable regular file or reading
   its bytes, including a nonexistent path, directory path, or OS read denial,
   exits `1`, writes empty stdout, and writes exactly
   `job-attempts: state file is unreadable\n` to stderr.
2. Readable bytes rejected by `JSON.parse` exit `1`, write empty stdout, and
   write exactly
   `job-attempts: state file is not valid JSON\n` to stderr.
3. Parsed JSON that fails any frozen structural rule exits `1`, writes empty
   stdout, and writes exactly
   `job-attempts: state file has invalid Relay state\n` to stderr.
4. Exact-ID lookup occurs only after whole-state validation and has the frozen
   not-found result above.

No error includes an input path, supplied ID, operating-system error, parser
text, stack trace, state content, or a second line. Every displayed error line
ends with exactly one LF. No path is written, renamed, deleted, chmodded, or
created.

The arity tests use fresh empty temporary parents. The one-argument case
supplies exactly `<tmp>/arity-state-does-not-exist.json`. The three-argument
case supplies that same nonexistent path, `job-attempts-dead`, and `extra`.
The path remains absent, proving arity validation precedes file access.

2. **What does exact ID selection mean?** The seed did not say whether trimming
   or case folding was forbidden. Resolved as JavaScript strict string
   equality to the literal argument, matching the current server lookup. The
   uppercase and trailing-space unknown IDs make both alternatives observable.
3. **What is structurally valid state?** The product spec names persisted
   collections but does not define an offline validator. Resolved from the
   current state model and the associated protected seam: require exactly four
   collection arrays, validate every field in every job, permit additional job
   fields, and reject duplicate IDs before lookup. Unconsumed collections
