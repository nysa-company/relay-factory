## Spec'd description

Add a read-only `GET /api/events/:id` detail endpoint so an API client can
retrieve one accepted event together with the single job created for it,
without downloading all Relay state from `GET /api/state`.

This is the detail-view counterpart to the event intake and state visibility
defined by [SPEC.md § Behavior spec, items 1 and 7](../../SPEC.md#behavior-spec).
The event-to-job relationship comes from item 2 ("each accepted event enqueues
one background job"), while the response returns the stored records unchanged
so the persistence and crash-recovery model in
[SPEC.md § Behavior spec, item 6](../../SPEC.md#behavior-spec) remains the
source of truth. The implementation remains in the zero-dependency product
defined by [AGENTS.md § Boundaries](../../AGENTS.md#boundaries), and
verification follows [AGENTS.md § Verification](../../AGENTS.md#verification).

No UI, write path, worker behavior, authentication behavior, or external-send
behavior changes.

### HTTP interface

- Method and path: `GET /api/events/:id`.
- Route match: `^\/api\/events\/([^/]+)$` against `url.pathname`; `:id` is the
  captured non-empty path segment and is matched exactly against `event.id`.
- The endpoint reads no request body.
- The acceptance surface is the two exact request paths in criteria 1 and 2.
  Query strings, IDs containing `/`, other methods, and non-matching paths are
  outside this ticket's interface.
- Scope is a valid Relay state where every stored event has the one related
  job guaranteed by
  [SPEC.md § Behavior spec, item 2](../../SPEC.md#behavior-spec). Recovery from
  manually corrupted state is outside this ticket.

For a matching event, find:

- `event`: the one entry in `state.events` whose `id === :id`;
- `job`: the one entry in `state.jobs` whose `eventId === event.id`.

Return HTTP `200`, `Content-Type: application/json`, and:

```json
{
  "event": "<the complete stored event object, unchanged>",
  "job": "<the complete stored related job object, unchanged>"
}
```

`event` and `job` are singular object-valued keys and are the only top-level
keys. "Unchanged" means every stored field and value is returned, with no
renaming, omission, computed field, or projection.

If no entry in `state.events` has `id === :id`, return HTTP `404`,
`Content-Type: application/json`, and exactly:

```json
{"error":"no such event"}
```

The unknown-ID branch does not inspect or return a job. Neither branch calls
`persist`, mutates in-memory `state`, schedules work, or performs an external
send.

## Ambiguity log

- **Event/job cardinality:** The Ready record said "the related job" but did
  not identify the invariant source. Resolved from
  [SPEC.md § Behavior spec, item 2](../../SPEC.md#behavior-spec), which says
  each accepted event enqueues one job. Version 1 therefore returns one `job`
  object, not an array.
- **Success envelope:** The Ready record did not name top-level response keys.
  With `Product-Decisions: frozen`, the contract uses the same `event` and
  `job` domain nouns and returns the complete stored objects described by
  [SPEC.md § Behavior spec, items 1–2](../../SPEC.md#behavior-spec), adding no
  derived behavior. This matches the prior same-endpoint frozen contracts on
  T-110 and T-114.
- **Meaning of read-only:** The Ready record did not say whether disk writes
  count as a change when bytes remain equal. Resolved from
  [SPEC.md § Behavior spec, item 6](../../SPEC.md#behavior-spec), which makes
  atomically persisted disk state part of the behavior. Criterion 3 checks
  state value, file bytes, inode, and modification timestamp.
- **Deterministic fixture versus worker timing:** A pending job can advance on
  the normal worker tick. Resolved using the documented `WORKER_MS`
  configuration in [SPEC.md](../../SPEC.md): `WORKER_MS=600000` prevents a
  tick during the detail assertions.
- **Earlier duplicate tickets:** T-110 and T-114 declare the same endpoint and
  owned files; their unmerged remote branches are from earlier qualification
  cohorts. The current
  [qualification manifest](../QUALIFICATION.json) admits T-118 through T-121,
  and the current worktree lease list contains only those four ticket
  branches. Therefore T-110/T-114 are precedents, not concurrent
  implementation inputs; T-118 remains confined to its declared files.
- **Concurrent file ownership:** Grepping every sibling record under
  `factory/tickets/` found multiple declarations of builder ownership over
  `app/server.js`. Inspection of every other currently leased branch
  (`origin/ticket/T-119`, `origin/ticket/T-120`, and
  `origin/ticket/T-121`) confirms all three also own `app/server.js` while
  adding disjoint detail routes and disjoint test files. This is a Git
  integration-order conflict, not an interface conflict. T-118 may not expand
  beyond its two owned files; after a sibling merges, this branch must
  incorporate that result and preserve the sibling route before review or
  merge.
- **Topology and external effects:** `Authentication-Seams: none`,
  `External: no`, and the current single-server architecture resolve this as a
  same-origin read route with no cookies, CORS, credentials, external sends,
  or preview topology to specify.
