## Spec'd description

Add one zero-dependency, read-only Node command,
`node app/tools/pending-approvals.js <state-file>`, that reports pending Relay
approvals from persisted state while the Relay service is offline. The command
projects only `id`, `jobId`, and `proposedAt`, sorts the projection by approval
ID, and never prints approval actions or rejection reasons. This gives an
operator a deterministic queue view without opening an HTTP listener,
executing an approval, or changing persisted state.

Product-doc sources:

- [`SPEC.md` behavior 3](../../SPEC.md#behavior-spec) defines the proposed
  action, its `pending` state, and the approval gate.
- [`SPEC.md` behaviors 4-6](../../SPEC.md#behavior-spec) distinguish later
  approval outcomes from pending work and require state to persist on disk.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) establishes the persisted
  state collections exposed by Relay; this ticket reads the same state
  representation directly rather than starting the service.
- [`SPEC.md` conformance cases 5-7](../../SPEC.md#test-cases-the-conformance-suite)
  require pending approvals to remain gated, blocked/rejected work not to send,
  and crash-recovered state not to duplicate effects. The new command is a
  read-only projection over those records.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) requires the app to stay
  zero-dependency and keeps Factory controls outside application work.
  [`AGENTS.md` Verification](../../AGENTS.md#verification) defines the later

### Command-line interface

- Repository-root invocation:
  `node app/tools/pending-approvals.js <state-file>`.
- The command accepts exactly one positional argument. Relative paths are
  interpreted from the command process's working directory; acceptance tests
  pass an absolute temporary path.
- Zero or two positional arguments produce exit code `2`, empty stdout, and
  exactly this single LF-terminated stderr line:

  ```text
  usage: node app/tools/pending-approvals.js <state-file>
  ```

- The command reads the named file directly as UTF-8. It does not import,
  require, spawn, or otherwise execute `app/server.js`; it opens no HTTP or
  other network listener and does not leave a timer or child process running.
- Read failure, including a nonexistent path, a directory in place of a file,
  or an OS read denial, produces exit code `1`, empty stdout, and exactly:

  ```text
  pending-approvals: cannot read state file
  ```

- Bytes that cannot be parsed by `JSON.parse` produce exit code `1`, empty
  stdout, and exactly:

  ```text
  pending-approvals: state file is not valid JSON
  ```

- A parsed value that fails the frozen structural rules produces exit code
  `1`, empty stdout, and exactly:

  ```text
  pending-approvals: invalid Relay state
  ```

- The command does not include the input path, an OS error, parser text, input
  content, a stack trace, or a second line in any error. Every displayed line
  above is terminated by one LF byte.
- Validation precedence is argument count, read, JSON parse, then structure.
  No error path writes the input or creates a replacement state file.

### Valid state and report shape

For this command, a structurally valid state is a non-null, non-array JSON
object with own `events`, `jobs`, `approvals`, and `outbox` properties whose
values are arrays.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string `id`;
- non-empty string `jobId`;
- non-empty string `proposedAt`; and
- string `status` equal to exactly one of `pending`, `sent`, `rejected`, or
  `blocked_recipient`.

The command does not reinterpret timestamps. Contents of `events`, `jobs`, and
`outbox`, additional top-level keys, and additional approval keys are opaque
to structural validation. In particular, `action` and `reason` may be present
but are never copied to output.

On valid input, select only approvals whose `status` is exactly `pending`,
project each to a newly serialized object with keys in this exact order:

```json
{"id":<stored id>,"jobId":<stored jobId>,"proposedAt":<stored proposedAt>}
```

Sort projected entries by ascending approval `id` using JavaScript string
less-than/greater-than comparison, not locale collation. Serialize the array
with compact `JSON.stringify` formatting and append exactly one LF byte.
Successful stderr is empty and the exit code is `0`. An empty selection is
exactly `[]\n`.

There are no endpoint paths, HTTP response shapes, UI routes, or UI selectors
in this contract.

## Ambiguity log

1. **Exact error protocol.** The seed ticket required concise deterministic
   errors but did not freeze their text or exit codes. No ruling in
   [`factory/rulings.md`](../rulings.md) addresses offline commands. Resolved
   as the four exact, path-independent outcomes above, following the existing
   repository convention that usage errors exit `2` and operational failures
   exit nonzero without platform-specific details.
2. **Meaning of structurally valid.** `SPEC.md` and `app/server.js` establish
   the four persisted collections and the approval status/fields but do not
   define a general state-file validator. Resolved narrowly for this read-only
   report: validate all top-level collections and only the approval fields the
   command must classify or return; treat unrelated collection contents and
   additive fields as opaque. S1-S11 make that boundary testable.
3. **Sorting and JSON determinism.** “Approval-id-sorted JSON” did not specify
   locale, whitespace, property order, or line termination. Resolved as
   JavaScript string comparison, compact JSON, the exact projected key order,
   and one final LF, with byte-exact expectations in AC1-2.
4. **Sensitive-field boundary.** The seed named recipients, subjects, bodies,
   and rejection reasons but did not provide sentinel data. Fixture A includes
   unique values in every named field, a nonempty outbox, all approval
   statuses, and additive metadata; exact stdout/stderr assertions prove none
   leaks.
5. **Missing versus unreadable input.** OS permission failures are not portable
   under privileged test users. The contract groups all read failures under
   one deterministic error and freezes an absent path plus a directory path as
   portable representatives.
6. **Cross-ticket file ownership.** A grep of `factory/tickets/` found only
   stranded T-172 declaring the same Builder and test-author paths. T-175's
   reconciled coordination record explicitly replaces T-172, and T-172 has no
   active worktree. The other active leased branches, T-173 and T-174, were
   inspected both at `origin/ticket/T-XXX` and in their worktrees; they own
   `state-summary.js`/`state-summary.test.js` and
   `dead-jobs.js`/`dead-jobs.test.js`, respectively, with no T-175 overlap.
7. **Protected source and text boundaries.** The new Builder file has no
   existing importer or source snapshot. The declared
   `app/tests/health-approvals.test.js` seam was inspected and asserts existing
   server HTTP behavior only, so it remains unchanged. Readiness checks for
   every new fixed visible literal returned `GLOBAL TEXT PASS`; no
   `Protected-Test-Conflicts` entry is needed.
