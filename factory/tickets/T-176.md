## Spec'd description

Add one zero-dependency, read-only Node 18+ command,
`node app/tools/blocked-approvals.js <state-file>`, that reports persisted
approvals whose status is exactly `blocked_recipient` while Relay is offline.
It emits only each blocked approval's `id`, `jobId`, and `proposedAt`, sorted
by approval ID. This gives operators a deterministic safety-block inventory
without revealing approval actions, recipients, subjects, bodies, rejection
details, unrelated approvals, or outbox data.

Product-doc sources:

- [`SPEC.md` behavior 3](../../SPEC.md#behavior-spec) defines the proposed
  action and approval gate.
- [`SPEC.md` behavior 4](../../SPEC.md#behavior-spec) defines the
  `blocked_recipient` outcome for an approved action whose recipient is not
  allowlisted.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the on-disk state
  Relay's durable source of truth.
- [`SPEC.md` conformance case 6](../../SPEC.md#test-cases-the-conformance-suite)
  requires a blocked approval to be recorded and not sent.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) requires the app to
  remain zero-dependency and keeps Factory controls outside application work.
  [`AGENTS.md` Verification](../../AGENTS.md#verification) defines the later
  repository verification commands.

The command is a read-only projection over the existing state file. It does
not start the service, execute or retry an approval, write an outbox record,
or change the server, persisted schema, worker, package manifest, dependencies,
UI, or Factory controls.

### Command-line interface

- Repository-root invocation:
  `node app/tools/blocked-approvals.js <state-file>`.
- Exactly one positional argument is accepted. Zero, two, or three arguments
  produce exit code `2`, empty stdout, and exactly this LF-terminated stderr
  line:

  ```text
  usage: node app/tools/blocked-approvals.js <state-file>
  ```

- The command reads the named regular file directly as UTF-8. It does not
  import, require, spawn, or otherwise execute `app/server.js`; open an HTTP or
  other network listener; make an outbound request; or leave a timer or child
  process running.
- A read failure, including a nonexistent path, a directory in place of a
  file, or an OS read denial, produces exit code `1`, empty stdout, and
  exactly:

  ```text
  blocked-approvals: cannot read state file
  ```

- Bytes rejected by `JSON.parse` produce exit code `1`, empty stdout, and
  exactly:

  ```text
  blocked-approvals: state file is not valid JSON
  ```

- A parsed value that fails the frozen structural rules produces exit code
  `1`, empty stdout, and exactly:

  ```text
  blocked-approvals: invalid Relay state
  ```

- No error includes the input path, OS error, parser text, input content, stack
  trace, or a second line. Every displayed line above ends with one LF byte.
- Validation precedence is argument count, read, JSON parse, then structure.
  No path is written, renamed, deleted, chmodded, or created.

Each argument-count case uses a fresh empty temporary parent. The two-argument
case supplies nonexistent `<tmp>/state-a.json` and `<tmp>/state-b.json`; the
three-argument case additionally supplies nonexistent `<tmp>/state-c.json`.
The test requires the parent's entry list to remain empty after each case.

### Valid state and report shape

For this command, a structurally valid state is a non-null, non-array JSON
object with own `events`, `jobs`, `approvals`, and `outbox` properties whose
values are arrays.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string `id`;
- non-empty string `jobId`;
- non-empty string `proposedAt`; and
- string `status` equal to exactly one of `pending`, `sent`, `rejected`, or
  `blocked_recipient`.

Contents of `events`, `jobs`, and `outbox`, additional top-level keys, and
additional approval keys are opaque to structural validation. Timestamps are
copied without parsing or normalization. `action` and `reason` may be present
but are never copied to output.

On valid input, select only approvals whose `status` is exactly
`blocked_recipient`. Project each selected approval to a newly serialized
object with keys in this exact order:

```json
{"id":<stored id>,"jobId":<stored jobId>,"proposedAt":<stored proposedAt>}
```

Sort projected entries by ascending approval `id` using JavaScript string
less-than/greater-than comparison, not locale collation. Duplicate approval
IDs are outside the persisted model because Relay derives them from unique
event IDs; no duplicate-ID tie behavior is added by this command. Serialize
the array with compact `JSON.stringify` formatting and append exactly one LF
byte. Success exits `0` with empty stderr. An empty selection is exactly
`[]\n`.

There are no endpoint paths, HTTP request or response shapes, UI routes, or UI
selectors in this contract.

## Ambiguity log

1. **Exact error protocol.** The seed required concise deterministic errors
   but did not freeze their text or exit codes. No entry in
   [`factory/rulings.md`](../rulings.md) addresses offline commands. Resolved
   as exact path-independent usage, read, parse, and structure outcomes,
   following the already shipped offline-command convention.
2. **Meaning of structurally valid.** The product docs establish the four
   persisted collections and approval statuses but do not define a general
   state-file validator. Resolved narrowly: validate every collection as an
   array and only the approval fields this report classifies or emits; treat
   unrelated contents and additive fields as opaque.
3. **Sorting and serialization.** “Approval-ID-sorted JSON” did not specify
   locale, whitespace, key order, line ending, or duplicate ties. Resolved as
   JavaScript string comparison, compact JSON, fixed projected key order, and
   one LF. Duplicate approval IDs remain outside Relay's idempotent persisted
   model rather than adding new behavior.
4. **Sensitive-field proof.** The seed names private field categories but no
   sentinels. Fixture A assigns a unique `-MUST-NOT-LEAK` value to every
   action field, rejection reason, outbox field, and additive metadata value;
   exact stream checks make leakage testable.
5. **Unreadable input portability.** Permission-denial fixtures are unreliable
   under privileged users. All OS read failures share one frozen result; an
   absent path and a directory path are the two portable representatives.
6. **Cross-ticket file ownership.** A grep of every Markdown ticket found no
   other declaration of `blocked-approvals.js` or
   `blocked-approvals.test.js`. The only active worktree is T-176. Remote
   ticket branches T-170, T-171, and T-172 were also inspected; they own the
   distinct state-summary, dead-jobs, and pending-approvals paths.
7. **Protected source and global text.** Inspection of the associated health
   seam and all tracked tests found no source boundary affecting the new file.
   The pinned readiness script accepted every new shell-visible literal, so
   no `Protected-Test-Conflicts` declaration or fixture-seam edit is needed.
8. **Topology, lifecycle, and external effects.** This is a local
   file-to-stdout command with isolated temporary fixtures and no database or
   network path. Auth, cookies, CORS, deployment domains, generated values,
   dependent rows, UI selectors, and external sends do not apply.
