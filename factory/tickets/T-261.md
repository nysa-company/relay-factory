## Spec'd description

The shipped [`state-summary` command](../../app/tools/state-summary.js) reads
one persisted Relay state file offline and prints deterministic collection and
status counts. It currently validates that every job record has an own
`status` property in the exact enum `pending`, `done`, `dead`
(`app/tools/state-summary.js` `recordsHaveStatuses`), but never validates a
job's `id` at all and never checks for duplicate job IDs across the array. A
duplicated durable job identity makes the printed aggregate misleading: the
same logical job can be represented twice and counted twice.

Add validation, ahead of counting, that every job record has an own `id`
property whose value is a non-empty string, and that the complete `jobs` array
contains pairwise-distinct `id` values. A violation is folded into the
existing generic invalid-state failure; no new error message, exit code, or
output shape is introduced. No other command behavior changes.

Product-doc and repository sources:

- [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec) establishes that Relay
  event/job identity must be idempotent ("a repeated `id` ... never creates a
  second job"), and
  [`SPEC.md` conformance case 7](../../SPEC.md#test-cases-the-conformance-suite)
  requires that crash recovery leaves "nothing duplicated." A job's `id` is
  the durable identity this ticket protects in the offline summary path.
- The current [`app/server.js` state model](../../app/server.js) establishes
  that every job carries an `id`, an `eventId`, and a `status` drawn from the
  same three-value enum already enforced by `state-summary`.
- The shipped [`state-summary` command](../../app/tools/state-summary.js) and
  its [acceptance suite](../../app/tests/state-summary.test.js) establish the
  exact CLI interface, failure precedence (arguments, read, JSON-parse,
  structural validation, then counting), the four fixed single-line error
  messages, the success envelope shape, and the read-only/offline/
  deterministic conventions this ticket must preserve unchanged.
- The sibling ticket [T-263](T-263.md), which requires unique approval IDs in
  the offline approval-report commands, and the shipped
  [`approval-count` command](../../app/tools/approval-count.js) (which already
  rejects duplicate approval IDs before counting) establish the project's
  existing convention for how duplicate-durable-identity is folded into a
  generic structural-invalid failure rather than a distinct error class.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency, and
  [`AGENTS.md` Verification](../../AGENTS.md#verification) defines the
  post-implementation full-suite and immutability checks.

No CLI argument, exit code (other than the existing four), error message text,
output shape, approval/event/outbox validation rule, endpoint, UI, dependency,
persisted schema, or Factory control changes.

- Failure precedence is unchanged: argument count, file read, JSON parse,

### Structurally valid state — updated rules

A structurally valid state is unchanged except for two additive rules on job
records:

- The parsed root, the four top-level collections (`events`, `jobs`,
  `approvals`, `outbox`), the requirement that every job and approval element
  is a non-null non-array object (`isRecord`), and the approval `status` enum
  check are all unchanged from the shipped implementation.
- **(New)** Every job element must additionally have an own `id` property
  whose value is a non-empty string (`typeof id === "string" && id.length >
  0`). A job missing an own `id`, or whose `id` is `""` or not a string (for
  example a number, `null`, `true`, an object, or an array), fails structural
  validation.
- **(New)** The complete `jobs` array must contain pairwise-distinct `id`
  values, compared with JavaScript strict equality (`===`) on the exact
  string value — no trimming, case-folding, decoding, or Unicode
  normalization. A duplicate fails structural validation regardless of
  whether the two (or more) jobs sharing that `id` have the same or different
  `status`, and regardless of how many other, distinct, valid jobs appear
  before or between them in the array.
- The existing job `status` enum check (`pending`, `done`, `dead`) is
  unchanged and is independent of the new `id` rules: a job can fail either,
  both, or neither check, and any failure anywhere in the `jobs` or
  `approvals` arrays causes the same generic invalid-state result.
- No rule changes for `events`, `outbox`, or `approvals` elements. Approval
  IDs are explicitly out of scope for this ticket (see T-263).
- The complete `jobs` array (every element, both the `id` rules and the
  existing `status` rule) is validated before the command counts anything or
  writes any output. There is no early return that stops validation partway
  through the array.

### Unchanged success envelope

Success is unchanged: exit `0`, zero stderr bytes, and one compact JSON line
followed by exactly one LF:

```json
{"events":<n>,"jobs":{"pending":<n>,"done":<n>,"dead":<n>},"approvals":{"pending":<n>,"sent":<n>,"rejected":<n>,"blocked_recipient":<n>},"outbox":<n>}
```

This ticket changes no field name, key order, or value semantics of this
object. `FIXTURE_A_OUTPUT` and `FIXTURE_B_OUTPUT`, as already defined in
`app/tests/state-summary.test.js`, remain byte-for-byte correct because every
job `id` in Frozen Fixture A and Frozen Fixture B is already unique and
already a non-empty string.

| D6 | `{"events":[],"jobs":[{"id":"job-a","status":"pending"},{"id":"job-b","status":"done"},{"id":"job-c","status":"dead"},{"id":"job-a","status":"dead"}],"approvals":[],"outbox":[]}` | duplicate job `id` non-adjacent, after two other unique valid jobs |

Before any command invocation, the acceptance test compares the exact
serialized bytes of D1-D6 pairwise, and against `FIXTURE_A_BYTES`,
`FIXTURE_B_BYTES`, `malformedPath`'s bytes, and every existing entry in the
`structural` array, and requires every pair to differ. (All six are
byte-distinct by construction: no other fixture in the file contains an own
`id` property on a job element.)

D4-D6 each contain jobs whose `status` values are individually valid
(`pending`, `done`, or `dead`), so the only violated rule each exercises is
job-ID uniqueness, isolating that rule from the existing `status`-enum check.
D6's first three jobs (`job-a`, `job-b`, `job-c`) are individually a
structurally valid, pairwise-distinct, fully-covering set of the three job
statuses — if the command counted incrementally instead of validating the

a job-status summary derived from `job-a`/`job-b`/`job-c` before reaching the
duplicate at index 3.

## Ambiguity log

1. **Should a duplicate/invalid job ID be a distinct error class, or fold into
   the existing invalid-state error?** Neither `SPEC.md` nor
   [`factory/rulings.md`](../rulings.md) addresses this directly. Resolved by
   following the project's existing convention, established by the shipped
   `approval-count` command (which already rejects duplicate approval IDs
   using the same generic invalid-state message) and mirrored by sibling
   ticket T-263: fold the new rules into the existing
   `state-summary: state file has invalid Relay state\n` line with no new
   exit code or message.
2. **Does approval-ID uniqueness belong in this ticket too?** No — the
   original ticket text and T-263's explicit, disjoint ownership of the
   approval-report commands establish that approval-ID uniqueness is out of
   scope here. `state-summary`'s own approval validation is unchanged.
3. **Is a job's `id` currently validated at all?** No — direct inspection of
   `app/tools/state-summary.js`'s `recordsHaveStatuses` shows it checks only
   `isRecord(record) && statuses.includes(record.status)`, never `id`. This
   ticket adds the `id` presence/type/uniqueness rules as wholly new
   structural checks; they were not silently already enforced.
4. **What counts as "duplicate"?** Resolved as JavaScript strict-equality
   (`===`) comparison of the exact string value, consistent with every other
   ID-uniqueness rule already shipped in this codebase (`approval-count`,
   T-211's `approval-recipient-count`): no trimming, case-folding, or
   Unicode normalization.
5. **Must duplicate detection be proven independent of which statuses are
   involved, and proven to happen before any output?** Resolved by freezing
   D5 (cross-status duplicate) and D6 (duplicate reached only after three
   other individually valid, distinct jobs spanning all three statuses),

6. **Do any other tickets' protected tests restrict `state-summary`'s source

   but not edited), and none inspects `app/tools/state-summary.js`'s source
   beyond running it as their own cited convention precedent. No conflict.
   The pinned readiness checker independently confirmed `READINESS PASS`.
7. **Does this ticket introduce any new global-shell-visible text requiring
   the global-literal check?** No new literal is introduced; the four
   existing literals were re-verified and each returned `GLOBAL TEXT PASS`.
8. **Does an existing operator ruling bear on this contract?**
   [`factory/rulings.md`](../rulings.md) was checked before freeze. Its
