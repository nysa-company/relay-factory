## Description

The offline `dead-jobs` command currently reports usage mistakes, unreadable
paths, malformed JSON, and invalid Relay structure through an inconsistent
exit-code and error protocol. An operator cannot tell whether to correct the
command, restore a file, or investigate corrupt state.

Align this existing command with Relay's other offline tools while preserving
its successful report bytes and read-only behavior.

## Acceptance criteria

1. Zero or two positional arguments exit `2`, write empty stdout, and write
   exactly `Usage: node app/tools/dead-jobs.js <state-file>\n` to stderr before
   any file access.
2. A missing path or directory path exits `1`, writes empty stdout, and writes
   exactly `dead-jobs: cannot read state file\n`.
3. Malformed JSON exits `1`, writes empty stdout, and writes exactly
   `dead-jobs: state file is not valid JSON\n`.
4. Structurally invalid Relay state exits `1`, writes empty stdout, and writes
   exactly `dead-jobs: invalid Relay state\n`.
5. Errors never include the input path, operating-system text, parser text,
   state content, job errors, or a second line. Validation precedence is
   arguments, read, parse, then structure.
6. Existing valid reports remain byte-for-byte unchanged, ID-sorted,
   deterministic, offline, read-only, and self-terminating.
7. Tests precede implementation. The targeted test, full app suite, and
   immutability check pass without server, dependency, schema, Factory, or
   other tool changes.

## Frozen contract — version 1

- **Freeze result:** PASS. Contract version 1 is frozen.

### Source

No `docs/` page documents the CLI offline-tool error protocol. The frozen
convention below is read from the sibling offline tools that already
implement it byte-for-byte identically: `app/tools/job-status-count.js`
(usage/read/parse/structure four-stage protocol, exit `2` for usage, exit `1`
for read/parse/structure) and `app/tools/event-count.js` (same protocol,
single-argument form). `app/tools/dead-jobs.js` currently collapses all of
read/parse/structure into one catch block reporting only
`dead-jobs: invalid Relay state\n` at exit `1`, and reports usage errors at
exit `1` instead of `2`. This contract aligns `dead-jobs.js` to the sibling
protocol without changing its validation semantics or successful-report
bytes, per the ticket Description.

### Interface (frozen)

File: `app/tools/dead-jobs.js` (Builder ownership; no other file changes; no
new `require`/import specifiers beyond `node:fs`, matching the existing
`app/tests/dead-jobs.test.js` AC5 static-inspection allowlist).

Invocation: `node app/tools/dead-jobs.js <state-file>`

Validation stages, in this exact precedence, each stage running only if the
prior stage passed:

1. **Arguments** — `process.argv.slice(2).length !== 1` (covers zero, two, or
   any other count). On failure: write nothing to stdout, write exactly
   `Usage: node app/tools/dead-jobs.js <state-file>\n` to stderr, exit `2`.
   No filesystem access occurs before this check.
2. **Read** — `fs.readFileSync(path, "utf8")` wrapped in try/catch. On throw
   (missing path, directory path, permission error, or any other read
   failure): write nothing to stdout, write exactly
   `dead-jobs: cannot read state file\n` to stderr, exit `1`.
3. **Parse** — `JSON.parse(contents)` wrapped in try/catch. On throw: write
   nothing to stdout, write exactly `dead-jobs: state file is not valid
   JSON\n` to stderr, exit `1`.
4. **Structure** — the parsed value must satisfy the existing, unchanged
   `isValidState`/`isValidJob` predicates already present in
   `app/tools/dead-jobs.js` on this branch (exactly the keys `events`,
   `jobs`, `approvals`, `outbox`, each an array, no extra top-level keys;
   every element of `jobs` a record with non-empty string `id` and
   `eventId`, `status` in `{"pending","done","dead"}`, non-negative-integer
   `attempts`/`retries`/`attemptsSinceRetry`, and `lastError` either `null`
   or a string; `events`/`approvals`/`outbox` elements are not otherwise
   validated). On failure: write nothing to stdout, write exactly
   `dead-jobs: invalid Relay state\n` to stderr, exit `1`.

No error path emits more than the one exact frozen line above, and none
includes the input path, an OS error message, a `JSON.parse` message, any
state content, or any job's `lastError`.

Success path (unchanged from current `app/tools/dead-jobs.js` behavior):
filter `state.jobs` to `status === "dead"`, map each to
`{id, eventId, attempts, retries}` (exactly these four keys, this order,
values copied unmodified), sort ascending by `id` (`<`/`>` string
comparison), write `` `${JSON.stringify(report)}\n` `` to stdout, write
nothing to stderr, exit `0`. The command never writes to the state file or
any other path.

## Frozen contract — version 2

- **Freeze result:** PASS. Contract version 2 is frozen.

### Repair note

Spec-lint round 1 found that AC1's file-snapshot check (bytes/mtime unchanged
after a two-argument run) cannot distinguish a compliant implementation from
one that reads a file before emitting the usage error, because
`fs.readFileSync` does not mutate the file it reads. This version adds a
decidable, mechanical seam — a `fs.readFileSync`-interception guard, loaded
into the child process via Node's `--require` flag — that turns "was any
read attempted" into a directly observable exit-code/stderr difference. All
other contract elements from version 1 (Source, Interface stages 1–4,
success-path bytes, frozen fixtures) are unchanged and still apply; only AC1
below is repaired, and AC2–AC7 are restated unchanged for a single
authoritative acceptance list.

### No-filesystem-access-before-argument-validation seam (frozen)

`app/tests/dead-jobs.test.js` (still the only Test-author-owned file; no new
tracked file, no new `require`/import specifier beyond the six already
allowlisted in version 1's AC5 — `node:assert`, `node:child_process`,
`node:fs`, `node:os`, `node:path`, `node:test`) must, for at least one
zero-argument run and at least one two-argument run:

1. At test run time, write a guard script to a temp file (via the
   already-imported `node:fs`/`node:os`/`node:path`) containing exactly this
   behavior: it overrides `fs.readFileSync` on the built-in `node:fs` module
   so that any call writes the literal line `GUARD-READ-CALLED\n` to stderr
   and calls `process.exit(99)` — it must not call the original
   `readFileSync` and must not throw.
2. Spawn the tool as
   `spawnSync(process.execPath, ["--require", <guard-file-path>, TOOL, ...args], { stdio: "pipe" })`
   with `...args` being the zero-argument case (`[]`) or the two-argument
   case (two paths to real, existing files, as already required by AC1).
3. Assert, for each of the two runs: `status === 2`, `stdout === ""`,
   `stderr === "Usage: node app/tools/dead-jobs.js <state-file>\n"` exactly,
   and that `stderr` does not equal, contain, or start with
   `GUARD-READ-CALLED`. A run whose stderr is `GUARD-READ-CALLED\n` and
   whose exit code is `99` proves the tool called `fs.readFileSync` before
   (or instead of) completing argument validation, and fails this
   assertion.
4. The guard file and its containing temp directory are created inside the
   same temp directory already used for that test's fixtures (via the
   existing `makeTempDir`/`fs.rmSync(dir, { recursive: true, force: true })`
   pattern already present in this file) and are removed in that test's
   cleanup, leaving no residual files on disk after the suite completes.

This is decidable because the guard makes "no read occurred" and "a read
occurred" produce byte-distinct, exit-code-distinct process outcomes — the
snapshot-only check from version 1 could not do this since a read leaves the
snapshotted file unchanged either way.
