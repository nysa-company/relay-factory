## Description

Approval IDs are identities, but the offline `pending-approvals` report accepts
duplicate IDs and may emit ambiguous rows. Reject duplicate approval IDs before
filtering or reporting.

## Acceptance criteria

1. A state containing two otherwise valid approvals with the same non-empty
   `id` exits `1`, writes exactly the existing invalid-state stderr line, and
   writes zero stdout bytes.
2. Duplicate IDs are invalid whether both approvals are pending or only one is
   pending. Complete approval validation and uniqueness checking precede the
   pending-status filter.
3. Valid unique approvals retain the existing compact array shape, field order,
   ID sort, exit statuses, and stderr messages byte-for-byte. Empty or
   no-pending state still emits `[]`.
4. Existing collection, approval field, proposed timestamp, and four-value
   status validation remain unchanged. Job IDs are not made unique by this
   ticket.
5. Failures remain redacted and leak no recipient, action, reason, state bytes,
   input path, parser detail, or operating-system detail.
6. The command remains offline, zero-dependency, deterministic, read-only, and
   self-terminating. Tests precede implementation; the targeted test, full app
   suite, and immutability check pass without other product or Factory changes.
