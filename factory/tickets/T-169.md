## Description

Add one additive, read-only detail route, `GET /api/outbox/:approvalId`, to the
zero-dependency Relay API. The route lets a caller retrieve the one sandbox
outbox receipt whose stored `approvalId` matches the path segment, without
changing Relay state or creating another outbox record.

This change is derived from Relay's sandbox-outbox behavior in
[`SPEC.md` Behavior spec items 4, 6, and 7](../../SPEC.md#behavior-spec), the
approval-gate case in [`SPEC.md` Test case 5](../../SPEC.md#test-cases-the-conformance-suite),
and the product's explicit
[`Known modeling limitation`](../../SPEC.md#known-modeling-limitation) that an
outbox write is a sandbox record rather than a real delivery. The exact success
envelope and the concurrent `app/server.js` ownership decision come from
[`factory/rulings.md`](../rulings.md). The zero-dependency and verification
constraints come from [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) and
[`AGENTS.md` Verification](../../AGENTS.md#verification).

## Acceptance criteria

1. Given the frozen two-receipt fixture, `GET
   /api/outbox/appr-outbox-detail` returns HTTP 200,
   `Content-Type: application/json`, and a parsed JSON body deeply equal to
   `{"sandbox":true,"receipt":<the fixture receipt whose approvalId is
   "appr-outbox-detail">}`; the body has no additional top-level keys and the
   selected receipt is the second, not the first, outbox item.
2. Given the same fixture, `GET /api/outbox/appr-missing` returns HTTP 404 and
   `Content-Type: application/json`, with a parsed JSON body deeply equal to
   `{"error":"no such outbox receipt"}`, with no additional keys.
3. A parsed `GET /api/state` snapshot taken before one successful detail read
   and one missing-receipt read is deeply equal to the snapshot taken after
   both reads: `outbox` still contains exactly the two fixture receipts in the
   same order, and a second successful detail read returns a body deeply equal
   to the first. Thus neither detail-route branch writes state, creates a
   sandbox receipt, or triggers an external effect.
4. The test-author commit precedes the implementation commit and changes only
   `app/tests/outbox-detail.test.js` (apart from role-owned ticket log updates);
   the builder changes only `app/server.js` (apart from role-owned ticket log
   updates). `app/package.json`, dependency lockfiles, `factory/KIT_PIN`, and
   Factory control scripts are unchanged, and both `npm test --prefix app` and
   `.github/scripts/test-immutability-check.sh` exit 0.

### HTTP interface

- Method and path: `GET /api/outbox/:approvalId`.
- `:approvalId` is one non-empty path segment and is compared by exact string
  equality with `receipt.approvalId` in `state.outbox`.
- Selection: return the stored outbox item with the matching `approvalId`.
  Relay's approval guard permits at most one receipt for an approval in normal
  product operation; duplicate `approvalId` values in manually corrupted state
  are outside this contract.
- Match response: HTTP 200 with exactly
  `{"sandbox":true,"receipt":<stored matching outbox item>}`. “Stored” means
  every key and value on that item is returned unchanged; no receipt fields
  are added, removed, renamed, or recomputed.
- No-match response: HTTP 404 with exactly
  `{"error":"no such outbox receipt"}`.
- Both responses use the existing `json` response helper and therefore have
  `Content-Type: application/json`.
- Both branches leave every parsed `/api/state` value unchanged and create no
  outbox receipt. Repeated reads return the same receipt. The route cannot
  trigger a real delivery; Relay has no production-send topology, and its only
  send result is the existing sandbox outbox record.

No UI route, markup, or selector changes. There are no UI selectors in this
contract.

### Fixture data

The test in `app/tests/outbox-detail.test.js` starts the real
`app/server.js` on its own port with a temporary `DATA_DIR` and seeds that
directory's `state.json` with this exact JSON value before startup:

```json
{
  "events": [],
  "jobs": [],
  "approvals": [],
  "outbox": [
    {
      "to": "test@example.com",
      "subject": "Other receipt",
      "body": "Not the requested receipt.",
      "approvalId": "appr-other",
      "sentAt": "2026-07-28T12:00:00.000Z"
    },
    {
      "to": "test@example.com",
      "subject": "Receipt detail",
      "body": "Requested sandbox receipt.",
      "approvalId": "appr-outbox-detail",
      "sentAt": "2026-07-28T12:00:01.000Z"
    }
  ]
}
```

The requested receipt is the second `outbox` element. The known-missing lookup
uses `appr-missing`. Tests compare parsed JSON objects with deep strict
equality; key order and insignificant wire whitespace are not acceptance
conditions.

## Ambiguity log

1. **Detail-route responses.** `SPEC.md` defines the aggregate outbox but not a
   single-receipt endpoint, success envelope, or not-found error. The
   reconciled seed ticket freezes the 404 error, and the existing
   [detail-route ruling](../rulings.md) independently freezes the success
   envelope as `{"sandbox":true,"receipt":<stored outbox item>}`.
2. **Receipt identity and stored shape.** [`SPEC.md` Behavior item 4](../../SPEC.md#behavior-spec)
   defines approval as the operation that creates the outbox record, and the
   current state model stores `approvalId` on each outbox item. Resolved as an
   exact `receipt.approvalId` match with the complete stored object returned;
   the two-receipt fixture makes wrong-item selection observable.
3. **Read-only and external-effect boundary.** The phrase “never performs an
   external send” could otherwise require an unavailable external connector.
   Resolved by [`SPEC.md` Behavior item 4](../../SPEC.md#behavior-spec) and the
   [`Known modeling limitation`](../../SPEC.md#known-modeling-limitation):
   Relay has only an in-process sandbox outbox write. AC3 therefore proves the
   detail route creates no additional sandbox write and leaves all state
   unchanged.
4. **Sibling file-boundary conflicts.** A grep of `factory/tickets/` found
   repeated Ready-generation tickets T-113 through T-165 (every fourth ticket)
   declaring the same `app/server.js` and
   `app/tests/outbox-detail.test.js` surfaces. None has a leased branch or
   active worktree. The active leased branches T-166, T-167, and T-168 were
   also inspected with `git show origin/ticket/T-XXX:factory/tickets/T-XXX.md`;
   each owns `app/server.js` but each owns a distinct test file. The existing
   [concurrent-ownership ruling](../rulings.md) authorizes the four additive
   detail routes to share `app/server.js` while protected publication remains
   serialized. T-169 therefore keeps exclusive ownership of
   `app/tests/outbox-detail.test.js` among active leases.
5. **UI and deployment topology.** The ticket adds an API detail route only.
   Resolved by explicitly freezing no UI selectors and placing cross-origin,
   auth, cookies, CORS, and preview deployment out of scope; the current
   same-origin, credential-free loopback topology remains unchanged.
