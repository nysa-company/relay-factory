## Spec'd description

Add one zero-dependency, read-only Node 18+ command,
`node app/tools/approval-timestamp.js <state-file> <approval-id>`, that reads a
persisted Relay state file without starting the service and selects one
approval by verbatim, case-sensitive ID. It emits only that approval's stored
identifier, lifecycle status, and proposal timestamp under the exact keys
`approvalId`, `status`, and `proposedAt`. This gives an operator a minimal
offline timing lookup without exposing the approval action, rejection reason,
related event payload or job error, outbox content, or unrelated state.

Product-doc sources:

- [`SPEC.md` behavior 3](../../SPEC.md#behavior-spec) defines the proposed
  action, its initial `pending` status, and the approval-before-execution gate.
- [`SPEC.md` behaviors 4-5](../../SPEC.md#behavior-spec) define the `sent`,
  `blocked_recipient`, and `rejected` approval outcomes.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the atomically
  persisted state file Relay's durable source of truth.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) establishes approvals as
  an operator-visible persisted collection.
- [`SPEC.md` conformance cases 5-7](../../SPEC.md#test-cases-the-conformance-suite)
  require approval gating, safety-blocked outcomes, and crash-recovered state
  to remain observable without duplicate effects.
- The current [`app/server.js` approval model](../../app/server.js) stores
  `id`, `jobId`, `action`, `status`, and `proposedAt`, with optional `reason`
  after rejection.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency and Factory controls outside application work.
  [`AGENTS.md` Verification](../../AGENTS.md#verification) defines the later
  full-app and immutability checks.

The command is a data-minimized projection over one existing regular file. It
does not start Relay, approve or reject a proposal, write an outbox record,
change the persisted schema, or modify the server, worker, UI, package
manifest, dependencies, lockfiles, or Factory controls.

### Valid state and successful result

For this command, a structurally valid state is a non-null, non-array JSON
object with own `events`, `jobs`, `approvals`, and `outbox` properties whose
values are arrays.

Every `approvals` element must be a non-null, non-array object with:

- a non-empty string `id`;
- a string `status` equal to exactly one of `pending`, `sent`, `rejected`, or
  `blocked_recipient`; and
- a non-empty string `proposedAt`.

Approval IDs must be pairwise distinct. Contents of `events`, `jobs`, and
`outbox`, additional top-level keys, and additional approval keys are opaque
to structural validation. In particular, `jobId`, `action`, and `reason` may
be present but are never copied to output. A referenced job need not exist.
`proposedAt` is copied as a stored non-empty string; the command does not parse,
validate as a date, reformat, or timezone-convert it.

On an exact-ID match, serialize one new object with keys in this exact order:

```json
{"approvalId":<stored id>,"status":<stored status>,"proposedAt":<stored proposedAt>}
```

Use compact `JSON.stringify` formatting and append exactly one LF byte.
Success exits `0` with empty stderr. There are no endpoint paths, HTTP request
or response shapes, UI routes, UI selectors, accessible names, or global page
shell changes in this contract.

## Ambiguity log

1. **Exact error protocol.** The seed required fixed privacy-safe errors but
   did not freeze text, exit codes, or validation precedence. No entry in
   [`factory/rulings.md`](../rulings.md) addresses offline commands. Resolved
   as exact path-independent usage, read, parse, structure, and lookup
   outcomes following the shipped offline-tool convention.
2. **Meaning of structurally valid.** The product docs establish the four
   persisted collections and approval lifecycle but do not define a general
   state-file validator. Resolved narrowly from
   [`app/server.js`](../../app/server.js): require all collection arrays and
   validate only approval `id`, `status`, and `proposedAt`, which this command
   matches or emits; unrelated collections and additive fields remain opaque.
3. **Timestamp validation.** Relay creates `proposedAt` with
   `new Date().toISOString()`, but the docs do not define an offline date
   parser, canonicalizer, or timezone conversion. Resolved by requiring a
   non-empty stored string and returning it verbatim. Fixture A freezes exact
   ISO-formatted values generated by the current model without making
   reformatting part of this command.
4. **Duplicate approval IDs.** Exact-ID selection is ambiguous if two
   approvals share an ID. Relay derives approval IDs from idempotent event IDs
   in [`app/server.js`](../../app/server.js), making persisted duplicates
   unreachable in normal operation. S17 freezes duplicate IDs as invalid and
   proves complete validation precedes array lookup.
5. **Output naming and byte determinism.** Relay stores the identifier as
   `id`, while the seed requires `approvalId`, and the seed did not specify key
   order, whitespace, or line ending. Resolved by copying stored `id` to
   `approvalId`, freezing key order `approvalId`, `status`, `proposedAt`,
   compact `JSON.stringify`, and one final LF.
6. **Exact lookup semantics.** “Exact ID” did not state whether case folding,
   trimming, decoding, or normalization was forbidden. Resolved as JavaScript
   strict string equality over the literal argument; uppercase and
   trailing-space unknown IDs distinguish those alternatives.
7. **Sensitive-field proof.** The seed names private field categories but no
   sentinels. Fixture A gives every category a `-MUST-NOT-LEAK` literal, and
   Fixture B embeds malformed-state content; byte-exact streams make leakage
   mechanically detectable.
8. **Unreadable input portability and timestamps.** Permission-denial fixtures
   are unreliable under privileged users, and ordinary reads may update
   filesystem access time. All OS read failures share the frozen result; an
   absent path and directory are portable representatives. Read-only
   invariance is measured with bytes, mode, size, modification time in
   nanoseconds, and directory entries, not access time.
9. **Cross-ticket file ownership.** A grep of every Markdown ticket found no
   other declaration of `approval-timestamp.js` or
   `approval-timestamp.test.js`. Related T-180, T-183, and T-186 approval
   inspectors own distinct paths. Because bounded concurrency is active, the
   other leased branches were also inspected with
   `git show origin/ticket/T-187:factory/tickets/T-187.md` and
   `git show origin/ticket/T-188:factory/tickets/T-188.md`; they own distinct
   outbox-receipt and job-link paths.
