## Description

The offline approval commands validate approval fields but currently accept
duplicate approval IDs. A duplicated durable identity makes the safety queues
ambiguous and can produce apparently authoritative rows for one approval.

Require approval IDs to be unique before either command filters or reports.
Preserve the existing report shapes, sorting, privacy boundaries, and all
other command behavior.

## Acceptance criteria

1. A structurally otherwise-valid state containing duplicate approval IDs
   exits `1`, writes empty stdout, and writes each command's existing exact
   invalid-Relay-state line to stderr.
2. Duplicate detection covers duplicates across any approval statuses,
   including a selected approval paired with a non-selected approval, and
   completes before filtering or output.
3. Failures do not print an approval ID, recipient, action, rejection reason,
   input path, or state content and leave the state file and sibling paths
   unchanged.
4. Existing valid blocked, pending, and empty reports remain byte-for-byte
   unchanged, ID-sorted, deterministic, offline, read-only, and
   self-terminating.
5. Existing argument, read, JSON-parse, and non-duplicate structural failures
   retain their current exact exit codes and messages.
6. Tests precede implementation. The targeted tests, full app suite, and
   immutability check pass without server, dependency, persisted-schema,
   Factory, or other tool changes.
