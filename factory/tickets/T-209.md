## Spec'd description

Add `app/tools/outbox-recipient-count.js`, a zero-dependency CommonJS command
that reads one persisted Relay state file while Relay is offline, validates the
complete stored sandbox-outbox collection, and counts receipts whose stored
`to` value is exactly equal to one operator-supplied `<recipient>`. It reports
only `{"outboxEntries":<count>}`, allowing an operator to inspect recipient
cardinality without starting Relay, changing durable state, creating a
receipt, performing a real send, or exposing the supplied recipient, stored
recipients, subjects, bodies, approval IDs, send timestamps, events, jobs,
approvals, or unrelated state.

- Repository-root invocation is exactly
  `node app/tools/outbox-recipient-count.js <state-file> <recipient>`.
- Exactly two user-supplied positional arguments are accepted. Any other arity
  exits `2`, writes zero stdout bytes, writes exactly the following single

  ```text
  usage: node app/tools/outbox-recipient-count.js <state-file> <recipient>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a

  ```text

  ```

  ```text

  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text

  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied recipient, OS error, parser text, input bytes, stack

### Structurally valid state, exact match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `outbox` element must be a non-null, non-array object with:

- own `to`, `subject`, and `body` properties, whose values are opaque;
- a non-empty string own `approvalId` property; and
- a non-empty string own `sentAt` property.

Outbox `approvalId` values must be pairwise distinct across the complete array.
Additional outbox properties are allowed and ignored. Event, job, and approval
elements are wholly opaque; only the fact that their top-level collections are
arrays is validated. An outbox `approvalId` need not resolve to a stored
approval. No relationship is imposed among `to`, `subject`, `body`,
`approvalId`, and `sentAt` beyond each field's individual rule.

The command validates the complete outbox array and approval-ID uniqueness
before counting. A receipt contributes one to the count only when its stored
`to` value is strictly equal to the supplied `<recipient>` using case-sensitive
JavaScript equality. The command does not trim, case-fold, decode, or
Unicode-normalize either value. Because command-line arguments are strings, an
opaque non-string stored `to` value never matches. A supplied recipient with
no matches is a successful query with count zero; there is no not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"outboxEntries":<nonnegative integer count>}
```

`outboxEntries` is the number of elements in the validated `outbox` array
whose stored `to` value matches the supplied recipient exactly. The supplied
recipient is not echoed. No stored recipient, subject, body, approval ID, send
timestamp, additional outbox field, event, job, approval, or top-level
metadata value is emitted.
