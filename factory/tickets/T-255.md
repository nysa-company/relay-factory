## Description

Add a zero-dependency, read-only Node command that counts persisted Relay
events whose type matches exactly and whose payload has a supplied own-property
key. This supports narrow offline event checks without starting Relay or
exposing payload values. Per `SPEC.md` "Behavior spec" item 1, a Relay event
is accepted as `{id, type, payload}`, where `payload` is an arbitrary
caller-supplied object (e.g. `{failTimes: 2}`, `{to, subject}`) — this ticket
adds a narrow read of that already-persisted shape, matching the read-only,
offline conventions established by `app/tools/event-type-count.js` and
`app/tools/event-metadata.js` (state-validity algorithm, error envelope
style, and module restrictions all reused verbatim below).

## Ambiguity log

- **Empty-string event-type/payload-key argument taxonomy.** The original
  draft AC said only "invalid arguments are rejected before file access"
  without naming the exact error envelope. Neither product doc distinguishes
  argument-count invalidity from argument-content invalidity, and no sibling
  tool in `app/tools/` validates a positional string argument's content
  before file access. Resolved by Planner convention (not escalated — this
  is CLI error-taxonomy, not product behavior): reuse the exact same frozen
  usage string and exit code 2 for both arity violations and empty-string
  content violations, keeping one "usage" bucket, consistent with every
  sibling tool's single arity-error envelope (see
  `app/tools/event-type-count.js`).
- **Payload shape eligible for the own-property check.** "Own-property key"
  is undefined for non-object payloads (the ticket's fixtures elsewhere show
  payload as either a plain object or an opaque string, e.g.
  `app/tests/event-type-count.test.js` FIXTURE_A). Resolved from
  `SPEC.md` item 1 (`payload` is always introduced as an arbitrary
  caller-supplied object, e.g. `{failTimes: 2}`) plus this codebase's
  existing `isRecord` convention (excludes `null` and arrays): only
  plain-object payloads (`isRecord`) are eligible; `null`, strings, numbers,
  booleans, and arrays never match, regardless of key. Array payloads are
  called out explicitly (AC8c) since arrays technically carry own index/
  `length` properties that a naive `Object.hasOwn` check could otherwise
  match.
- **Traversal/prototype-lookup exclusions are structurally unreachable via
  fixtures.** The ticket bans "traversal" and "prototype lookup" for the key
  check. `Object.hasOwn` inherently ignores the prototype chain, and
  `JSON.parse` output never carries inherited properties, so a fixture
  proving "no prototype lookup" is unconstructable through the state-file
  input surface. Only the one-level "no traversal into nested objects" case
  (AC8d) is fixture-checkable and is required.
- **Cross-ticket file-boundary check.** Grepped `factory/tickets/T-256.md`
  and `factory/tickets/T-257.md`: both declare disjoint Builder/Test-author
  paths (`approval-job-proposed-count.*`, `outbox-approval-sent-count.*`).
  No overlap with this ticket's `event-type-payload-key-count.*` paths.
- **Protected-test source-boundary and global-shell-text checks.** Grepped
  every `app/tests/*.js` for `readFileSync`/hash-table patterns referencing
  this ticket's two new paths: none found (files do not yet exist and no

### §2. Success output

```
{"eventsWithTypeAndPayloadKey":<N>}\n
```

where `<N>` is the decimal count with no leading zeros (standard

| Condition | stdout | stderr (exact) | exit |

The usage check runs before any filesystem access (no `readFileSync` call
occurs for arity/empty-argument failures).

### §4. State validity (`isValidState`)

Identical algorithm to `app/tools/event-type-count.js`'s `isValidState`,
reused verbatim (same `COLLECTIONS = ["events", "jobs", "approvals",
"outbox"]`, same per-event `id`/`type`/`receivedAt` non-empty-own-string and
unique-`id` checks). `payload` is never inspected by this validity check —
its presence, absence, or type never makes state invalid.

The structurally-invalid fixture corpus is the identical S1-S19 set defined
in `app/tests/event-type-count.test.js` (byte-for-byte reusable, since the
validity algorithm is unchanged): fixtures `S1`..`S19` covering non-record
state, missing/wrong-typed collections, non-record events, and missing/
empty/duplicate/wrong-typed `id`/`type`/`receivedAt`.

### §5. Matching and counting

For each `event` in `state.events`:

1. `event.type === argv[1]` (exact `===`, no normalization) — if false, skip.
2. `isRecord(event.payload)` where `isRecord(v) = v !== null && typeof v ===
   "object" && !Array.isArray(v)` — if false, skip (this excludes `null`,
   strings, numbers, booleans, and arrays; array payloads are explicitly
   excluded even though arrays carry own `length`/index properties).
3. `Object.hasOwn(event.payload, argv[2])` — own-property presence only, no
   traversal into any nested value, no key trimming, no key coercion, no
   prototype-chain lookup (prototype exclusion follows automatically:
   `Object.hasOwn` never consults the prototype chain, and
   `JSON.parse`-produced objects never carry inherited own properties).

`eventsWithTypeAndPayloadKey` is the count of events satisfying all three
steps. Zero is a valid, successful (§2) result — never an error.

### §6. Determinism and module boundary

- No writes anywhere; two consecutive invocations against one fixture file

- `app/tools/event-type-payload-key-count.js`: exactly one `require`

#### §5. Matching and counting — unchanged algorithm, gap made explicit

For each `event` in `state.events`:

1. `event.type === argv[1]` (exact `===`, no normalization) — if false, skip.
2. `isRecord(event.payload)` where `isRecord(v) = v !== null && typeof v ===

   strings, numbers, booleans, and arrays; array payloads are explicitly
   excluded even though arrays carry own `length`/index properties). When
   `event` has no `payload` own-property at all, `event.payload` evaluates
   to `undefined` by normal property access, `typeof undefined !== "object"`,
   so `isRecord(undefined)` is `false` and the event is skipped by this same
   step — no separate branch, no error, no distinct code path (AC13).
3. `Object.hasOwn(event.payload, argv[2])` — own-property presence only, no
   traversal into any nested value, no key trimming, no key coercion, no
   prototype-chain lookup (prototype exclusion follows automatically:
   `Object.hasOwn` never consults the prototype chain, and
   `JSON.parse`-produced objects never carry inherited own properties).

`eventsWithTypeAndPayloadKey` is the count of events satisfying all three
steps. Zero is a valid, successful (§2) result — never an error, including
when the only matching-type event(s) present are payload-absent (AC13a).
