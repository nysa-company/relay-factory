## Description

Add a read-only `GET /api/outbox/:approvalId` endpoint to the zero-dependency
Relay API so a client can retrieve one persisted sandbox receipt without
fetching all state. The endpoint exposes only receipts already created by the
existing allowlisted approval flow; it neither approves an action nor appends
an outbox record.

This change comes from the product's sandbox-send and state-read requirements
in [SPEC.md § Behavior spec, items 4 and 7](../../SPEC.md#behavior-spec), the
pre-/post-approval and allowlist checks in
[SPEC.md § Test cases, items 5 and 6](../../SPEC.md#test-cases-the-conformance-suite),
and the definition of a Relay send as an atomic in-process outbox write in
[SPEC.md § Known modeling limitation](../../SPEC.md#known-modeling-limitation).
It preserves the zero-dependency Node product and verification conventions in
[README.md § Verify](../../README.md#verify).

## Acceptance criteria

1. After the `outbox-detail-existing` fixture is approved, `GET
   /api/outbox/appr-outbox-detail-existing` returns HTTP `200`,
   `Content-Type: application/json`, and exactly
   `{"sandbox":true,"receipt":{"to":"test@example.com","subject":"Outbox detail subject","body":"Outbox detail body","approvalId":"appr-outbox-detail-existing","sentAt":<the exact sentAt string stored for that receipt in GET /api/state>}}`.
2. `GET /api/outbox/appr-outbox-detail-missing` returns HTTP `404`,
   `Content-Type: application/json`, and exactly
   `{"error":"no such outbox receipt"}`.
3. After the `outbox-detail-pending` fixture has produced a pending approval
   but has not been approved, `GET
   /api/outbox/appr-outbox-detail-pending` returns the same HTTP `404` headers
   and body as criterion 2.
4. Two consecutive successful reads of the existing receipt and one read of
   each `404` fixture leave `GET /api/state` deeply equal to its pre-read
   snapshot and leave the persisted `state.json` bytes unchanged; in
   particular, the existing approval remains `sent`, the pending approval
   remains `pending`, and `outbox` still contains exactly the one existing
   receipt.
5. The test-author commit adds only
   `app/tests/outbox-detail.test.js` and precedes the builder commit; the
   builder commit changes only `app/server.js`; `app/package.json`, every
   pre-existing file under `app/tests/`, and every Factory control remain
   unchanged; both `npm test --prefix app` and
   `.github/scripts/test-immutability-check.sh` exit `0`.

### Endpoint

- Method and path: `GET /api/outbox/:approvalId`.
- `:approvalId` is one non-empty path segment and is compared by exact string
  equality with `receipt.approvalId` in the persisted `state.outbox` array.
  The route therefore matches the pathname pattern
  `^/api/outbox/([^/]+)$`.
- The endpoint reads no request body.
- A matching receipt returns HTTP `200` and the existing JSON response header
  `Content-Type: application/json`.
- The success body has exactly two top-level keys:

  ```json
  {
    "sandbox": true,
    "receipt": {
      "to": "test@example.com",
      "subject": "Outbox detail subject",
      "body": "Outbox detail body",
      "approvalId": "appr-outbox-detail-existing",
      "sentAt": "<stored ISO-8601 timestamp>"
    }
  }
  ```

  `sandbox` is the boolean literal `true`. `receipt` is the stored outbox
  object without added, removed, or renamed fields; `sentAt` is the exact
  dynamically generated string already present on that object.
- If no outbox receipt has the exact `approvalId`, the endpoint returns HTTP
  `404`, `Content-Type: application/json`, and exactly:

  ```json
  {"error":"no such outbox receipt"}
  ```

  The frozen fixtures cover both an identifier absent from all approvals and
  an existing pending approval that has no outbox receipt.
- The endpoint does not call `approve`, append to `state.outbox`, change any
  approval, call `persist`, or perform network delivery. Under Relay's product
  model, the sandbox send is the existing outbox write; a detail read creates
  no send.
- No UI is added, so there are no UI selectors in this contract.

### Fixture data

`app/tests/outbox-detail.test.js` starts the real server on port `4764` with a
fresh temporary `DATA_DIR`, `WORKER_MS=50`, and
`ALLOWLIST=test@example.com`.

1. Existing-receipt fixture:
   - POST `/webhook/event`
   - body:

     ```json
     {
       "id": "outbox-detail-existing",
       "payload": {
         "to": "test@example.com",
         "subject": "Outbox detail subject",
         "body": "Outbox detail body"
       }
     }
     ```

   - wait until approval `appr-outbox-detail-existing` is pending, then POST
     `/api/approvals/appr-outbox-detail-existing/approve`;
   - read its generated `sentAt` from `/api/state` for the exact expected
     receipt.
2. Pending-without-receipt fixture:
   - POST `/webhook/event` with
     `{"id":"outbox-detail-pending","payload":{"to":"test@example.com"}}`;
   - wait until `appr-outbox-detail-pending` exists and remains `pending`;
   - do not approve or reject it.
3. Missing fixture: `appr-outbox-detail-missing` is not created.

## Ambiguity log

1. **Which identifier selects a receipt?** Outbox entries have no independent
   receipt ID; the current stored shape uses `approvalId`
   ([`app/server.js`](../../app/server.js#L98)). Resolved by exact lookup on
   `state.outbox[].approvalId`, matching the reconciled endpoint path.
2. **What happens when an approval exists but no receipt does?** SPEC.md says
   the outbox is empty before approval and remains empty for a blocked
   recipient ([Test cases 5–6](../../SPEC.md#test-cases-the-conformance-suite)).
   Resolved as the exact no-receipt `404`, rather than exposing an approval as
   a receipt.
3. **What does “stored outbox item” contain?** The current persisted write
   stores `to`, `subject`, `body`, `approvalId`, and generated `sentAt`
   ([`app/server.js`](../../app/server.js#L98)). Resolved by returning that
   object unchanged inside the already specified
   `{"sandbox":true,"receipt":...}` envelope.
4. **How is no-send behavior observable?** SPEC.md defines Relay's sandbox
   send as an atomic outbox write and states that no real delivery exists
   ([Known modeling limitation](../../SPEC.md#known-modeling-limitation)).
   Resolved by requiring the full in-memory state and persisted bytes to remain
   unchanged across reads, including no appended outbox item.
5. **Do concurrent tickets overlap this implementation surface?** Yes.
   T-122, T-123, and T-124 are all currently leased and each declares
   `app/server.js` as its builder-owned file. Their contracts add disjoint GET
   handlers (`/api/events/:id`, `/api/jobs/:id`, and
   `/api/approvals/:id`), so no product-interface decision is shared with
   T-125. T-125 remains buildable as one additive handler, but its builder and
   reviewer must preserve every sibling route present in the branch baseline;
   the overlap must not be resolved by deleting or rewriting a sibling route.
6. **Does the endpoint require auth/CORS/cookie/preview behavior?** Neither the
   product spec nor the current server defines those surfaces. Resolved by
   retaining the current same-origin, unauthenticated server topology without
   adding any such behavior.
7. **Is an operator ruling required?** `factory/rulings.md` is absent in both
   this ticket worktree and the product worktree, and the product sources above
   resolve all interface questions. No operator decision is required to freeze
   version 1.
