## Spec'd description

Add `app/tools/event-type-count.js`, a zero-dependency CommonJS command that
reads one persisted Relay state file while the service is offline and counts
events whose stored `type` is exactly equal to one operator-supplied
`<event-type>`. The command returns only the supplied type and the integer
count, so an operator can inspect the durable event collection without
starting Relay, changing persisted state, or exposing event payloads, event
IDs, timestamps, job errors, approval content, outbox content, or unrelated
state.

Product-doc and repository sources:

- [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec) defines event intake with
  `{id, type, payload}` and idempotency by exact event ID.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) defines the on-disk state
  as Relay's durable state, which this command reads without participating in
  startup or recovery.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) makes events an
  operator-visible collection, while
  [`SPEC.md` conformance cases 1, 2, and 7](../../SPEC.md#test-cases-the-conformance-suite)
  require accepted events to remain visible, duplicate IDs not to duplicate
  work, and persisted work to survive restart.
- The current [`app/server.js` state model](../../app/server.js) establishes
  the four stored collections and persists accepted events with `id`, `type`,
  `payload`, and `receivedAt`.
- The shipped
  [`event-metadata` command](../../app/tools/event-metadata.js) and its
  [acceptance suite](../../app/tests/event-metadata.test.js) establish the
  same-collection convention for a zero-dependency, redacted, read-only
  offline command and its event-state validation.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency, and [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

No endpoint, HTTP shape, UI selector, global-shell UI text, persisted schema,
server behavior, package, dependency, lockfile, Factory control,
authentication path, deployment topology, or external-send behavior changes.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/event-type-count.js <state-file> <event-type>`.
- Exactly two user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not read or create the
  candidate state path:

  ```text
  usage: node app/tools/event-type-count.js <state-file> <event-type>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  event-type-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  event-type-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  event-type-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied event type, OS error, parser text, input bytes,
  stack trace, event field, job field, approval field, outbox field, or second
  line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state, exact match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `events` element must be a non-null, non-array object with non-empty
string own properties `id`, `type`, and `receivedAt`. Event IDs must be
pairwise distinct across the complete array. Event `payload` and all
additional event fields are opaque. Job, approval, and outbox elements are
wholly opaque; only the fact that their top-level collections are arrays is
validated.

The command validates the complete event array and ID uniqueness before
counting. An event contributes one to the count only when its stored `type` is
strictly equal to the supplied `<event-type>` using case-sensitive JavaScript
string equality. The command does not trim, case-fold, decode, or Unicode-
normalize either value. A supplied type with no matches is a successful query
with count zero; there is no not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only keys, in this order, are:

```json
{"eventType":<supplied event-type>,"events":<nonnegative integer count>}
```

`eventType` copies the supplied argument exactly. `events` is the number of
elements in the validated `events` array whose stored `type` matches it
exactly. No stored event ID, type from a nonmatching event, payload,
`receivedAt`, additional event field, job, approval, outbox, or metadata value
is emitted.

## Ambiguity log

1. **What counts as an exact event-type match?** Neither the product spec nor
   [`factory/rulings.md`](../rulings.md) defines normalization. Resolved from
   the ticket's exact-match requirement and the current server's strict event
   lookups as case-sensitive JavaScript string equality. Direct literal
   `Meeting` makes case-folding observable.
2. **Is a missing type an error?** The requested behavior says a valid type
   with no matches returns zero. Resolved by making every structurally valid
   state query succeed, including empty events and the case-distinct no-match
   case; there is no not-found branch.
3. **Which value is emitted as `eventType`?** Multiple matching records have
   the same stored value, but a zero-match query has no stored value to copy.
   Resolved by copying the supplied argument exactly and freezing key order as
   `eventType`, then `events`.
4. **What state structure is required before counting?** The product has no
   general-purpose state validator. Resolved from the four collections and
   event fields in [`app/server.js`](../../app/server.js) and the declared
   [`event-metadata` fixture seam](../../app/tests/event-metadata.test.js):
   require all four arrays, validate every event's `id`, `type`, and
   `receivedAt`, require unique event IDs, and leave payload, additional event
   fields, and other collection elements opaque.
5. **How are failures classified without leaking input?** Raw OS and parser
   errors can reveal paths or state bytes. Resolved using the shipped offline
   command convention: usage exit `2`, operational exits `1`, fixed
   single-line redacted errors, empty opposite streams, and precedence from
   arity through complete structure.
6. **How are offline, read-only, and self-terminating claims proved?** Resolved
   with synchronous child invocations under a `5_000` ms timeout, exact file

   production source boundary admitting only `node:fs` and `readFileSync`.
7. **Are derived fixtures or generated expected values involved?** No invalid

   rather than a runtime casing operation. Every serialization is pairwise
   checked, and all expected identifiers, types, timestamps, and counts come

8. **Does fixture cleanup have hidden dependencies?** No service or database
   is started. Each test owns one temporary directory removed after its child
   exits, so there are no parent rows, sibling tables, foreign keys, cascades,
   resets, or teardown ordering.
9. **Do sibling or concurrently leased tickets overlap ownership?** A grep of
   all local `factory/tickets/*.md` ownership declarations found no other
   owner of either T-199 path. `git branch -r` lists no other leased ticket
   branch; nearby T-200 through T-202 own distinct count-command pairs.
10. **Do protected tests reject the new source boundary?** Direct inspection
