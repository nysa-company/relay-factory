## Spec'd description

Add one zero-dependency, read-only Node 18+ command,
`node app/tools/job-approval-count.js <state-file> <job-id>`, that selects one
persisted Relay job by exact, case-sensitive ID while Relay is offline and
counts every stored approval whose `jobId` is strictly equal to that job's
stored `id`. It emits only the selected job ID and the nonnegative integer
count under the exact keys `jobId` and `approvals`; a job with no linked
approvals succeeds with count `0`.

This gives an operator a deterministic relationship count without starting
Relay, changing durable state, or printing event payloads, job details or
errors, approval IDs, actions, statuses or reasons, outbox content, input
paths, or unrelated state.

Product-doc sources:

- [`SPEC.md` behaviors 2-3](../../SPEC.md#behavior-spec) define persisted jobs
  and the approvals produced from successful jobs.
- [`SPEC.md` behaviors 4-6](../../SPEC.md#behavior-spec) define approval
  outcomes and make the atomically persisted state file Relay's durable source
  of truth.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) establishes events, jobs,
  approvals, and outbox as the observable persisted collections.
- [`SPEC.md` conformance cases 2, 5-7](../../SPEC.md#test-cases-the-conformance-suite)
  require unique jobs, approval gating and outcomes, and crash-recovered state
  without duplicate effects.
- The current [`app/server.js` durable-state model](../../app/server.js)

  relationship counted by this command.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`

The command is a data-minimized projection over one existing regular file. It
does not execute or reject an approval, send or enqueue anything, write an
outbox record, start the server or worker, change the persisted schema, or
modify the UI, package manifest, dependencies, lockfiles, or Factory controls.

### Command-line interface and error protocol

- Repository-root invocation is exactly
  `node app/tools/job-approval-count.js <state-file> <job-id>`.
- Exactly two positional arguments are accepted. The job ID is used verbatim;
  it is not trimmed, case-folded, decoded, normalized, or prefixed.
- Zero, one, three, or four positional arguments produce exit code `2`, empty
  stdout, and exactly this single LF-terminated stderr line:

  ```text
  usage: node app/tools/job-approval-count.js <state-file> <job-id>
  ```

- The command reads the named regular file directly as UTF-8. It does not
  import, require, spawn, or execute `app/server.js`; open a listener; make an
  outbound request; or leave a timer or child process running.
- A read failure, including a nonexistent path, a directory in place of a
  regular file, or an OS read denial, produces exit code `1`, empty stdout, and
  exactly:

  ```text
  job-approval-count: cannot read state file
  ```

- Bytes rejected by `JSON.parse` produce exit code `1`, empty stdout, and
  exactly:

  ```text
  job-approval-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structural rules produces exit code
  `1`, empty stdout, and exactly:

  ```text
  job-approval-count: invalid Relay state
  ```

- A valid state with no job whose stored `id` is strictly equal to the supplied
  ID produces exit code `1`, empty stdout, and exactly:

  ```text
  job-approval-count: no such job
  ```

- Every displayed line ends with exactly one LF byte. No error contains the
  input path, supplied job ID, OS error, parser text, input content, stack
  trace, or a second line.
- Validation precedence is argument count, file read, JSON parse, complete
  structural validation, exact job lookup, then approval counting.
- The arity cases use fresh empty temporary parents. The one-argument case
  supplies nonexistent `<tmp>/state-a.json`; the three-argument case supplies
  that path, `job-approval-count-many`, and `extra-a`; the four-argument case
  adds `extra-b`. Only `<tmp>/state-a.json` is a candidate filesystem path.

### Valid state, relationship count, and result shape

For this command, structurally valid state is a non-null, non-array JSON object
with own `events`, `jobs`, `approvals`, and `outbox` properties whose values
are arrays.

Every `jobs` element must be a non-null, non-array object with a non-empty
string own property `id`. Job IDs must be pairwise distinct.

Every `approvals` element must be a non-null, non-array object with a non-empty
string own property `jobId`. Every approval's `jobId` must strictly equal one
stored job's `id`; an approval with no matching job is structurally invalid.

Contents of `events` and `outbox`, additional top-level keys, and additional
job and approval keys are allowed and ignored by this projection. The command
does not validate or emit event records, job `eventId`, status, counters or
errors, approval ID, action, status, reason or timestamp, or outbox fields.

After complete validation, select the job whose stored `id` strictly equals
`<job-id>`. Count every element of `approvals` whose stored `jobId` strictly
equals the selected job's stored `id`; approval status does not filter the
count. Success exits `0`, writes zero stderr bytes, and serializes one new
object with keys in this exact order:

```json
{"jobId":<stored job id>,"approvals":<nonnegative integer count>}
```

Use compact `JSON.stringify` formatting and append exactly one LF byte. There
are no endpoint paths, HTTP request or response shapes, UI routes, UI
selectors, or global page-shell text in this contract.
