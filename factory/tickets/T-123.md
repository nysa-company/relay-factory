## Description

Add a read-only `GET /api/jobs/:id` endpoint to the zero-dependency Relay API
so an operator or client can inspect one durable job together with the event
that created it without downloading all state. This is the single-job view of
the event-to-job relationship defined by [SPEC.md § Behavior
spec](../../SPEC.md#behavior-spec), especially items 2, 6, and 7. Its fixture
and verification follow [SPEC.md § Test cases](../../SPEC.md#test-cases-the-conformance-suite);
the zero-dependency, file-ownership, test-first, and verification constraints
come from [AGENTS.md § Boundaries](../../AGENTS.md#boundaries),
[AGENTS.md § Workflow](../../AGENTS.md#workflow), and
[AGENTS.md § Verification](../../AGENTS.md#verification).

## Acceptance criteria

1. With the frozen `job-detail-001` fixture loaded and before a worker tick,
   `GET /api/jobs/job-job-detail-001` returns HTTP `200`, content type
   `application/json`, and a parsed body deeply equal to
   `{"job":<the stored job whose id is "job-job-detail-001">,"event":<the stored event whose id equals that job's eventId>}`;
   the two objects have exactly the fields and values listed in Frozen
   contract § Successful response.
2. `GET /api/jobs/missing-job` returns HTTP `404`, content type
   `application/json`, and the exact response body
   `{"error":"no such job"}`.
3. After creating the frozen fixture, performing the successful request from
   criterion 1 and the missing-job request from criterion 2 leaves both the
   parsed `GET /api/state` response and the bytes of
   `<DATA_DIR>/state.json` exactly equal to snapshots taken before those two
   requests.
4. The test-author commit precedes the implementation commit; after excluding
   permitted durable-record updates to `factory/tickets/T-123.md` and
   `factory/ledger.csv`, the former changes only
   `app/tests/job-detail.test.js` and the latter changes only `app/server.js`.
   `npm test --prefix app` passes, and no other path under `factory/` or
   `.github/` changes.

### Endpoint

- Method and path: `GET /api/jobs/:id`.
- `:id` is matched against `state.jobs[].id` using exact string equality.
- The endpoint is served by the existing Relay HTTP server on the same origin
  as `/api/state`; it introduces no authentication, cookies, CORS behavior,
  cross-origin request, or preview-deploy topology.
- It is read-only: neither the successful nor unknown-job path calls
  `persist()` or mutates any object in `state`.
- No UI is in scope, so there are no UI selectors.

### Successful response

For a matching job, return status `200`, header
`Content-Type: application/json`, and this exact JSON shape:

```json
{
  "job": {
    "id": "job-job-detail-001",
    "eventId": "job-detail-001",
    "status": "pending",
    "attempts": 0,
    "lastError": null,
    "retries": 0,
    "attemptsSinceRetry": 0
  },
  "event": {
    "id": "job-detail-001",
    "type": "meeting",
    "payload": {
      "failTimes": 99,
      "to": "test@example.com",
      "subject": "Job detail fixture",
      "body": "Fixture body."
    },
    "receivedAt": "<receivedAt>"
  }
}
```

`job` is the stored job object itself as exposed in `GET /api/state`; `event`
is the stored event for which `event.id === job.eventId`. `<receivedAt>` is the
ISO timestamp generated while accepting the fixture and captured from
`GET /api/state`; the detail response must return that exact string. No fields
may be added, omitted, renamed, or transformed.

### Unknown-job response

When no stored job has the requested id, return status `404`, header
`Content-Type: application/json`, and exactly:

```json
{"error":"no such job"}
```

### Fixture

- Start `app/server.js` with an isolated temporary `DATA_DIR`,
  `WORKER_MS=600000`, and `ALLOWLIST=test@example.com`. The test may allocate
  any unused local port.
- Create the fixture with `POST /webhook/event` and this exact JSON body:

```json
{
  "id": "job-detail-001",
  "type": "meeting",
  "payload": {
    "failTimes": 99,
    "to": "test@example.com",
    "subject": "Job detail fixture",
    "body": "Fixture body."
  }
}
```

- Snapshot both `GET /api/state` and `<DATA_DIR>/state.json` after the event
  POST and before either detail request. The long worker interval keeps the
  frozen job in the `pending`, zero-attempt state during the assertions.

## Ambiguity log

- **Response envelope and exact fields:** the seed criterion required the
  stored job and its related event but did not name the envelope. Resolved as
  singular `job` and `event` properties containing the untransformed stored
  objects. This follows the event-to-job relation in
  [SPEC.md § Behavior spec](../../SPEC.md#behavior-spec) items 2 and 7 and the
  existing `/api/state` domain names; it adds no new product behavior.
- **Worker race in the fixture:** a normal worker tick would change
  `attempts`, `status`, and possibly approvals while read-only assertions run.
  Resolved with `WORKER_MS=600000`, using the documented `WORKER_MS` config in
  [SPEC.md § Test cases](../../SPEC.md#test-cases-the-conformance-suite), and
  by snapshotting after fixture creation.
- **Meaning of read-only:** observing only the HTTP response would not detect
  a write that preserves parsed values. Resolved by requiring equality of
  both `/api/state` and the durable `state.json` bytes before and after both
  detail requests, grounded in atomic persistence from
  [SPEC.md § Behavior spec](../../SPEC.md#behavior-spec) item 6.
- **Existing retry route:** `POST /api/jobs/:id/retry` already shares the jobs
  path prefix. Resolved by freezing both method and complete path:
  `GET /api/jobs/:id` cannot consume the POST-only `/retry` route.
- **Concurrent file ownership:** T-122, T-124, and T-125 each declare Builder
  ownership of `app/server.js` on the other three leased branches
  (`origin/ticket/T-122`, `origin/ticket/T-124`, and
  `origin/ticket/T-125`). Their current ticket records were inspected with
  `git show`; each proposes a distinct additive GET route and none has a
  frozen contract or implementation yet. Resolved for T-123 by limiting its
  builder surface to the job-detail handler and private lookup only. The
  dispatcher must serialize integration/rebase shared-file additions; T-123
  does not claim or alter the sibling endpoint contracts.
- **Topology applicability:** the route is a same-server read endpoint and
  does not involve cross-origin access, authentication, cookies, previews, or
  sends. No domains, SameSite policy, CORS allowlist, credentials mode, or
  `external` label is required.
