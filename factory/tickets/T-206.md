## Spec'd description

Add `app/tools/outbox-count.js`, a zero-dependency CommonJS command that reads
one persisted Relay state file while Relay is offline, validates the complete
stored sandbox-outbox collection, and reports only its total cardinality as
`{"outboxEntries":<count>}`. This gives operators a deterministic count without
starting Relay, changing durable state, creating a receipt, performing a real
send, or exposing approval IDs, recipients, subjects, bodies, send timestamps,
events, jobs, approvals, or unrelated stored content.

Product-doc and repository sources:

- [`SPEC.md` behavior 4](../../SPEC.md#behavior-spec) defines approval as the
  operation that creates one sandbox outbox record and defines the
  blocked-recipient outcome as creating no send.
- [`SPEC.md` behaviors 6 and 7](../../SPEC.md#behavior-spec) make the
  atomically persisted state file Relay's durable source and make the outbox
  operator-visible, while
  [`SPEC.md` conformance cases 5-7](../../SPEC.md#test-cases-the-conformance-suite)
  require the approval gate, allowlist outcome, and duplicate-free recovery.
- [`SPEC.md`'s known modeling limitation](../../SPEC.md#known-modeling-limitation)
  defines each outbox item as an in-process sandbox record rather than an
  external delivery.
- The current [`app/server.js` state model](../../app/server.js) establishes
  the four stored collections and persists each outbox receipt with own `to`,
  `subject`, `body`, `approvalId`, and `sentAt` properties.
- The shipped [`state-summary` command](../../app/tools/state-summary.js) and
  its [acceptance suite](../../app/tests/state-summary.test.js) establish the
  one-path, compact-JSON, redacted, read-only offline-summary convention. The
  shipped [`event-count`](../../app/tools/event-count.js),
  [`job-count`](../../app/tools/job-count.js), and
  [`approval-count`](../../app/tools/approval-count.js) commands establish the
  count-only envelope and complete selected-collection validation. The shipped
  [outbox-detail acceptance suite](../../app/tests/outbox-detail.test.js)

- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency, and [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/outbox-count.js <state-file>`.
- Exactly one user-supplied positional argument is accepted. Any other arity
  exits `2`, writes zero stdout bytes, writes exactly the following single
  LF-terminated line to stderr, and does not read or create a candidate state
  path:

  ```text
  usage: node app/tools/outbox-count.js <state-file>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  outbox-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  outbox-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  outbox-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, OS error, parser text, input bytes, stack trace, outbox field,
  event field, job field, approval field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `outbox` element must be a non-null, non-array object with:

- own `to`, `subject`, and `body` properties, whose values are opaque;
- a non-empty string own `approvalId` property; and
- a non-empty string own `sentAt` property.

Outbox `approvalId` values must be pairwise distinct across the complete array.
Additional outbox properties are allowed and ignored. Event, job, and approval
elements are wholly opaque; only the fact that their top-level collections are
arrays is validated. An outbox `approvalId` need not resolve to a stored
approval. No relationship is imposed among `to`, `subject`, `body`,
`approvalId`, and `sentAt` beyond each field's individual rule.

The command validates the complete outbox array and approval-ID uniqueness
before counting. Success exits `0`, writes zero stderr bytes, and writes one
compact JSON object followed by exactly one LF. Its only key is:

```json
{"outboxEntries":<nonnegative integer count>}
```

`outboxEntries` is exactly the validated `outbox` array length. No stored
recipient, subject, body, approval ID, send timestamp, additional outbox field,
event, job, approval, or top-level metadata value is emitted.

## Ambiguity log

1. **Does "all outbox entries" mean array cardinality or unique approval IDs?**
   Resolved from [`SPEC.md` behaviors 4 and 6](../../SPEC.md#behavior-spec) and
   the current state model: a structurally valid receipt has one unique
   `approvalId`, then the result is exactly `state.outbox.length`; no filtering
   or deduplication is performed. S19 makes duplicate receipt identity invalid
   instead of silently changing the count.
2. **What state structure is required before counting?** The product has no
   general-purpose receipt validator. Resolved from the four collections and
   receipt fields in [`app/server.js`](../../app/server.js), the declared
   [`state-summary` fixture seam](../../app/tests/state-summary.test.js), the
   shipped [outbox-detail suite](../../app/tests/outbox-detail.test.js), and
   the three shipped collection-count commands: require all four arrays,
   validate every outbox receipt's five persisted properties and unique
   `approvalId`, allow additional top-level and receipt fields, and leave
   sibling collection elements opaque.
3. **Must message values be strings, timestamps parse as ISO-8601, or receipt
   IDs resolve to approvals?** `app/server.js` always persists the five keys,
   but action values originate in webhook payloads and existing offline
   validators treat selected timestamp fields as non-empty strings without
   resolving related collections. Resolved by treating `to`, `subject`, and
   `body` as opaque, requiring non-empty string `approvalId` and `sentAt`,
   imposing no cross-record relationship, and freezing Fixture A with opaque
   non-string message values, a non-ISO `sentAt`, and no matching approval.
4. **Why require unique outbox `approvalId` values?** The
   [outbox-detail contract](T-169.md#http-interface) records that Relay's
   approval guard permits at most one receipt per approval, and
   [`SPEC.md` conformance case 7](../../SPEC.md#test-cases-the-conformance-suite)
   requires recovery without duplication. Resolved by rejecting duplicate
   receipt identities before counting; no new product outcome is introduced.
5. **How are failures classified without leaking input?** Raw OS and parser
   errors can reveal paths or state bytes. Resolved using the shipped
   count-command convention: usage exit `2`, operational exits `1`, fixed
   single-line redacted errors, empty opposite streams, and precedence from
   arity through complete structure.
6. **How are offline, read-only, and self-terminating claims proved?** Resolved
   with synchronous child invocations under a `5_000` ms timeout, exact file
   and directory fingerprints, repeated success, isolated teardown, and a
   production source boundary admitting only `node:fs` and `readFileSync`.
7. **Are derived fixtures or generated expected values involved?** No invalid
   fixture is transformed from valid data. Every serialization is pairwise
   byte-compared, and all expected identifiers, timestamps, and counts come
   from literal test setup.
8. **Does fixture cleanup have hidden dependencies?** No service or database
   is started. Each test owns one temporary directory removed after its child
   exits, so there are no parent rows, sibling tables, foreign keys, cascades,
   resets, or teardown ordering.
9. **Do sibling or concurrently leased tickets overlap ownership?** A grep of
   every local `factory/tickets/*.md` ownership declaration and inspection of
   every remote `origin/ticket/T-*` ticket record found no other owner of
   either T-206 path. T-198 and T-202 concern outbox counts but own distinct
   tool and test filenames.
10. **Do protected tests reject the new source boundary?** Direct inspection of
    `app/tests/state-summary.test.js`, `app/tests/outbox-detail.test.js`,
    `app/tests/factory-contract.test.js`, count-tool suites, and tracked source
    assertions found only tool-specific boundaries. The pinned readiness check
    returned `READINESS PASS`, so `Protected-Test-Conflicts: none` is exact.
11. **Does protected global text collide?** The pinned global-literal checker
    accepted every shell-visible literal named in the criteria checklist. No
    accessible UI name is added.
12. **Are deployment, authentication, or external-send details applicable?**
    No. The complete topology is a local process reading one local path and
    writing stdout/stderr; there is no network, UI, credential, preview, or
    send path, so no `external` label is required.
13. **Does an existing operator ruling change the contract?**

    detail-route ruling is consistent with the cited stored-receipt shape, and
