## Spec'd description

Add `app/tools/outbox-approval-subject-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while Relay is offline,
validates the complete stored sandbox-outbox collection, and counts receipts
whose stored `approvalId` **and** stored `subject` are each strictly equal to
one operator-supplied `<approval-id>` and `<subject>`. It reports only
`{"outboxWithApprovalAndSubject":<count>}`, allowing an operator to inspect an
approval/subject pair's outbox cardinality without starting Relay, changing
durable state, looking up or echoing a stored approval, creating a receipt,
performing a real send, or exposing either supplied argument, stored IDs,
recipients, subjects, bodies, send timestamps, events, jobs, approvals, or
unrelated state.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/outbox-approval-subject-count.js <state-file> <approval-id> <subject>`.
- A valid invocation supplies exactly three positional arguments, and both
  `<approval-id>` and `<subject>` must be non-empty strings. Any other arity,
  or an empty-string `<approval-id>` or `<subject>` at arity 3, exits `2`,
  writes zero stdout bytes, writes exactly the following single LF-terminated
  line to stderr, and does not read or create a candidate state path:

  ```text
  usage: node app/tools/outbox-approval-subject-count.js <state-file> <approval-id> <subject>
  ```

  (Ambiguity log item 1 records why the empty-argument case is folded into
  this usage-error class rather than given a distinct error line.)
- After that validation, the command synchronously reads `<state-file>`
  directly as UTF-8 via `readFileSync`. Any failure, including an absent
  path, a directory in place of a regular file, or an OS read denial, exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  outbox-approval-subject-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  outbox-approval-subject-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  outbox-approval-subject-count: invalid Relay state
  ```

- Failure precedence is argument validation (arity and non-emptiness), file
  read, JSON parse, complete structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error
  includes the state path, either supplied argument, an OS error, parser
  text, input bytes, a stack trace, or any outbox/event/job/approval field.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state, exact match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `outbox` element must be a non-null, non-array object with:

- own `to`, `subject`, and `body` properties, whose values are opaque
  (any JSON type, not required to be strings);
- a non-empty string own `approvalId` property; and
- a non-empty string own `sentAt` property.

Outbox `approvalId` values must be pairwise distinct across the complete
array. Additional outbox properties are allowed and ignored. Event, job, and
approval elements are wholly opaque; only the fact that their top-level
collections are arrays is validated.

The command validates the complete outbox array and `approvalId` uniqueness
before counting. A receipt contributes one to the count only when its stored
`approvalId` is strictly equal (`===`) to the supplied `<approval-id>` **and**
its stored `subject` is strictly equal (`===`) to the supplied `<subject>`.
Neither supplied value is trimmed, case-folded, decoded, coerced, prefixed,
or normalized; a numeral-shaped string argument (for example `"7"`) never
matches a stored JSON number (for example `7`). A query with no matching
receipt is a successful count of `0`; there is no approval lookup and no
not-found error.

Because a structurally valid outbox has pairwise-distinct `approvalId`
values, the only successful counts are `0` and `1`. Success exits `0`, writes
zero stderr bytes, and writes one compact JSON object followed by exactly one
LF. Its only key is:

```json
{"outboxWithApprovalAndSubject":<0-or-1>}
```

The supplied `approvalId` and `subject` are not echoed. No stored approval
ID, recipient, subject, body, send timestamp, additional outbox field, event,
job, approval, or top-level metadata value is emitted.

## Ambiguity log

1. **Is an empty `<approval-id>` or `<subject>` a valid zero-match query, or
   an invalid argument?** The seeded, frozen ticket description states
   explicitly: "Approval ID and subject must be non-empty ... Invalid
   arguments are rejected before file access." This is a deliberate
   divergence from the earlier shipped `outbox-approval-count` convention
   (where an empty approval ID was an accepted, always-zero query) — the same
   "must be non-empty" language also appears in the concurrently seeded,
   still-unplanned siblings T-252 and T-254, so this is a consistent product
   decision for this ticket generation, not a one-off. No further product-doc
   ambiguity remains about *whether* emptiness is invalid. The remaining
   design choice — resolved here without escalation because it is a
   mechanical detail, not a product behavior — is which error class reports
   it. Folding it into the existing arity/usage class (exit `2`, the existing
   usage line, no new error string) was chosen because: (a) it keeps the
   error fully generic and non-revealing (no supplied value is echoed, same
   as every other error line); (b) it requires no new redacted-error
   convention beyond the three already shipped by every sibling count tool;
   and (c) "rejected before file access" is already the defining property of
   the usage-error class for every shipped tool in this family. AC4 exercises
   both single-field-empty combinations and the both-empty combination so the
   Test-author's fixture matrix cannot special-case only one argument.
2. **What counts as an exact match for two independent fields?** Resolved
   from the ticket's "match stored values exactly and case-sensitively"
   requirement and the shipped `outbox-recipient-count` convention: plain
   `===` per field, no trimming, case folding, decoding, or coercion. AC1's
   same-subject/different-`approvalId` receipt and AC3's approval-only /
   subject-only cases directly prove the two fields are combined with AND,
   not OR — a receipt only counts when both fields match the same receipt.
3. **Can the combined count exceed one?** No. Resolved the same way as
   T-212: [`app/tools/outbox-approval-count.js`](../../app/tools/outbox-approval-count.js)
   and its
   [acceptance suite](../../app/tests/outbox-approval-count.test.js) require
   pairwise-distinct `approvalId` values before counting, and this ticket
   inherits that same validation unchanged (it adds a `subject` comparison,
   not a new uniqueness rule). Since at most one receipt can share the
   queried `approvalId`, the combined AND count is bounded to `0` or `1`.
4. **Is `subject` constrained to be a string?** No. Resolved from
   [`app/server.js`](../../app/server.js) and the shipped `outbox-*-count`
   validators (`outbox-approval-count.js`, `outbox-recipient-count.js`):
   `to`, `subject`, and `body` are opaque and only required to be own
   properties, not of any particular type. Fixture A's third receipt stores
   `subject: 7` (a JSON number) to prove a numeral-shaped string query
   argument (`"7"`) never coerces to match it, mirroring
   `outbox-recipient-count`'s existing numeric-`to` coverage.
5. **Does this command select from the `approvals` collection?** No. Same
   reasoning as T-212: the seed asks to count outbox entries by their stored
   `approvalId` and `subject`; approval elements remain opaque, an outbox
   `approvalId` need not resolve to a stored approval, and no supplied or
   stored ID is echoed.
6. **What state structure is required before counting?** Resolved from the
   four collections and receipt fields in
   [`app/server.js`](../../app/server.js), the shipped `outbox-approval-count`
   and `outbox-recipient-count` commands, and the declared
   [`outbox-detail` fixture seam](../../app/tests/outbox-detail.test.js):
   require all four arrays, validate every outbox receipt's five persisted

   receipt fields, and leave sibling collection elements opaque. Unchanged
