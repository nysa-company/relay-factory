## Description

Add a read-only `GET /api/jobs/:id` detail route to the zero-dependency Relay
API so an operator or API client can inspect one durable job together with the
event that created it without fetching and filtering all of `/api/state`.
Relay's [behavior spec](../../SPEC.md#behavior-spec) requires every accepted
event to enqueue one durable job and requires durable state to survive restart;
the [conformance cases](../../SPEC.md#test-cases-the-conformance-suite) make the
event/job relationship and recorded attempts observable. The exact response
envelope and concurrent file-ownership decision come from the prior
[detail-route ruling](../rulings.md). The implementation remains within the
product boundary in [`app/server.js`](../../app/server.js), preserves the
[zero-dependency boundary](../../AGENTS.md#boundaries), and neither performs nor
enables an external send.

#### HTTP interface

- Method and path: `GET /api/jobs/:id`, where `:id` is one non-empty path
  segment.
- Lookup: select the stored `state.jobs` entry whose string `id` exactly equals
  `:id`, then select the stored `state.events` entry whose string `id` exactly
  equals that job's `eventId`.
- Existing job: return HTTP `200`, header `Content-Type: application/json`, and
  parsed JSON exactly equal to
  `{"job":<stored job>,"event":<stored related event>}`. The two stored objects
  are returned without projection, normalization, or additional fields.
- Unknown job: return HTTP `404`, header
  `Content-Type: application/json`, and parsed JSON exactly equal to
  `{"error":"no such job"}`.
- Both outcomes are read-only: they do not mutate in-memory state, call the
  persistence path, or change `$DATA_DIR/state.json`.
- Malformed persisted state containing a job with no related event is outside
  this contract. Relay-created durable state cannot contain that relationship
  because event acceptance enqueues and persists the event and job together.
- No UI selector is introduced. No authentication, cookie, CORS, cross-origin,
  or preview-deploy behavior changes; the route uses the existing Relay server
  origin and transport.

#### Deterministic fixture

`app/tests/job-detail.test.js` creates an isolated `DATA_DIR`, writes the
following JSON to `state.json` before starting the server, starts the server
with `WORKER_MS=60000`, and waits for `/health` before exercising the route:

```json
{
  "events": [
    {
      "id": "event-job-detail",
      "type": "meeting",
      "payload": {
        "failTimes": 99
      },
      "receivedAt": "2026-07-28T12:00:00.000Z"
    }
  ],
  "jobs": [
    {
      "id": "job-event-job-detail",
      "eventId": "event-job-detail",
      "status": "dead",
      "attempts": 3,
      "lastError": "simulated failure on attempt 3",
      "retries": 0,
      "attemptsSinceRetry": 3
    }
  ],
  "approvals": [],
  "outbox": []
}
```

The existing-resource request is
`GET /api/jobs/job-event-job-detail`; the unknown-resource request is
`GET /api/jobs/job-missing`. The dead job keeps the fixture stable while the
worker interval is active.

## Ambiguity log

- **What is the exact detail response envelope?** The aggregate-state behavior
  in the [Relay spec](../../SPEC.md#behavior-spec) does not define a detail
  route. Resolved by the prior
  [operator ruling](../rulings.md): the success body is exactly
  `{"job":<stored job>,"event":<stored related event>}` and the unknown-job
  body is exactly `{"error":"no such job"}`.
- **Which event belongs to a job?** Resolved from the
  [behavior spec](../../SPEC.md#behavior-spec) and current durable model:
  `job.eventId` equals the originating event's `id`; the contract freezes that
  exact lookup and returns both stored objects unchanged.
- **How is read-only behavior made observable?** Resolved from the
  [atomic-persistence requirement](../../SPEC.md#behavior-spec): compare both
  the public `/api/state` value and the durable `state.json` bytes before and
  after successful and missing-resource reads.
- **How is an orphaned job handled?** The product docs define only
  Relay-created state, where event and job are persisted together. No malformed
  state recovery behavior is specified, so orphan handling is explicitly
  outside this ticket rather than invented.
- **How is a deterministic job kept stable under the worker?** Resolved from
  the [dead-letter conformance case](../../SPEC.md#test-cases-the-conformance-suite):
  the fixture uses a dead job at three attempts, so the current worker does not
  process it.
- **Do sibling tickets overlap the implementation boundary?** Yes. A grep of
  `factory/tickets/` found historical job-detail tickets and the current
  `app/server.js` ownership declarations. Under bounded concurrency,
  `origin/ticket/T-166`, `origin/ticket/T-168`, and
  `origin/ticket/T-169` were also inspected with `git show`; all three own
  `app/server.js`. The prior
  [concurrent-ownership ruling](../rulings.md) explicitly permits these four
  additive detail routes, with protected publication serialized and each later
  branch refreshed from protected main before merge.
- **Does this require deploy or external-action topology?** No. The endpoint is
  an unauthenticated read on the existing server origin; it changes no cookie,
  CORS, cross-origin, credential, or preview behavior and cannot invoke the
  approval/send paths. `External: no` therefore remains correct and no
  `external` label is required.
