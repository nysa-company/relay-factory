## Spec'd description

Add `app/tools/outbox-approval-sent-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while Relay is offline,
validates the complete stored sandbox-outbox collection, and counts receipts
whose stored `approvalId` **and** `sentAt` are both strictly equal to two
operator-supplied literals `<approval-id>` and `<sent-at>`. It reports only
`{"outboxWithApprovalAndSentAt":<count>}`, letting an operator confirm one
specific delivery attempt's outbox cardinality without starting Relay,
changing durable state, looking up or echoing a stored approval, creating a
receipt, performing a real send, or exposing the supplied literals, stored
IDs, recipients, subjects, bodies, other timestamps, events, jobs, approvals,
or unrelated state.

- Exactly three user-supplied positional arguments are accepted. Any other

### Structurally valid state, compound exact match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `outbox` element must be a non-null, non-array object with:

- own `to`, `subject`, and `body` properties, whose values are opaque;
- a non-empty string own `approvalId` property; and
- a non-empty string own `sentAt` property.

Outbox `approvalId` values must be pairwise distinct across the complete
array — this uniqueness invariant is keyed on `approvalId` alone, matching
`app/server.js`'s one-receipt-per-approval model and the shipped
`outbox-approval-count` contract; `sentAt` participates in no uniqueness
check. Additional outbox properties are allowed and ignored. Event, job, and
approval elements are wholly opaque; only the fact that their top-level
collections are arrays is validated. An outbox `approvalId` need not resolve
to a stored approval. No relationship is imposed among `to`, `subject`,
`body`, `approvalId`, and `sentAt` beyond each field's individual rule; in
particular `sentAt` is never parsed as a date, validated as ISO-8601, or
compared as a timestamp.

The command validates the complete outbox array and `approvalId` uniqueness
before matching. A receipt contributes one to the count only when **both**
its stored `approvalId` is strictly equal to the supplied `<approval-id>`
**and** its stored `sentAt` is strictly equal to the supplied `<sent-at>`,
using case-sensitive JavaScript equality for each field independently. A
receipt matching only one of the two fields contributes nothing. Neither
supplied value is trimmed, case-folded, decoded, prefixed, or normalized. The
empty string is an accepted positional argument for either field but cannot
equal any structurally valid non-empty stored `approvalId` or `sentAt`. A
supplied pair with no match is a successful query with count zero; there is
no approval lookup and no not-found error.

Because a structurally valid outbox has pairwise-distinct `approvalId`
values, at most one receipt can match a given `approvalId`, so the only
successful counts are `0` and `1`. Success exits `0`, writes zero stderr
bytes, and writes one compact JSON object followed by exactly one LF. Its
only key is:

```json
{"outboxWithApprovalAndSentAt":<0-or-1>}
```

`outboxWithApprovalAndSentAt` is `1` if the validated `outbox` array contains
a receipt whose stored `approvalId` and `sentAt` both match the two supplied
literals, else `0`. Neither supplied literal is echoed. No stored
`approvalId`, `sentAt`, recipient, subject, body, additional outbox field,
event, job, approval, or top-level metadata value is emitted.

## Ambiguity log

1. **What counts as an exact match for `<approval-id>` and `<sent-at>`?**
   Resolved from the ticket's exact-match requirement, the strict equality
   used by [`app/server.js`](../../app/server.js) for outbox receipt
   identity, and the shipped exact field-matching command convention:
   case-sensitive JavaScript strict equality with no trimming, case folding,
   decoding, prefixing, or normalization, applied independently to each
   field.
2. **Is a single-field match (approval ID matches but sent timestamp does
   not, or vice versa) sufficient for a count?** No. The ticket title and AC2
   ("Approval ID and sent timestamp must be non-empty and match stored
   strings exactly") name a compound predicate. Resolved as logical AND: both
   fields must match the same receipt. The two cross-field trap fixtures
   (AC3) make this observable and would fail under an OR interpretation.
3. **Is an unknown or empty pair an error?** No. Resolved from the original
   ticket criterion that every valid-state no-match returns
   `{"outboxWithApprovalAndSentAt":0}\n` and from exactly-three-argument
   arity. AC3 passes actual zero-byte arguments for each field; AC7 proves
   neither can bypass state validation.
4. **Does this command select from the `approvals` collection?** No. The seed
   asks to count outbox entries by their stored `approvalId` and `sentAt` and
   requires a valid no-match to return zero. Resolved as an outbox-only
   query: approval elements remain opaque, an outbox ID need not resolve to
   an approval, and no supplied or stored value is echoed.
5. **Why can a successful count not exceed one?** Complete outbox validation
   is resolved from the shipped
   [`outbox-approval-count` contract](T-212.md#structurally-valid-state-exact-match-and-successful-output):
   `approvalId` values are non-empty strings and pairwise distinct before
   matching. Because the compound predicate requires `approvalId` equality as
   one of its two conjuncts, at most one receipt can ever match, matching
   `SPEC.md` conformance case 7 and normal Relay operation's one receipt per
   approval.
6. **Does the uniqueness invariant key on `approvalId` alone, or on the
   `(approvalId, sentAt)` pair?** `approvalId` alone. Resolved from
   `app/server.js` line 98, which pushes exactly one outbox record per
   approved action keyed by the approval's own id — `sentAt` is a
   consequence, not a co-key. S19 freezes two receipts sharing one
   `approvalId` with two different `sentAt` values and requires the
   invalid-state result, proving `sentAt` cannot be used to admit duplicate
   `approvalId` values.

   already treated as opaque by the shipped validators; Fixture A's third
   receipt freezes a non-ISO `sentAt` value to prove no format is enforced.
