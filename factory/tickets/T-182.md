## Description

Add `app/tools/event-job-link.js`, a zero-dependency Node 18+ command that reads
one persisted Relay state file without starting the service, selects one event
by case-sensitive exact ID, and reports only that event ID plus its stored
job's ID and status. An event without a related job is reported with two
explicit `null` values. The command never emits event payloads, job errors,
approval data, or outbox data and never changes the input filesystem.

This operational link follows the one-event/one-job and idempotency behavior in
[`SPEC.md` Behavior spec items 1–2](../../SPEC.md#behavior-spec), the persisted
and offline-recovery requirements in
[`SPEC.md` Behavior spec items 6–7](../../SPEC.md#behavior-spec), and the job
status outcomes in
[`SPEC.md` conformance cases 2–4](../../SPEC.md#test-cases-the-conformance-suite).
The stored relation and status names come from the current
[`app/server.js` durable-state and domain model](../../app/server.js). The
standalone, dependency-free boundary follows
[`AGENTS.md` Boundaries](../../AGENTS.md#boundaries), while test-first ordering
and verification follow [`AGENTS.md` Workflow and Verification](../../AGENTS.md#workflow)
and [`docs/git-flow.md`](../../docs/git-flow.md).

### Command interface and output

- Invocation is exactly
  `node app/tools/event-job-link.js <state-file> <event-id>`.
- Exactly two arguments after the script path are accepted. Any other arity
  exits `2`, writes no stdout, writes exactly
  `usage: node app/tools/event-job-link.js <state-file> <event-id>\n` to
  stderr, and does not inspect either supplied path.
- `<event-id>` is matched case-sensitively against stored event `id`. The
  command validates the complete link-relevant state before looking up the
  requested event.
- The command synchronously reads `<state-file>` as UTF-8, parses and validates
  it in memory, writes its result, and exits. It does not import or start
  `app/server.js`, open a network socket, spawn a process, or write, rename,
  chmod, truncate, or delete any path.
- A known event exits `0`, writes no stderr, and writes exactly one compact
  JSON object followed by one LF to stdout. Property order is `eventId`,
  `jobId`, `jobStatus`; no other property is present.
- If exactly one job has `eventId` equal to the selected event's `id`, `jobId`
  and `jobStatus` are that stored job's `id` and `status`. If no job has that
  `eventId`, both properties are JSON `null`.
- A structurally valid state without the requested event exits `1`, writes no
  stdout, and writes exactly `event-job-link: event not found\n` to stderr.
- Output never copies event `type`, `payload`, or `receivedAt`; job counters or
  `lastError`; approval records, actions, reasons, or statuses; outbox records;
  input paths; parser text; operating-system errors; stack traces; or any
  unconsumed field.

### Input validation and error precedence

A link-valid Relay state is a non-null, non-array JSON object with own
properties `events`, `jobs`, `approvals`, and `outbox`, each an array.
Additional top-level properties are allowed and ignored.

Every `events` element must be a non-null, non-array object whose `id` is a
nonempty string. Event IDs must be unique. Other event properties are allowed
and ignored.

Every `jobs` element must be a non-null, non-array object with:

- `id`: a nonempty string, unique across jobs;
- `eventId`: a nonempty string equal to exactly one stored event `id`, unique
  across jobs so one event cannot have two jobs; and
- `status`: exactly `pending`, `done`, or `dead`.

Other job properties are allowed and ignored. An event may have no job, which
is the frozen `null` result. Approval and outbox elements are not consumed or
validated beyond their collections being arrays.

After argument validation, failures are classified in this order:

1. A nonexistent path, non-regular path, or any filesystem read failure exits
   `1` with empty stdout and exactly
   `event-job-link: state file is unreadable\n` on stderr.
2. Readable bytes rejected by `JSON.parse` exit `1` with empty stdout and
   exactly `event-job-link: state file is not valid JSON\n` on stderr.
3. Parsed JSON that is not link-valid exits `1` with empty stdout and exactly
   `event-job-link: state file has invalid Relay state\n` on stderr.
4. Link-valid state without the requested event uses the frozen not-found
   result above.

### Ambiguity log

   `job.eventId` to stored `event.id`; do not derive a job ID from the event ID.

   job fields. Frozen as an event that exists with no matching job, producing
   JSON `null` for both `jobId` and `jobStatus`; a missing event remains a
   distinct fixed error.

   and [`SPEC.md` durable collections](../../SPEC.md#behavior-spec): validate
   the four collections plus every event ID and consumed job link/status field;
   allow unrelated fields and do not create a second schema for approval or
   outbox entries.

   event ID and one job per accepted event. Duplicate event IDs, duplicate job

  Findings:

  1. AC1 is the only criterion that invokes the command against a linked event,
     and it asserts `"jobStatus":"dead"`. No criterion selects
     `event-link-other` (`pending`) or `event-link-done` (`done`), so the frozen
     behavior "`jobStatus` is that stored job's `status`" is never
     distinguished from emitting the literal `dead`. An implementation that
     looks up the job and hard-codes `"dead"` — or that reads any always-`dead`
     field — passes AC1 through AC7 while misreporting every live `pending` or
     `done` job, which is the ordinary case for real Relay state written by
     `app/server.js`. The contract also asserts of itself that "the `done` job
     exercises the third valid status", which the criteria do not do, so the
     contract and the acceptance criteria contradict each other here. Add one
     criterion selecting `event-link-done` with exact stdout
     `{"eventId":"event-link-done","jobId":"job-event-link-done","jobStatus":"done"}\n`
     and one selecting `event-link-other` with exact stdout
     `{"eventId":"event-link-other","jobId":"job-event-link-other","jobStatus":"pending"}\n`,
     or drop the two unreachable statuses from the contract.
  2. Ambiguity log 1 freezes the relation as "match stored `job.eventId` to
     stored `event.id`; do not derive a job ID from the event ID", but every
     job in Frozen Fixture A has `id` exactly equal to `"job-" + eventId`
