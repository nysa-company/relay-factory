## Spec'd description

Add one zero-dependency, read-only Node 18+ command,
`node app/tools/approval-link.js <state-file> <approval-id>`, that selects one
persisted approval by exact, case-sensitive ID while Relay is offline. It
follows the approval's stored `jobId` to the matching job and emits only the
approval ID, that job's stored event ID, and the approval status under the
exact keys `approvalId`, `eventId`, and `status`.

This gives an operator a deterministic approval-to-event link without starting
Relay, changing durable state, or printing approval actions, rejection
reasons, event payloads, job errors, outbox content, or unrelated state.

Product-doc sources:

- [`SPEC.md` behaviors 2-3](../../SPEC.md#behavior-spec) define the persisted
  job-to-event relationship and the approval produced by a successful job.
- [`SPEC.md` behaviors 4-6](../../SPEC.md#behavior-spec) define approval
  outcomes and make the atomically persisted state file Relay's durable source
  of truth.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) establishes events, jobs,
  approvals, and outbox as the observable persisted collections.
- [`SPEC.md` conformance cases 2, 5-7](../../SPEC.md#test-cases-the-conformance-suite)
  require event/job uniqueness, approval gating, blocked-send visibility, and
  crash-recovered state without duplicate effects.
- The current [`app/server.js` durable-state model](../../app/server.js)
  establishes approval fields `id`, `jobId`, and `status`, job fields `id` and
  `eventId`, the exact four approval statuses, and the relationship traversed
  by the existing approval detail route.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`

The command is a data-minimized projection over one existing regular file. It
does not execute or reject an approval, send or enqueue anything, write an
outbox record, start the server or worker, change the persisted schema, or
modify the UI, package manifest, dependencies, lockfiles, or Factory controls.

### Command-line interface and error protocol

- Repository-root invocation is exactly
  `node app/tools/approval-link.js <state-file> <approval-id>`.
- Exactly two positional arguments are accepted. The approval ID is used
  verbatim; it is not trimmed, case-folded, decoded, normalized, or prefixed.
- Zero, one, three, or four positional arguments produce exit code `2`, empty
  stdout, and exactly this single LF-terminated stderr line:

  ```text
  usage: node app/tools/approval-link.js <state-file> <approval-id>
  ```

- The command reads the named regular file directly as UTF-8. It does not
  import, require, spawn, or execute `app/server.js`; open a listener; make an
  outbound request; or leave a timer or child process running.
- A read failure, including a nonexistent path, a directory in place of a
  regular file, or an OS read denial, produces exit code `1`, empty stdout, and
  exactly:

  ```text
  approval-link: cannot read state file
  ```

- Bytes rejected by `JSON.parse` produce exit code `1`, empty stdout, and
  exactly:

  ```text
  approval-link: state file is not valid JSON
  ```

- A parsed value that fails the frozen structural rules produces exit code
  `1`, empty stdout, and exactly:

  ```text
  approval-link: invalid Relay state
  ```

- A valid state with no approval whose stored `id` is strictly equal to the
  supplied ID produces exit code `1`, empty stdout, and exactly:

  ```text
  approval-link: no such approval
  ```

- Every displayed line ends with exactly one LF byte. No error contains the
  input path, approval ID, OS error, parser text, input content, stack trace,
  or a second line.
- Validation precedence is argument count, file read, JSON parse, complete
  structural validation, then exact approval lookup.
- The arity cases use fresh empty temporary parents. The one-argument case
  supplies nonexistent `<tmp>/state-a.json`; the three-argument case supplies
  that path, `appr-pending`, and `extra-a`; the four-argument case adds
  `extra-b`. Only `<tmp>/state-a.json` is a candidate filesystem path.

### Valid state, relationship traversal, and result shape

For this command, structurally valid state is a non-null, non-array JSON object
with own `events`, `jobs`, `approvals`, and `outbox` properties whose values
are arrays.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string own property `id`;
- non-empty string own property `jobId`; and
- string own property `status` equal to exactly one of `pending`, `sent`,
  `rejected`, or `blocked_recipient`.

Approval IDs must be pairwise distinct.

Every `jobs` element must be a non-null, non-array object with non-empty string
own properties `id` and `eventId`. Job IDs must be pairwise distinct. Every
approval's `jobId` must strictly equal one stored job's `id`; an approval with
no matching job is structurally invalid.

Contents of `events` and `outbox`, additional top-level keys, and additional
approval and job keys are opaque. Job status, counters, timestamps and errors;
approval action, reason and timestamp; event records and payloads; and outbox
fields are never copied to output. The job's stored `eventId` is reported
without joining or validating a matching event record.

After complete validation, select the approval whose stored `id` strictly
equals `<approval-id>`, then select the job whose stored `id` strictly equals
that approval's `jobId`. Success exits `0`, writes zero stderr bytes, and
serializes one new object with keys in this exact order:

```json
{"approvalId":<stored approval id>,"eventId":<stored related job eventId>,"status":<stored approval status>}
```

Use compact `JSON.stringify` formatting and append exactly one LF byte. There
are no endpoint paths, HTTP request or response shapes, UI routes, UI
selectors, or global page-shell text in this contract.

## Ambiguity log

1. **Meaning of the event relationship.** The seed named `eventId` but an
   approval stores only `jobId`. Resolved from
   [`app/server.js`](../../app/server.js): follow `approval.jobId` to
   `job.id`, then copy that job's stored `eventId`. The command does not join
   the event collection because no event field is emitted.
2. **Missing and ambiguous links.** The seed did not define an approval whose
   job is absent or duplicated. Relay creates jobs before approvals and derives
   unique IDs from idempotent event IDs. Complete validation therefore rejects
   dangling approval links and duplicate approval/job IDs; S16, S23, and S24
   make each result observable.
3. **Structural-validation depth.** The product has no general state-file
   validator. Resolved narrowly: validate all four collection arrays, every
   approval field consumed or emitted, every job field needed for the join,
   ID uniqueness, and relationship closure. Events, outbox records, and
   unrelated fields stay opaque.
4. **Exact errors and precedence.** The seed required fixed redacted errors but
   did not freeze text, exit codes, or ordering. No entry in
   [`factory/rulings.md`](../rulings.md) changes offline command errors.
   Resolved as the exact usage/read/parse/structure/lookup protocol above,
   following the shipped offline-command convention.
5. **Lookup and serialization.** “Exact ID” did not state trimming or case
   behavior, and deterministic JSON did not fix key order or line ending.
   Resolved as strict equality over the literal argument, compact
   `JSON.stringify`, key order `approvalId`, `eventId`, `status`, and one final
   LF. Uppercase and trailing-space misses distinguish normalization choices.
6. **Sensitive-data proof.** The seed named excluded categories but supplied no
   sentinels. Fixture A gives event payload, job errors, approval actions and
   rejection reason, outbox content, and additive state unique
   `MUST-NOT-LEAK` tokens; Fixture B embeds malformed-state content.
7. **Unreadable-input portability.** Permission-denial fixtures are unreliable
   under privileged users. All OS read failures share one result; an absent
   path and a directory path are the portable frozen representatives.
8. **Cross-ticket file ownership.** A grep of every local Markdown ticket and
   inspection of remote ticket branches T-187 through T-191 found no other
   declaration of `app/tools/approval-link.js` or
   `app/tests/approval-link.test.js`. Those branches own distinct outbox,
