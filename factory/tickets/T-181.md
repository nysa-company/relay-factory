## Spec'd description

Add `app/tools/outbox-inspect.js`, a zero-dependency Node 18+ command that reads
one persisted Relay state file while the service is offline and selects one
sandbox outbox receipt by exact approval ID. It emits only the stored
`approvalId` and `sentAt`. This gives an operator a deterministic receipt
lookup without starting Relay, changing state, or exposing the recipient,
subject, body, event payloads, job errors, or approval content.

Product-doc sources:

- [`SPEC.md` behavior 4](../../SPEC.md#behavior-spec) defines an approved
  allowlisted send as a sandbox outbox record.
- [`SPEC.md` behaviors 6-7](../../SPEC.md#behavior-spec) define persisted
  on-disk state and the outbox collection this command reads offline.
- [`SPEC.md` conformance cases 5-7](../../SPEC.md#test-cases-the-conformance-suite)
  require sends to appear only after approval, blocked sends not to appear,
  and persisted work not to duplicate across restart.
- [`SPEC.md` known modeling limitation](../../SPEC.md#known-modeling-limitation)
  establishes that Relay's receipt is the persisted in-process outbox record,
  not evidence of real delivery.
- The current [`app/server.js` durable-state model](../../app/server.js)
  establishes the stored receipt fields and approval-ID link.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps the app
  zero-dependency, and [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

The command is a read-only projection over the existing state file. It does
not start the service, approve or reject an action, send a message, write an
outbox record, or change the server, persisted schema, worker, package
manifest, dependencies, UI, or Factory controls.

### Command-line interface and errors

- Repository-root invocation is exactly
  `node app/tools/outbox-inspect.js <state-file> <approval-id>`.
- Exactly two positional arguments are accepted. Relative state paths resolve
  from the command process's working directory; acceptance tests use absolute
  temporary paths.
- Zero, one, or three positional arguments produce exit code `2`, empty
  stdout, and exactly this single LF-terminated stderr line:

  ```text
  usage: node app/tools/outbox-inspect.js <state-file> <approval-id>
  ```

- The command reads `<state-file>` directly as UTF-8. Any read failure,
  including an absent path, a directory in place of a file, or an OS read
  denial, produces exit code `1`, empty stdout, and exactly:

  ```text
  outbox-inspect: cannot read state file
  ```

- Bytes rejected by `JSON.parse` produce exit code `1`, empty stdout, and
  exactly:

  ```text
  outbox-inspect: state file is not valid JSON
  ```

- A parsed value that fails the frozen structural rules produces exit code
  `1`, empty stdout, and exactly:

  ```text
  outbox-inspect: invalid Relay state
  ```

- A valid state with no outbox item whose stored `approvalId` is strictly
  equal to the supplied `<approval-id>` produces exit code `1`, empty stdout,
  and exactly:

  ```text
  outbox-inspect: outbox receipt not found
  ```

- Validation precedence is argument count, read, JSON parse, complete
  structural validation, then receipt lookup.
- Errors never contain the state path, approval ID, OS error, parser text,
  input bytes, stack trace, event content, job content, approval content,
  recipient, subject, body, or a second line. Every displayed error is
  terminated by exactly one LF.
- No path is written, renamed, deleted, chmodded, or created.

### Structurally valid state and successful output

For this command, structurally valid state is a non-null, non-array JSON object
with own `events`, `jobs`, `approvals`, and `outbox` properties whose values
are arrays.

Every `outbox` element must be a non-null, non-array object with these own
properties:

- non-empty string `approvalId`; and
- non-empty string `sentAt`.

Outbox approval IDs must be pairwise distinct. Contents of `events`, `jobs`,
and `approvals`, additional top-level properties, and additional outbox
properties are opaque to structural validation. In particular, `to`,
`subject`, and `body` may be present but are never copied to output. `sentAt`
is copied as stored without date parsing or normalization.

The lookup uses exact, case-sensitive JavaScript string equality and does not
trim, normalize, decode, or case-fold either ID. Success exits `0`, writes
zero stderr bytes, and writes one compact JSON object plus exactly one LF. Its
only keys, in order, are:

```json
{"approvalId":<stored approvalId>,"sentAt":<stored sentAt>}
```

No endpoint, HTTP shape, route, UI selector, or global page-shell text is
introduced.

## Ambiguity log

1. **Receipt identity and safe output.** The seed names exact approval-ID
   lookup and safe receipt metadata but does not freeze serialization.
   [`SPEC.md` behavior 4](../../SPEC.md#behavior-spec) and the current
   [`app/server.js` outbox write](../../app/server.js) identify `approvalId`
   and `sentAt` as the non-message receipt fields. Resolved as the exact
   two-key compact object above, with stored values copied unchanged.
2. **Meaning of structurally valid.** The product has no general state-file
   validator. Resolved narrowly: validate all four collections, then every
   outbox field needed for exact lookup and output; treat unrelated
   collections, message fields, and additive fields as opaque.
3. **Duplicate receipt IDs.** The docs do not state a generic duplicate-row
   policy. The current server derives one approval ID per event and refuses a
   second approval execution after status leaves `pending`, while conformance
   case 7 requires no duplicate send after restart. Duplicate outbox
   `approvalId` values are therefore frozen as invalid rather than selecting
   one arbitrarily.
4. **Exact lookup and errors.** The seed does not specify normalization, error
   text, exit codes, or precedence. No entry in
   [`factory/rulings.md`](../rulings.md) addresses offline receipt
   inspection. Resolved as strict case-sensitive equality, usage exit `2`,
   operational exits `1`, four path-independent lines, and the frozen
   precedence above.
5. **Sensitive-data boundary.** “Never prints recipient, subject, or body”
   does not provide test values. Fixture A gives selected and unselected
   receipt message fields and every related collection a distinct
   `-MUST-NOT-LEAK` token; exact stream checks make leakage mechanically
   observable.
6. **Read-only and self-termination proof.** Resolved with 5-second child
   timeouts, signal checks, repeated invocation, byte/stat/directory-entry
   comparisons, and the exact production module/API boundary. No service or
   network module is admitted.
7. **Cross-ticket file ownership.** Repository-wide grep found no other
   declaration of either T-181-owned path. Active leased branches T-182 and
   T-183 and in-flight remote branches T-178 and T-179 were inspected; they
   own distinct job, event, event-job-link, and approval-job-link paths.
   Canceled T-177's event-inspector paths are also distinct. There is no
   concurrent file-boundary conflict.
8. **Protected source and global text.** The declared
   `app/tests/outbox-detail.test.js` seam and all tracked tests contain no
   static boundary for the new file. The pinned readiness check accepted
   every fixed shell-visible literal, so no protected-test conflict
   declaration or fixture-seam expansion is required.
9. **Topology, lifecycle, and external effects.** This is an offline local
   file read with isolated temporary fixtures and no database or network
   path. Auth, cookies, CORS, origins, credentials, preview deployment, UI
   selectors, generated values, dependent rows, and external sends do not
   apply. `External: no` remains correct.
