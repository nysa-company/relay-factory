## Spec'd description

Add `app/tools/job-status-count.js`, a zero-dependency CommonJS command that
reads one persisted Relay state file while Relay is offline, validates the
complete stored job collection, and counts jobs whose stored `status` is
strictly equal to one operator-supplied `<status>`. It emits only
`{"jobsWithStatus":<count>}`, allowing an operator to inspect queue-state
cardinality without starting Relay, changing durable state, or exposing the
supplied status, job IDs, event links, counters, errors, events, approvals,
outbox entries, or other stored content.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/job-status-count.js <state-file> <status>`.
- Exactly two user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not read or create a candidate
  state path:

  ```text
  usage: node app/tools/job-status-count.js <state-file> <status>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  job-status-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  job-status-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  job-status-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied status, OS error, parser text, input bytes, stack
  trace, job ID, event link, counter, `lastError`, event field, approval field,
  outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.
  For the directory fixture, the frozen observable is the exact command
  envelope above, not any errno, error class, or operating-system text.

### Structurally valid state, exact match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with exactly four own properties: `events`, `jobs`, `approvals`,
and `outbox`, each an array.

Every `jobs` element must be a non-null, non-array object with:

- non-empty string own properties `id` and `eventId`;
- an own `status` property exactly equal to `pending`, `done`, or `dead`;
- own `attempts`, `retries`, and `attemptsSinceRetry` properties that are
  integers greater than or equal to zero; and
- an own `lastError` property equal to `null` or a string, including `""`.

Job IDs must be pairwise distinct across the complete array. Additional job
properties are allowed and ignored. Event, approval, and outbox elements are
wholly opaque; only the fact that their top-level collections are arrays is
validated. A job `eventId` need not resolve to a stored event. No relationship
is imposed among `status`, the three counters, and `lastError` beyond each
field's individual rule.

The command validates the complete job array and ID uniqueness before
counting. A job contributes one to the count only when its stored `status` is
strictly equal to the supplied `<status>` using case-sensitive JavaScript
string equality. The command performs no trimming or case folding. The
supplied argument need not be a member of the stored status enum; any supplied
string with no exact match, including `Dead`, ` dead`, and `""`, is a
successful query with count zero.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"jobsWithStatus":<nonnegative integer count>}
```

`jobsWithStatus` is the number of elements in the validated `jobs` array whose
stored `status` matches the supplied status exactly. The supplied status is not
echoed. No stored job ID, `eventId`, status, counter, `lastError`, additional
job field, event, approval, or outbox value is emitted.
