## Spec'd description

Add a focused, read-only `GET /api/jobs/:id` endpoint to Relay's
zero-dependency HTTP API. A caller that knows a job ID can retrieve that exact
stored job together with the accepted event identified by the job's `eventId`,
without fetching and filtering the complete `/api/state` document. The route
does not process work, persist state, alter the UI, or perform a send.

This is an additive projection of:

- [SPEC.md § Behavior spec](../../SPEC.md#behavior-spec), especially items 2,
  6, and 7: each accepted event creates one related durable job, state is
  persisted atomically, and the aggregate state is available as JSON.
- [SPEC.md § Test cases](../../SPEC.md#test-cases-the-conformance-suite),
  especially cases 1–4: events, jobs, attempts, and dead-letter state are
  observable conformance data.
- [AGENTS.md § Boundaries](../../AGENTS.md#boundaries): `app/` remains the
  zero-dependency conformance product and Factory controls remain separate.
- [AGENTS.md § Workflow](../../AGENTS.md#workflow) and
  [§ Verification](../../AGENTS.md#verification): test-author commits precede
  implementation, role file ownership remains separated, and both required
  repository checks run before completion.
- The pinned engine's
  [ticket sequence](https://github.com/nysa-company/software-factory/blob/f4fe9a4d856b24dde2c2f4b166d7c233d53e948a/docs/workflows/ticket-flow.md#sequence)

## Frozen contract — version 1

This is the exact contract for the test-author and builder. If it proves
wrong, return T-119 to Ready and re-plan it as a new numbered contract version;
do not edit version 1 in place.

### HTTP interface and lookup

- Method and path: `GET /api/jobs/:id`.
- The route matches `url.pathname` with `^/api/jobs/([^/]+)$`. `:id` is one
  non-empty path segment and is compared exactly to `job.id`.
- The job lookup is
  `state.jobs.find(job => job.id === id)`. For a found job, the related event
  lookup is
  `state.events.find(event => event.id === job.eventId)`.
- The route reads no request body.
- The route remains on Relay's existing unauthenticated, same-origin HTTP
  service. It introduces no domain, cross-origin request, CORS header,
  credential mode, cookie, `SameSite` setting, or preview-deploy behavior.

### Existing-job response

For a found job and its related event, return HTTP `200` with
`Content-Type: application/json`. The parsed JSON body has exactly this shape:

```json
{
  "job": "<the complete stored job object, unchanged>",
  "event": "<the complete stored event object whose id equals job.eventId, unchanged>"
}
```

`job` and `event` are the only top-level fields. The endpoint does not add,
remove, rename, default, or transform any nested field. It returns all stored
job fields (`id`, `eventId`, `status`, `attempts`, `lastError`, `retries`, and
`attemptsSinceRetry`) and all stored event fields (`id`, `type`, `payload`, and
`receivedAt`) unchanged.

Manually corrupted durable state containing a job without its related event is
outside this contract. Relay's accepted-event transition creates the event and
job together before the atomic persist required by
[SPEC.md § Behavior spec](../../SPEC.md#behavior-spec) items 2 and 6.

### Unknown-job response

If no stored job has `id === :id`, return HTTP `404` with
`Content-Type: application/json` and exactly:

```json
{"error":"no such job"}
```

There is no `ok`, `job`, `event`, or other response field.

### Read-only guarantee

Neither response path calls `persist()` or mutates an object or array in
`state`. After each request, the complete value returned by `GET /api/state`
and the bytes of `$DATA_DIR/state.json` are unchanged from immediately before
that request. The route does not create an approval or outbox item and cannot
perform an external send.

### Frozen fixture and exact successful body

`app/tests/job-detail.test.js` owns one isolated server fixture. Before server
startup, it creates a fresh temporary `DATA_DIR` and writes the following
complete value to `$DATA_DIR/state.json`:

```json
{
  "events": [
    {
      "id": "job-detail-event-1",
      "type": "meeting",
      "payload": {"failTimes": 99},
      "receivedAt": "2026-07-27T00:00:00.000Z"
    }
  ],
  "jobs": [
    {
      "id": "job-detail-1",
      "eventId": "job-detail-event-1",
      "status": "dead",
      "attempts": 3,
      "lastError": "simulated failure on attempt 3",
      "retries": 0,
      "attemptsSinceRetry": 3
    }
  ],
  "approvals": [],
  "outbox": []
}
```

The server configuration is:

```text
PORT=4762
DATA_DIR=<the fresh temporary directory above>
WORKER_MS=600000
ALLOWLIST=test@example.com
```

The dead job gives the worker no pending transition during assertions. For
`GET /api/jobs/job-detail-1`, the exact parsed response body is:

```json
{
  "job": {
    "id": "job-detail-1",
    "eventId": "job-detail-event-1",
    "status": "dead",
    "attempts": 3,
    "lastError": "simulated failure on attempt 3",
```

The representative unknown ID is `job-missing`.

## Ambiguity log

- **What is the exact successful response envelope?** The reconciled ticket
  freezes a response containing exactly the stored job and related event.
  Version 1 names the two existing state entities with the existing collection
  nouns `job` and `event`, permits no other top-level key, and preserves every
  nested stored field. This is consistent with
  [SPEC.md § Behavior spec](../../SPEC.md#behavior-spec) items 2 and 7.
- **How is the relationship selected?** Resolved from the ticket's
  `event.id === job.eventId` requirement and the event-to-job model in
  [SPEC.md § Behavior spec](../../SPEC.md#behavior-spec) item 2: exact job ID
  lookup is followed by exact event ID lookup.
- **How can “exactly stored” avoid timestamp and worker timing ambiguity?**
  Resolved with a complete static dead-job fixture. Dead-letter state is
  required to be visible by
  [SPEC.md § Behavior spec](../../SPEC.md#behavior-spec) item 2 and
  [§ Test cases](../../SPEC.md#test-cases-the-conformance-suite) case 4, and a
  dead job has no worker transition.
- **How is read-only behavior distinguished from rewriting identical JSON?**
  Resolved from the atomic persistence requirement in
  [SPEC.md § Behavior spec](../../SPEC.md#behavior-spec) item 6 by checking
  both deep-equal in-memory state and byte-identical durable state after each
  found and not-found request.
- **What happens for an orphaned job?** Product behavior creates an event and
  its job in one persisted transition. Recovery for manually corrupted state
  is not specified, so it is excluded rather than invented.
- **Do concurrent tickets overlap the implementation surface?** Yes. The
  sibling scan found `app/server.js` builder ownership in T-110 through T-121.
  The three other currently leased branches were also inspected directly at
  `origin/ticket/T-118`, `origin/ticket/T-120`, and
  `origin/ticket/T-121`; all own `app/server.js`, all currently contain the
  same server blob as `origin/main`, and their route paths and test files are
  distinct. T-119 owns only `GET /api/jobs/:id` and
  `app/tests/job-detail.test.js`; it does not own or remove sibling detail
  routes. Protected publication must serialize the shared-file branches,
  incorporate routes already merged to `main`, and rerun the required checks,
  as directed by the pinned engine's
  [parallel-work guidance](https://github.com/nysa-company/software-factory/blob/f4fe9a4d856b24dde2c2f4b166d7c233d53e948a/docs/git-flow.md#parallel-kit-development).
- **Does deployment topology require a decision?** No. This is a same-origin
  read on the existing unauthenticated service and adds no auth, cookies, CORS,
  credentials, domains, or preview deployment.
- **Can this ticket trigger an external send?** No. Both response paths are
  read-only and do not touch approvals or outbox state. `External: no` remains
  correct and no `external` label is required.
- **Was there a prior product/security ruling?** No
  `factory/rulings.md` exists in the product worktree, so no prior ruling
  applies and no operator question remains.
