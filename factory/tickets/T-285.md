## Spec'd description

Add `app/tools/approval-event-type-count.js`, a zero-dependency, read-only,
offline CommonJS command that reads one persisted Relay state file, validates
the complete stored `events`, `jobs`, and `approvals` collections plus every
approval→job→event reference among them, and counts approvals whose
referenced job's referenced event has a stored `type` strictly equal
(case-sensitive) to one operator-supplied `<event-type>`. It reports only
`{"approvalsForEventType":<count>}`, letting an operator ask "how many
proposed actions trace back to events of type X" without starting Relay,
changing durable state, or exposing any stored ID, event payload, job error,
approval action, approval reason, outbox content, timestamp, or unrelated
state.

Product-doc and repository sources:

- [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec) defines webhook-accepted
  events, each carrying a `type`.
- [`SPEC.md` behavior 2](../../SPEC.md#behavior-spec) defines exactly one
  background job enqueued per accepted event — the job→event link this
  command joins across.
- [`SPEC.md` behavior 3](../../SPEC.md#behavior-spec) defines a successful job
  producing one proposed action (an approval) in state `pending` — the
  approval→job link this command joins across.
- [`SPEC.md` behaviors 4 and 5](../../SPEC.md#behavior-spec) define the full
  approval status lifecycle (`pending`→`sent`/`blocked_recipient` via
  approve, `pending`→`rejected` via reject); T-285 counts every approval
  regardless of its status.
- [`SPEC.md` behaviors 6 and 7](../../SPEC.md#behavior-spec) make the
  atomically persisted state file Relay's durable, operator-visible source.
- The current [`app/server.js`](../../app/server.js) state model establishes
  the exact persisted shapes this command validates: event
  `{id, type, payload, receivedAt}`; job `{id, eventId, status, attempts,
  retries, attemptsSinceRetry, lastError}` created with `id: "job-" + evt.id`
  and `eventId: evt.id`; approval `{id, jobId, action:{to,subject,body},
  status, proposedAt[, reason]}` created with `id: "appr-" + job.eventId` and
  `jobId: job.id`.
- The shipped [`event-type-count` command](../../app/tools/event-type-count.js)
  and its [acceptance suite](../../app/tests/event-type-count.test.js)
  (Fixture-Seam) establish exact case-sensitive type matching, minimal event
  structural validation (`id`, `type`, `receivedAt` all non-empty strings,
  unique `id`), and the "zero matches is a successful zero count" convention.
- The shipped [`approval-link` command](../../app/tools/approval-link.js) and
  its [acceptance suite](../../app/tests/approval-link.test.js) (Fixture-Seam)
  establish the approval→job→event join, minimal job/approval structural
  validation (`id`/`eventId` and `id`/`jobId` non-empty strings, unique per
  collection), and the redacted single-line error-envelope convention.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency; [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

T-285 differs from both seam commands. Unlike `event-type-count`, it counts
approvals, not events, and does not echo the supplied type in its output.
Unlike `approval-link`, it selects across every stored approval by event type
rather than looking up one approval by ID, does not require or echo
`approval.status`, and additionally requires every job's `eventId` and every
approval's `jobId` to resolve to a structurally valid sibling record. That
resolution rule is new relative to both seams (`event-type-count` never
validates jobs or approvals; `approval-link` accepts a job's `eventId`
without checking it against the events collection) because a *count* over the
complete collection, unlike a single-record lookup, is only sound if every
join in the full collection is proven resolvable up front — an unresolved or
duplicate reference anywhere must fail the whole query rather than being
silently skipped or silently counted.

No endpoint, HTTP shape, UI selector, global-shell UI text, persisted schema,
server behavior, package, dependency, lockfile, Factory control,
authentication path, deployment topology, or external-send behavior changes.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/approval-event-type-count.js <state-file> <event-type>`.
- Exactly two user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not read or create a
  candidate state path:

  ```text
  usage: node app/tools/approval-event-type-count.js <state-file> <event-type>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8 via `readFileSync`. Any read failure — an absent path, a
  directory in place of a regular file, or an OS read denial — exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  approval-event-type-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  approval-event-type-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules below
  exits `1`, writes zero stdout bytes, and writes exactly:

  ```text
  approval-event-type-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation (including every cross-collection reference), then
  counting.
- Every error is one fixed line terminated by exactly one LF. No error
  includes the state path, supplied event type, OS error, parser text, input
  bytes, stack trace, event payload, job error, approval action, approval
  reason, outbox field, timestamp, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state, the join, exact match, and successful output

A structurally valid state is a parsed non-null, non-array JSON object with
own `events`, `jobs`, `approvals`, and `outbox` properties whose values are
arrays. Additional top-level properties (e.g. `metadata`) are allowed and
ignored. `outbox` elements are wholly opaque — only the fact that `outbox` is
an array is validated; no `outbox` element is inspected.

Every `events` element must be a non-null, non-array object with own
non-empty string `id`, `type`, and `receivedAt` properties. Event `id` values
must be pairwise distinct across the complete `events` array.

Every `jobs` element must be a non-null, non-array object with own non-empty
string `id` and `eventId` properties. Job `id` values must be pairwise
distinct across the complete `jobs` array. Every job's `eventId` must equal
exactly one validated event's `id` (a dangling `eventId` is invalid state,
independent of whether any approval references that job). No other job
property (`status`, `attempts`, `retries`, `attemptsSinceRetry`, `lastError`)
is validated or used.

Every `approvals` element must be a non-null, non-array object with own
non-empty string `id` and `jobId` properties. Approval `id` values must be
pairwise distinct across the complete `approvals` array. Every approval's
`jobId` must equal exactly one validated job's `id` (a dangling `jobId` is
invalid state, independent of whether that job's own `eventId` would resolve).
No other approval property (`action`, `status`, `proposedAt`, `reason`) is
validated or used.

Not every event needs a referencing job, and not every job needs a
referencing approval — only the forward references (job→event, approval→job)
require resolution; there is no requirement that every event or job be
reachable from an approval.

The command validates the complete `events`, `jobs`, and `approvals` arrays
and every job→event and approval→job reference before counting. An approval
contributes one to the count only when, following its `jobId` to a job and
that job's `eventId` to an event, the event's `type` is strictly equal
(case-sensitive JavaScript `===`, no trimming, case-folding, or
normalization) to the supplied `<event-type>`. A supplied type with no match
is a successful query with count zero; there is no per-approval lookup error
and no not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON
object followed by exactly one LF. Its only key is:

```json
{"approvalsForEventType":<n>}
```

`approvalsForEventType` is the number of approvals in the validated
`approvals` array whose event-type join (approval→job→event) matches the
supplied `<event-type>` exactly. The supplied type is not echoed. No stored
ID, event payload, job error, approval action, approval reason, outbox field,
or top-level metadata value is emitted.

## Ambiguity log

1. **Does the output echo the supplied event type?** No. AC1's literal text
   ("compact JSON containing exactly one `approvalsForEventType` integer")
   and the shipped `job-status-count` (`{"jobsWithStatus":n}`, no status
   echo) and `outbox-approval-count` (`{"outboxEntries":n}`, no ID echo)
   commands establish a single-key, no-echo convention for later count
   commands in this family, distinct from `event-type-count`'s earlier
   two-key echo. Resolved in favor of the single-key, no-echo shape to match
   the more recent, more conservative convention and the literal AC1 text.
2. **Must every job's `eventId` resolve to a real event, and every
   approval's `jobId` to a real job?** Yes, for the complete `jobs` and
   `approvals` arrays, not only for chains reachable from an approval.
   `approval-link.js` never validates that a job's `eventId` resolves (it
   only echoes whatever is stored), but that command looks up one approval;
   this command *counts* over the whole collection, so an unvalidated
   dangling reference anywhere would let a corrupted job or approval
   silently contribute nothing (undercounting) or crash the join
   (`event.type` of `undefined`) rather than failing closed. Resolved by
   extending `approval-link`'s exhaustive per-array validation (already
   established for `id`/`eventId`/`jobId` presence and uniqueness) with a
   resolution check, applied globally for consistency with the existing
   global uniqueness checks. S29 and S39 test this for a job/approval with no
   downstream reference, proving the rule is not silently skipped for
   unreferenced records.
3. **Does a job or event need a referencing record?** No. An event with no
   job, or a job with no approval, is ordinary valid state (Relay's own job
   worker does not require every event to already have a job, and not every
   successful job has yet been approved or rejected). Only the two forward
   references (job→event, approval→job) are required to resolve.
4. **Are `job.status`, `approval.status`, `approval.action`, or
   `approval.reason` validated or does status filter the count?** No. The
   ticket description and AC2 ask to count "approvals whose job references an
   event with a supplied exact type," with no status qualifier, and
   `SPEC.md` behaviors 4-5 show every approval status (`pending`, `sent`,
   `rejected`, `blocked_recipient`) is a normal outcome of the same proposed
   action. Resolved by counting every structurally valid approval regardless
   of status, matching `event-type-count.js`'s precedent of validating only
   the fields a command actually uses.
5. **What counts as an exact type match?** Resolved identically to the
   shipped `event-type-count` contract: case-sensitive JavaScript strict
   equality, no trimming, case folding, decoding, prefixing, or
   normalization. Fixture A's `Meeting` case-distinct query and its `call`
   absent-type query make the two common accidental-match bugs (case-folding,
   partial/substring matching) observable.
6. **Is an absent or non-matching event type an error?** No. Resolved from
   the ticket's "zero matches is valid" requirement (AC2 in the ticket seed)
   and from the shipped `event-type-count`/`outbox-approval-count` precedent
   that a valid-state no-match returns a successful zero count, never a
   not-found error.
7. **How are failures classified without leaking input?** Resolved using the
   shipped offline count-command convention shared by `event-type-count.js`
