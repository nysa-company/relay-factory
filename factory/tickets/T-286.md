## Description

Add a zero-dependency, read-only CommonJS command that counts persisted Relay
outbox entries whose approval references a job with a supplied exact status
while Relay is offline.

## Acceptance criteria

1. `node app/tools/outbox-job-status-count.js <state-file> <job-status>` emits
   compact JSON containing exactly one `outboxEntriesForJobStatus` integer.
2. Status matching is exact and case-sensitive. Every outbox entry must
   reference exactly one valid approval and every referenced approval exactly
   one valid job; duplicate job or approval IDs, duplicate outbox references,
   and missing references are rejected before counting, and zero matches is
   valid.
3. Invalid arguments are rejected before file access. Unreadable, malformed,
   or structurally invalid state returns fixed redacted errors.
4. The command is offline, zero-dependency, deterministic, read-only, and
   self-terminating. Tests resolve fixtures from the test file, work from any
   current directory, use a five-second child timeout, and do not assume Git
   history depth.
5. Tests precede implementation. Targeted, full app, and immutability checks
   pass without dependency, server, schema, manifest, or Factory changes.
6. The Test-author suite includes, for each of the frozen state-validation
   rules 1–7, at least one positive (state otherwise valid) case and at least
   one negative (single-rule violation, all other rules held valid) case,
   specifically: a non-object/array/null root; each of `events`/`jobs`/
   `approvals`/`outbox` absent or non-array in turn, plus one valid case
   carrying an extra ignored top-level key; each job field (`id`, `eventId`,
   `status`, `attempts`, `retries`, `attemptsSinceRetry`, `lastError`)
   violated in turn, plus one valid case with an extra ignored job property
   and one case with two jobs sharing an `id`; each approval field (`id`,
   `jobId`, `status`) violated in turn, plus one valid case with an extra
   ignored approval property, one case with two approvals sharing an `id`,
   and one case with an approval `jobId` matching no job; each outbox field
   (`to`, `subject`, `body`, `approvalId`, `sentAt`) violated in turn, plus
   one valid case with an extra ignored outbox property, one case with two
   outbox entries sharing an `approvalId`, and one case with an outbox
   `approvalId` matching no approval; and one valid case whose `events`
   array contains an arbitrarily-shaped element. Every negative case asserts
   the exact `outbox-job-status-count: invalid Relay state` envelope (exit
   `1`, empty stdout); every positive case asserts the exact matching
   `outboxEntriesForJobStatus` count.
7. The Test-author suite invokes the command at least twice against the same
   valid fixture within a single test and, after each invocation, asserts
   via `fs.statSync(<fixture-path>, { bigint: true })` that `mode`, `size`,
   and `mtimeNs` are unchanged from the pre-invocation snapshot, and that the
   fixture's parent directory's entry list is unchanged. A separate case
   supplies a directory path as `<state-file>` and asserts the exact
   `outbox-job-status-count: cannot read state file` envelope (exit `1`,
   empty stdout).

### Command interface

`node app/tools/outbox-job-status-count.js <state-file> <job-status>`

- Exactly 2 positional arguments are required. 0, 1, 3, or more arguments
  produce the usage error below, exit code `2`, before any filesystem access
  (`fs.readFileSync` is never called).
- Usage error, exit `2`, empty stdout:
  `usage: node app/tools/outbox-job-status-count.js <state-file> <job-status>\n`
- Success: exit `0`, empty stderr, stdout is exactly
  `{"outboxEntriesForJobStatus":<N>}\n` (compact JSON, this exact single key,
  `<N>` a non-negative JSON integer, no trailing/extra whitespace beyond the
  final `\n`).
- Read failure (absent path, directory path, permission denied, or any other
  `readFileSync` error), exit `1`, empty stdout:
  `outbox-job-status-count: cannot read state file\n`
- JSON parse failure, exit `1`, empty stdout:
  `outbox-job-status-count: state file is not valid JSON\n`
- Structurally invalid Relay state (see below), exit `1`, empty stdout:
  `outbox-job-status-count: invalid Relay state\n`
- Failure precedence is argument count, file read, JSON parse, complete
  structural validation (rules 1–7 below, in order), then matching. No error
  includes the state path, the supplied job-status literal, an OS error,
  parser text, a job/approval/outbox ID, an event, a stack trace, or a
  second line.
- Read-only: the command never creates, writes, or modifies any filesystem
  path. Repeated invocations against the same fixture leave its bytes and
  `fs.statSync(..., { bigint: true })` `mode`/`size`/`mtimeNs` unchanged, and
  leave the parent directory's entry list unchanged.
- Zero-dependency/offline/deterministic/self-terminating: the file's only
  `require` specifier is `"node:fs"`, its only `node:fs` operation is
  `readFileSync`, and it contains none of the literal substrings `server.js`,
  `fetch(`, `WebSocket`, `node:http`, `node:https`, `node:net`,
  `node:child_process`, `setTimeout`, `setInterval`.

### State validation (`isValidState`)

`state` is valid iff all of:

1. `state` is a non-null, non-array object.
2. `state.events`, `state.jobs`, `state.approvals`, `state.outbox` are each
   an own property and each an array. Other top-level keys (e.g.
   `metadata`) may be present and are ignored — this command's counted
   collection is `outbox`, so it follows `outbox-approval-count.js`'s
   extra-top-level-key convention, not `job-status-count.js`'s exact-key
   convention.
3. Every element of `state.jobs` is a non-null, non-array object with: `id`
   a non-empty string, `eventId` a non-empty string, `status` a string that
   is one of `"pending"`, `"done"`, `"dead"`, `attempts` a non-negative
   integer, `retries` a non-negative integer, `attemptsSinceRetry` a
   non-negative integer, and `lastError` either `null` or a string.
   Additional own job properties are allowed and ignored. No two elements of
   `state.jobs` share the same `id`.
4. Every element of `state.approvals` is a non-null, non-array object with:
   `id` a non-empty string, `jobId` a non-empty string, `status` a string
   that is one of `"pending"`, `"sent"`, `"rejected"`,
   `"blocked_recipient"`. Additional own approval properties are allowed and
   ignored. No two elements of `state.approvals` share the same `id`.
5. Every `state.approvals[i].jobId` equals the `id` of some element of
   `state.jobs` (rules 3–4 guarantee at most one match). Any approval whose
   `jobId` matches no job makes the whole state invalid.
6. Every element of `state.outbox` is a non-null, non-array object with own
   properties `to`, `subject`, `body` present (any type), `approvalId` a
   non-empty string, and `sentAt` a non-empty string. Additional own outbox
   properties are allowed and ignored. No two elements of `state.outbox`
   share the same `approvalId`.
7. Every `state.outbox[i].approvalId` equals the `id` of some element of
   `state.approvals` (rules 4 and 6 guarantee at most one match). Any outbox
   entry whose `approvalId` matches no approval makes the whole state
   invalid.

`state.events` element contents are not otherwise validated beyond rule 2.
Any violation of 1–7 makes the state invalid.

### Count semantics

Rules 3–7 guarantee that every valid outbox entry resolves, via its
`approvalId` and then that approval's `jobId`, to exactly one job.
`outboxEntriesForJobStatus` is the number of `state.outbox` entries whose
resolved job has `status === <job-status>` (the second positional argument),
compared with exact, case-sensitive `===` string equality — no trimming,
case folding, or normalization of either the stored or supplied value. Zero
matches is a successful result (exit `0`), not an error. There is no reverse
requirement that every approval or job be referenced.
