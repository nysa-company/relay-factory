## Spec'd description

`app/tools/event-count.js` is a zero-dependency, offline, read-only command
that reads one persisted Relay state file and writes the total count of
events it contains. Its structural validator currently requires every
event's own `type` property to be a non-empty string
(`app/tools/event-count.js:11-17,33`), so a state holding a persisted
non-string `type` is rejected as `invalid Relay state` before it can be
counted.

`app/server.js:40` writes `type: evt.type || "generic"` when accepting an
event, so any truthy value the operator sent — including a nonzero JSON
number such as `7` or `-0.5` — is persisted unchanged; only a falsy `type`
(`undefined`, `null`, `0`, `""`, `false`) is replaced with the literal string
`"generic"`. `factory/tickets/T-190.md` (Frozen contract version 2, Finding 2
and its close-out) already established this as the product's real behavior
and froze a numeric stored `type` (`7`) as legitimate opaque event data for
the sibling `event-timestamp` command. `event-count` disagrees with that
precedent: it rejects the same state `event-timestamp` accepts.

This ticket makes `event-count`'s structural validator accept a persisted
nonzero JSON-number `type` alongside the existing non-empty-string rule, so a
state containing that legitimate data is counted instead of rejected. No
other rule, output shape, error text, or behavior changes. Sibling tickets
T-268 (`event-type-count`) and T-269 (`event-metadata`) apply the identical
nonzero JSON-number rule to their own commands over the same persisted
`events` collection, for the same reason and citing the same precedent.

### Command-line interface and failure precedence

All of this section is the product's existing, unchanged runtime behavior
(`app/tools/event-count.js:46-77`), frozen here so a rewrite cannot silently
diverge.

- Repository-root invocation is exactly
  `node app/tools/event-count.js <state-file>`.
- Exactly one user-supplied positional argument is accepted. Any other arity
  exits `2`, writes zero stdout bytes, writes exactly the following single
  LF-terminated line to stderr, and performs no filesystem access:

  ```text
  usage: node app/tools/event-count.js <state-file>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  event-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  event-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen count-valid structure (below) exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  event-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, then complete
  structural validation.
- Every error is one fixed line terminated by exactly one LF. No error
  includes the state path, event ID, event type, OS error, parser text,
  input bytes, stack trace, payload, job field, approval field, outbox
  field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture
  matrix; if `readFileSync` throws for either, the frozen read-error result
  applies.

### Count-valid state and successful output

A count-valid state is a parsed non-null, non-array JSON object with own
`events`, `jobs`, `approvals`, and `outbox` properties whose values are
arrays. Additional top-level properties are allowed and ignored.

Every `events` element must be a non-null, non-array object with:

- a non-empty string own property `id`, pairwise distinct across the
  complete array;
- a non-empty string own property `receivedAt`;
- an own property `type` that is **type-valid**.

**Type-valid** (the sole rule this ticket changes): the event's own `type`
value is either a non-empty JavaScript string, or a JSON number not equal to
`0`. No other case is type-valid: a missing `type` property, an empty
string, the number `0`, `true`/`false`, `null`, a plain object, or an array
all fail validation exactly as before. `payload` and all additional event
fields remain opaque. Job, approval, and outbox elements remain wholly
opaque; only the fact that their top-level collections are arrays is
validated.

The command validates the complete event array, including ID uniqueness and
every event's type-valid `type`, before counting. Success exits `0`, writes
zero stderr bytes, and writes exactly one compact JSON object followed by
one LF:

```json
{"events":<state.events.length>}
```

No event ID, type, payload, timestamp, job, approval, outbox, or metadata
field is emitted; the output is the array length only.
