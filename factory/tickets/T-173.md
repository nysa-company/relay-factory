## Description

Add `app/tools/state-summary.js`, a zero-dependency Node 18+ command that reads
one persisted Relay `state.json` without starting the HTTP service and writes a
single deterministic, data-minimized JSON summary. The summary reports the
number of events and outbox entries, plus counts for every persisted job and
approval status. It never emits event payloads, approval actions, rejection
reasons, or outbox records.

This offline view is derived from the four durable collections exposed by
[`SPEC.md` Behavior spec items 2–7](../../SPEC.md#behavior-spec), the job status
outcomes in [`SPEC.md` conformance cases 2–4](../../SPEC.md#test-cases-the-conformance-suite),
and the approval/outbox outcomes in
[`SPEC.md` conformance cases 5–6](../../SPEC.md#test-cases-the-conformance-suite).
The persisted collection and status names are fixed by the current
[`app/server.js` durable-state model](../../app/server.js). The standalone,
dependency-free file boundary follows
[`AGENTS.md` Boundaries](../../AGENTS.md#boundaries), and repository
verification follows [`AGENTS.md` Verification](../../AGENTS.md#verification).

### Command interface and output

- Invocation is exactly
  `node app/tools/state-summary.js <state-file>`.
- Exactly one argument after the script path is accepted. Zero or two or more
  arguments exit `2`, write no stdout, and write exactly
  `usage: node app/tools/state-summary.js <state-file>\n` to stderr.
- The command reads `<state-file>` synchronously as UTF-8, parses it as JSON,
  validates only the summary-relevant Relay structure below, computes the
  result in memory, and exits. It does not import or start `app/server.js`,
  open a listening socket, or write, rename, chmod, or delete any path.
- Success exits `0`, writes no stderr, and writes exactly one compact JSON
  object followed by one LF to stdout. Property order is fixed as `events`,
  `jobs`, `approvals`, `outbox`; job property order is `pending`, `done`,
  `dead`; approval property order is `pending`, `sent`, `rejected`,
  `blocked_recipient`.
- The exact output shape is:
  `{"events":<integer>,"jobs":{"pending":<integer>,"done":<integer>,"dead":<integer>},"approvals":{"pending":<integer>,"sent":<integer>,"rejected":<integer>,"blocked_recipient":<integer>},"outbox":<integer>}`.
  `events` and `outbox` are array lengths. Each job and approval counter is the
  number of records whose case-sensitive `status` equals that counter's key.
  Every counter is present even when zero.
- Only the keys and integer values in that shape are emitted. Input object
  keys, event payloads, job details, approval actions and reasons, and outbox
  contents are not copied to output.

### Input validation and errors

A summary-valid Relay state is a non-null, non-array JSON object with own
properties `events`, `jobs`, `approvals`, and `outbox`, each an array. Every
`jobs` element is a non-null, non-array object with `status` exactly one of
`pending`, `done`, or `dead`. Every `approvals` element is a non-null,
non-array object with `status` exactly one of `pending`, `sent`, `rejected`, or
`blocked_recipient`. Other top-level and record fields are allowed and ignored;
the command does not perform a deeper schema migration or repair.

After argument validation, failures are classified in this order:

1. Any filesystem read failure, including a nonexistent path or a path that is
   not a readable regular file, exits `1`, writes no stdout, and writes exactly
   `state-summary: state file is unreadable\n` to stderr.
2. Readable bytes that `JSON.parse` rejects exit `1`, write no stdout, and
   write exactly `state-summary: state file is not valid JSON\n` to stderr.
3. Parsed JSON that fails the summary-valid structure above exits `1`, writes
   no stdout, and writes exactly
   `state-summary: state file has invalid Relay state\n` to stderr.

Errors never include the input path, an operating-system error, or a stack
trace.

   status, approvals by status, and outbox entries” but does not spell the JSON
   object. Resolved by preserving those collection names and the persisted
   status order in the current
   [`app/server.js` state and health model](../../app/server.js); all buckets,
   including zero buckets, are frozen above.

   command never reads would create a second persisted-schema authority.
   Resolved from the ticket's count-only scope and
   [`SPEC.md` durable-state collections](../../SPEC.md#behavior-spec): validate
   the four arrays and the two status-bearing record types needed to make every
   count exact; allow and ignore unrelated fields.
3. **Unknown statuses.** Silently ignoring one would make collection totals
   incomplete. The current model closes the job and approval enums in
   [`app/server.js`](../../app/server.js), so an unknown status is frozen as
   structurally invalid rather than omitted.

   associated protected status-count reference and contains no static source
   restriction. The pinned readiness checker accepted the ticket seams and
   every new global-shell literal; no `Protected-Test-Conflicts` declaration or
