## Spec'd description

Add one read-only detail route, `GET /api/approvals/:id`, so a caller can read
one stored approval together with the stored job that produced it without
downloading and joining the entire `GET /api/state` document. The route is
additive: it does not change approval creation, approval status, outbox
behavior, persistence, the UI, or any existing endpoint.

Product-doc sources:

- [`SPEC.md` behavior 3](../../SPEC.md#behavior-spec) defines an approval as the
  proposed action produced by a successful job.
- [`SPEC.md` behavior 6-7](../../SPEC.md#behavior-spec) defines durable state
  and the existing JSON state view from which the stored approval and job are
  read.
- [`SPEC.md` conformance cases 5-7](../../SPEC.md#test-cases-the-conformance-suite)
  require the approval gate, allowlist result, and crash-recovered records to
  remain unchanged; this ticket adds a view over those records, not a new
  transition.
- [`factory/rulings.md`](../rulings.md) resolves the detail response envelope
  and permits the four additive detail routes to share `app/server.js`
  ownership while protected publication is serialized and later branches
  refresh from protected `main`.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps Relay
  zero-dependency and Factory controls outside application work, while
  [`AGENTS.md` Verification](../../AGENTS.md#verification) supplies the
  repository-wide test and immutability commands.

### HTTP interface

The route is:

```text
GET /api/approvals/:id
```

`:id` is one non-empty path segment and is matched exactly against the `id`
field of an object in `state.approvals`. The route does not claim or change the
existing `POST /api/approvals/:id/approve` or
`POST /api/approvals/:id/reject` interfaces. Acceptance requests have no body.
Authentication, cookies, CORS, and UI behavior are unchanged.

For a matching approval, find the related stored job whose `id` exactly equals
`approval.jobId` and return:

```json
{"approval":<the complete stored approval object>,"job":<the complete stored related job object>}
```

The response is HTTP `200` with `Content-Type: application/json`. The two
stored objects are returned without projection, renaming, defaulting, or
mutation. The top-level object has exactly the `approval` and `job` keys; it
does not add `ok`, `sandbox`, or any other key.

If no approval has exactly that `id`, return HTTP `404` with
`Content-Type: application/json` and exactly:

```json
{"error":"no such approval"}
```

Both branches are read-only: the observable in-memory records and arrays and
the bytes of `<DATA_DIR>/state.json` remain unchanged. An orphaned approval in
a manually corrupted state file is outside this contract; valid Relay
approvals are produced by successful stored jobs.

## Ambiguity log

- **What is the exact HTTP 200 envelope?** `SPEC.md` defines the records but
  not a detail-route envelope. Resolved by the prior
  [`factory/rulings.md`](../rulings.md) decision:
  `{"approval":<stored approval>,"job":<stored related job>}`.
- **How is the related job selected?** Resolved by
  [`SPEC.md` behavior 3](../../SPEC.md#behavior-spec), the ruling's “stored
  related job,” and Relay's existing record relation: the approval's `jobId`
  equals the job's `id`.
- **Does “exactly” require byte-identical JSON formatting?** Resolved as exact
  parsed shape and values, with no extra keys; JSON whitespace and property
  order are not frozen. The deterministic timestamp and record values above
  make the assertion independent of worker timing.
- **What happens for an approval whose `jobId` has no stored job?** Neither the
  product spec nor the ruling defines corrupt-state behavior. It is excluded
  rather than invented because valid approvals are created only by successful
  jobs; Fixture A covers the specified valid-state interface.
- **Do existing routes or exact-body tests need edits?** No. The one-segment
  GET matcher cannot claim the existing two-segment approve/reject POST paths,
  and the additive route changes no existing response. The current test suite
  has no approval-detail test, so the acceptance file is additive.
- **Which sibling tickets overlap file ownership?** A grep of
  `factory/tickets/` found repeated Ready detail-route tickets declaring
  `app/server.js`, including the approval-detail test path on earlier approval
  tickets. After refreshing remotes, the other leased branches
  `origin/ticket/T-162`, `T-166`, `T-167`, and `T-169` also declare
  `app/server.js`; none declares T-168's
  `app/tests/approval-detail.test.js`. The prior ruling resolves the
  implementation-file overlap: additive route work may proceed concurrently,
  publication is serialized, and each later branch refreshes from protected
  `main` before merge.
- **Is deploy/topology detail required?** No. This is an unauthenticated
  same-process read route on Relay's existing origin. It adds no domain,
  preview-deploy, credential, cookie, or CORS behavior.
- **Can this ticket trigger an external send?** No. Both outcomes are GET-only
  state reads and the outbox is unchanged, so `External: no` remains correct
  and no `external` label is required.
