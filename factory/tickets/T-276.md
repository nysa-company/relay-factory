## Spec'd description

Extend the shipped `app/tools/job-attempts.js` command's structural-validity
check so that a persisted Relay state file is rejected whenever two jobs
carry the same non-empty `eventId`, before any lookup or reporting occurs.
Every other validation rule, the successful output shape, and every existing
failure path are unchanged byte-for-byte.

Product-doc and repository sources:

- `app/server.js`'s `acceptEvent` (`app/server.js:34-51`) creates at most one
  job per accepted event, keyed `"job-" + evt.id`, and acknowledges a
  duplicate event delivery idempotently without creating a second job — so a
  persisted state with two jobs sharing one `eventId` is never produced by
  Relay itself, but (mirroring the precedent set by
  [T-186's duplicate-approval-ID defense](../tickets/T-186.md), which rejects
  a persisted state class that is likewise unreachable through
  `app/server.js`) the offline report must still defend against a corrupted
  or hand-edited state file that violates this invariant.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the persisted
  state file Relay's durable source of truth, and
  [`SPEC.md` conformance case 7](../../SPEC.md#test-cases-the-conformance-suite)
  requires crash recovery to duplicate nothing — an offline report reading
  that same file must not silently tolerate a state that violates the
  one-job-per-event invariant it depends on.
- The shipped [`app/tools/job-attempts.js`](../../app/tools/job-attempts.js)
  and its [acceptance suite](../../app/tests/job-attempts.test.js), frozen by
  [T-191](../tickets/T-191.md), establish the exact CLI, structurally-valid-state
  rules (including existing job-ID uniqueness), successful output shape, fixed
  redacted error lines, and read-only offline execution that this ticket
  extends without altering.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency; [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

No endpoint, HTTP shape, UI selector, global-shell UI text, persisted schema,
server behavior, package, dependency, lockfile, Factory control,
authentication path, deployment topology, or external-send behavior changes.
`state.events` is not made unique by this ticket.

### Structurally valid state and successful output

Unchanged base rules: a structurally valid state is a parsed non-null,
non-array JSON object with exactly four own array properties `events`,
`jobs`, `approvals`, `outbox`. Every `jobs` element must be a non-null,
non-array object with non-empty string `id` and `eventId`, `status` exactly
one of `pending`, `done`, `dead`, non-negative-integer `attempts`, `retries`,
`attemptsSinceRetry`, and `lastError` equal to `null` or a string. Additional
job properties are allowed and ignored. Event, approval, and outbox elements
are opaque; only their top-level collections being arrays is checked. Job IDs
must be pairwise distinct across the array (existing rule, unchanged).

**New rule.** After every job independently satisfies the field rules above,
job `eventId` values must also be pairwise distinct across the complete
array: if any two jobs in `state.jobs` have `eventId` values that are equal
under `===` (case-sensitive, no trimming or normalization), the state is
invalid. Because the field rules already require every job's `eventId` to be
a non-empty string before this comparison runs, the comparison only ever
applies to non-empty string values; the "non-empty" qualifier in the ticket
description names an existing precondition, not a new special case. This
rule imposes no ordering relative to the existing job-ID-uniqueness check —
either may be evaluated first, and both must pass for the state to be valid.
`state.events` element IDs are not compared or made unique by this rule.

The command validates the complete job array — every per-job field rule, job
ID uniqueness, and `eventId` uniqueness — before performing lookup. Success
exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF, with exactly these keys in this order:

```json
{"jobId":<job id>,"attempts":<job attempts>,"attemptsSinceRetry":<job attemptsSinceRetry>}
```

No `eventId`, `status`, `retries`, `lastError`, additional job field, event,
approval, or outbox value is emitted.
