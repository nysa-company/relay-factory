## Spec'd description

Add `app/tools/job-event-status-count.js`, a zero-dependency CommonJS command
that reads one persisted Relay state file while Relay is offline, validates the
complete stored job collection, and counts jobs for which both the stored
`eventId` and stored `status` are strictly equal to operator-supplied filters.
It emits only `{"jobsWithEventAndStatus":<count>}`, allowing an operator to
inspect one event's queue-state cardinality without starting Relay, changing
durable state, or exposing either filter, job identities, counters, errors,
events, approvals, outbox entries, or other stored content.

Product-doc and repository sources:

- [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec) defines event intake as
  idempotent by event ID and behavior 2 defines one durable background job per
  accepted event with `pending`, `done`, and `dead` lifecycle outcomes.
- [`SPEC.md` behaviors 6 and 7](../../SPEC.md#behavior-spec) make the
  atomically persisted state file Relay's durable source and make jobs and
  attempts operator-visible.
- [`SPEC.md` conformance cases 2-4 and 7](../../SPEC.md#test-cases-the-conformance-suite)
  require exactly one job per accepted event, observable retries and
  dead-letter outcomes, and duplicate-free crash recovery.
- The current [`app/server.js` state model](../../app/server.js) establishes
  the four stored collections, complete persisted job shape, exact three-value
  job-status enum, event-link field, and atomic persistence behavior.
- The shipped [`job-count` command](../../app/tools/job-count.js) and its
  [acceptance suite](../../app/tests/job-count.test.js) establish complete job
  validation, unique job IDs, compact count-only output, redacted failures,
  and the read-only offline convention. The shipped
  [`job-status-count` command](../../app/tools/job-status-count.js) and its
  [acceptance suite](../../app/tests/job-status-count.test.js) establish exact
  status matching and all three stored status values.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency, and [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

No endpoint, HTTP shape, UI selector, global page-shell text, persisted schema,
server behavior, package, dependency, lockfile, Factory control,

### Structurally valid state, exact conjunction, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with exactly four own properties: `events`, `jobs`, `approvals`,
and `outbox`, each an array.

Every `jobs` element must be a non-null, non-array object with:

- non-empty string own properties `id` and `eventId`;
- an own `status` property exactly equal to `pending`, `done`, or `dead`;
- own `attempts`, `retries`, and `attemptsSinceRetry` properties that are
  integers greater than or equal to zero; and
- an own `lastError` property equal to `null` or a string, including `""`.

Job IDs must be pairwise distinct across the complete array. Additional job
properties are allowed and ignored. Event, approval, and outbox elements are
wholly opaque; only the fact that their top-level collections are arrays is
validated. A job `eventId` need not resolve to a stored event. No relationship
is imposed among `status`, the three counters, and `lastError` beyond each
field's individual rule.

The command validates the complete job array and job-ID uniqueness before
counting. A job contributes exactly one to the count only when both its stored
`eventId` is strictly equal to the supplied `<event-id>` and its stored
`status` is strictly equal to the supplied `<status>`, using case-sensitive
JavaScript string equality for both comparisons. Neither side is trimmed,
case-folded, decoded, parsed, coerced, or Unicode-normalized. An unknown but
non-empty event ID is a successful query with count zero; there is no event
lookup and no not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"jobsWithEventAndStatus":<nonnegative integer count>}
```

`jobsWithEventAndStatus` is the number of elements in the validated `jobs`
array satisfying both frozen comparisons. Neither supplied filter is echoed.
No stored job ID, `eventId`, status, counter, `lastError`, additional job
field, event, approval, or outbox value is emitted.
