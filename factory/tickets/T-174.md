## Spec'd description

Add a zero-dependency Node command, `app/tools/dead-jobs.js`, that reads one
persisted Relay state file without starting the service and writes a stable,
minimal JSON report of dead jobs. This gives an operator an offline
dead-letter inventory while withholding `lastError`, retry-window state,
events, approvals, and outbox contents. The command is read-only and does not
change retry behavior, the persisted schema, the server, or the UI.

Product-doc sources:

- [`SPEC.md` behavior 2](../../SPEC.md#behavior-spec) defines a permanently
  failing job as dead after three attempts and requires dead-letter work to be
  visible rather than silently dropped.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) defines the on-disk state
  as Relay's durable source of truth; this command reads that artifact without
  participating in service startup or recovery.
- [`SPEC.md` conformance cases 3-4](../../SPEC.md#test-cases-the-conformance-suite)
  establish recorded attempts and the dead status used by the report.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) requires the Relay
  product to remain zero-dependency and keeps Factory controls outside
  application work. [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the repository verification commands used after implementation.

### Command interface

- Invocation: `node app/tools/dead-jobs.js <state-file>`.
- The invocation accepts exactly one user-supplied argument. Zero or more than
  one user-supplied argument is a usage failure: exit `1`, empty stdout, and
  exactly `Usage: node app/tools/dead-jobs.js <state-file>\n` on stderr.
- The command reads `<state-file>` directly and does not import, require, or
  start `app/server.js`. It performs no writes, renames, deletes, permission
  changes, or directory creation.
- A valid invocation exits `0`, has empty stderr, and writes exactly one
  compact JSON array followed by one LF (`\n`) to stdout.
- Include only jobs whose `status` is exactly the lowercase string `dead`.
  Each output element has exactly four keys in this order: `id`, `eventId`,
  `attempts`, `retries`. Values are copied unchanged from the stored job.
- Output elements are ascending by `id` using JavaScript's default string
  ordering, which compares UTF-16 code units. Input array order is not
  preserved.
- A valid state containing no dead jobs writes exactly `[]\n`.
- JSON whitespace and object-key order in the input file are not significant.
  Output bytes, including output object-key order and the final LF, are
  significant.

For this command, a structurally valid state is a parsed, non-null, non-array
JSON object with exactly four top-level properties: `events`, `jobs`,
`approvals`, and `outbox`, each an array. The entries in `events`, `approvals`,
and `outbox` are not validated because this report does not consume them.
Every element of `jobs` must be a non-null, non-array object with:

- non-empty string `id` and `eventId`;
- `status` exactly one of `pending`, `done`, or `dead`;
- integer `attempts`, `retries`, and `attemptsSinceRetry`, each greater than
  or equal to zero; and
- `lastError` equal to `null` or a string.

Any read failure (including a nonexistent path or a path that is a directory),
JSON parse failure, or failure of the structure above is an invalid-state
failure: exit `1`, empty stdout, and exactly
`dead-jobs: invalid Relay state\n` on stderr. Error details from the operating
system or JSON parser are not exposed.

### Version 2 command interface

- Invocation: `node app/tools/dead-jobs.js <state-file>`.
- Exactly one argument after the script path is accepted. Zero or two or more
  arguments are usage failures: exit `1`, empty stdout, and exactly

  start `app/server.js`. It performs no writes, renames, deletes, permission
  changes, or directory creation.
- A valid invocation exits `0`, has empty stderr, and writes exactly one
  compact JSON array followed by one LF (`\n`) to stdout.
- Include only jobs whose `status` is exactly the lowercase string `dead`.
  Each output object has exactly four keys in this order: `id`, `eventId`,
  `attempts`, `retries`. Values are copied unchanged from the stored job.
- Output objects are ascending by `id` using JavaScript default string
  ordering, which compares UTF-16 code units. Input array order is not
  preserved. In particular, `job-Zulu` sorts before `job-alpha`.
- A valid state containing no dead jobs writes exactly `[]\n`.
- Input JSON whitespace and object-key order are insignificant. Output bytes,
  output key order, and the final LF are significant.

For this command, a structurally valid state is a parsed, non-null, non-array
JSON object with exactly four top-level properties named `events`, `jobs`,
`approvals`, and `outbox`, each an array. Entries in `events`, `approvals`,
and `outbox` are not validated because the report does not consume them.
Every `jobs` element must be a non-null, non-array object with:

- non-empty string `id` and `eventId`;
- `status` exactly one of `pending`, `done`, or `dead`;
- integer `attempts`, `retries`, and `attemptsSinceRetry`, each greater than
  or equal to zero; and
- `lastError` equal to `null` or a string.

Any read failure, JSON parse failure, or failure of this structure is an
invalid-state failure: exit `1`, empty stdout, and exactly
`dead-jobs: invalid Relay state\n` on stderr. OS and parser details are not
exposed.
