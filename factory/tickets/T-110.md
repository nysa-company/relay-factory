## Spec'd description

Add one additive, read-only `GET /api/events/:id` detail route to the
zero-dependency Relay API. The route lets an operator or API client retrieve
one durable event together with the job created for it, without downloading
and filtering the complete `GET /api/state` document. It returns stored
records unchanged, has an exact missing-event response, and does not mutate
memory or persisted state.

### HTTP interface

- Method and path: `GET /api/events/:id`, where `:id` is exactly one
  non-empty segment captured from the parsed URL pathname.
- Lookup: select the first stored `state.events` entry whose string `id`
  exactly equals `:id`, then select the first stored `state.jobs` entry whose
  string `eventId` exactly equals the selected event's `id`.
- Existing event: return HTTP `200`, header
  `Content-Type: application/json`, and parsed JSON exactly equal to
  `{"event":<complete stored event>,"job":<complete stored related job>}`.
  Neither stored object is projected, renamed, normalized, defaulted, or
  given an additional field.
- Unknown event: return HTTP `404`, header
  `Content-Type: application/json`, and parsed JSON exactly equal to
  `{"error":"no such event"}`.
- Both outcomes are read-only: they do not mutate an in-memory collection,
  invoke persistence, or change `<DATA_DIR>/state.json`.
- Manually corrupted state containing an event without its related job, or
  multiple jobs for one event, is outside this contract. Relay-created state
  persists an accepted event and exactly one job together, and duplicate
  event intake does not create another job.
- UI selectors and accessible names: none. The route does not change the
  existing `GET /` markup or `ui()` output.
- Authentication, cookies, CORS, cross-origin behavior, credentials, domains,
  and preview-deploy topology are unchanged. Requests use unauthenticated
  same-origin HTTP on the existing Relay server; the acceptance topology is
  loopback HTTP with no credentials.

### Frozen Fixture A

`app/tests/event-detail.test.js` creates a fresh temporary `DATA_DIR` and
writes the following complete parsed JSON value to
`<DATA_DIR>/state.json` before starting the real server:

```json
{
  "events": [
    {
      "id": "event-detail",
      "type": "meeting",
      "payload": {
        "failTimes": 99
      },
      "receivedAt": "2026-08-07T12:00:00.000Z"
    }
  ],
  "jobs": [
    {
      "id": "job-event-detail",
      "eventId": "event-detail",
      "status": "dead",
      "attempts": 3,
      "lastError": "simulated failure on attempt 3",
      "retries": 0,
      "attemptsSinceRetry": 3
    }
  ],
  "approvals": [],
  "outbox": []
}
```

The existing-resource ID is exactly `event-detail`. The unknown ID is the
literal `event-missing`, which is byte-distinct from `event-detail`; it is not
created by casing, normalization, or mutation. Tests compare parsed JSON
values, so object-property order and insignificant serialized whitespace are
not response-interface requirements.

Every asserted event ID, job ID, counter, status, error string, and timestamp
is written literally. Fixture setup generates only an unasserted temporary
directory name; it generates no asserted identifier, sequence, counter, or
timestamp. The dead job is not selected by the pending-only worker, and
`WORKER_MS=60000` further prevents fixture activity during an acceptance
case.

### Fixture lifecycle

Each of the three product acceptance cases owns a distinct loopback port
(`4781`, `4782`, or `4783`) and performs this closed lifecycle:

1. create a fresh temporary directory;
2. write Frozen Fixture A to its `state.json`;
3. start `app/server.js` with that directory as `DATA_DIR`,
   `WORKER_MS=60000`, and `ALLOWLIST=test@example.com`;
4. wait until `GET /health` succeeds before issuing acceptance requests;
5. consume every response body;
6. in `finally`, send `SIGKILL` if the child is running, await its exit, and
   recursively remove the temporary directory.

There is no database and no parent/child table cleanup. No setup state is
shared between cases, so no reset helper, foreign-key cleanup, or cascading
delete edit is required. Ports `4781-4783` are distinct from every fixed port
in the current protected suite.

### Findings

1. Related-job selection is untestable as frozen. The contract's material
   lookup rule is "the first stored `state.jobs` entry whose string `eventId`
   exactly equals the selected event's `id`", but Frozen Fixture A contains
   exactly one event and exactly one job, so AC1's `job.eventId === event.id`
   holds for any implementation, including `job: state.jobs[0]` or
   `job: state.jobs.find(j => j.status === "dead")`, which ignores the
   relationship entirely and returns the wrong job on any real multi-job state.
   AC2 constrains only event lookup. Fixture A is frozen and its complete
   parsed value is fixed by the contract, so the test-author cannot close this
   gap; the sibling receipt route already uses a two-record fixture
   (`app/tests/outbox-detail.test.js`, `appr-other` plus the target) for exactly
   this reason. This is a Planner fix: append a contract version 2 whose
   Fixture A carries at least one additional non-matching event and one
   additional job belonging to that other event, and extend AC1 to assert the
   returned pair is the matching one.
2. SPEC-WARN: AC3 names "one request from criterion 1 and one request from
   criterion 2" without requiring their statuses inside that case, so the
   read-only assertions can pass vacuously against a server where the route
   does not exist and both requests fall through to the generic
   `{"error":"not found"}` 404. Assert `200` for the existing id and `404` with
   the exact `no such event` body inside the AC3 case, as
   `app/tests/job-detail.test.js` does at its AC3.
3. SPEC-WARN: no criterion exercises non-matching path shapes for the frozen
   "exactly one non-empty segment" rule (`/api/events`, `/api/events/`,
