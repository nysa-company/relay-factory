## Spec'd description

Add `app/tools/event-count.js`, a zero-dependency CommonJS command that reads
one persisted Relay state file while Relay is offline, validates the complete
stored event collection, and reports only its total cardinality as
`{"events":<count>}`. This gives operators a deterministic count without
starting Relay, changing durable state, or exposing event IDs, types, payloads,
timestamps, job details, approval details, outbox details, or unrelated
metadata.

Product-doc and repository sources:

- [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec) defines accepted events
  and exact-ID idempotency.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the atomically
  persisted state file Relay's durable source, which this command reads
  without participating in startup or recovery.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) makes events an
  operator-visible collection, while
  [`SPEC.md` conformance cases 1, 2, and 7](../../SPEC.md#test-cases-the-conformance-suite)
  require accepted events to remain visible, duplicate IDs not to duplicate
  work, and persisted work to survive restart.
- The current [`app/server.js` state model](../../app/server.js) establishes
  the four stored collections and persists events with `id`, `type`, `payload`,
  and `receivedAt`.
- The shipped [`state-summary` command](../../app/tools/state-summary.js) and
  its [acceptance suite](../../app/tests/state-summary.test.js) establish the
  one-path, compact-JSON, redacted, read-only offline-summary convention. The
  shipped [`event-type-count` command](../../app/tools/event-type-count.js)
  establishes complete event-record and unique-ID validation before counting.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency, and [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/event-count.js <state-file>`.
- Exactly one user-supplied positional argument is accepted. Any other arity
  exits `2`, writes zero stdout bytes, writes exactly the following single
  LF-terminated line to stderr, and does not read or create a candidate state
  path:

  ```text
  usage: node app/tools/event-count.js <state-file>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  event-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  event-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  event-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, OS error, parser text, input bytes, stack trace, event field,
  job field, approval field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `events` element must be a non-null, non-array object with non-empty
string own properties `id`, `type`, and `receivedAt`. Event IDs must be
pairwise distinct across the complete array. Event `payload` and all
additional event fields are opaque. Job, approval, and outbox elements are
wholly opaque; only the fact that their top-level collections are arrays is
validated.

The command validates the complete event array and ID uniqueness before
counting. Success exits `0`, writes zero stderr bytes, and writes one compact
JSON object followed by exactly one LF. Its only key is:

```json
{"events":<nonnegative integer count>}
```

`events` is exactly the validated `events` array length. No stored event ID,
type, payload, `receivedAt`, additional event field, job, approval, outbox, or
metadata value is emitted.
