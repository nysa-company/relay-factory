## Spec'd description

Add `app/tools/event-payload-value-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while the service is
offline, validates the complete stored event collection, and counts events
whose payload is a JSON object with one exact operator-supplied own key whose
stored value is strictly equal to one operator-supplied string. It reports
only `{"eventsWithPayloadValue":<count>}`, allowing an operator to inspect the
durable collection without starting Relay, changing state, coercing values,
walking nested values, consulting object prototypes, or exposing either
supplied argument or any stored content.

Product-doc and repository sources:

- [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec) defines accepted events
  with `{id, type, payload}` and idempotency by exact event ID.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the atomically
  persisted state file Relay's durable source, which this command reads
  without participating in startup or recovery.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) makes events an
  operator-visible collection, while
  [`SPEC.md` conformance cases 1, 2, and 7](../../SPEC.md#test-cases-the-conformance-suite)

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/event-payload-value-count.js <state-file> <key> <value>`.
- Exactly three user-supplied positional arguments are accepted. The key and
  value may each be the empty string. Any other arity exits `2`, writes zero
  stdout bytes, writes exactly the following single LF-terminated line to
  stderr, and does not read or create a candidate state path:

  ```text
  usage: node app/tools/event-payload-value-count.js <state-file> <key> <value>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  event-payload-value-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  event-payload-value-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  event-payload-value-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied key or value, OS error, parser text, input bytes,
  stack trace, event field, job field, approval field, outbox field, or second
  line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state, exact pair match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `events` element must be a non-null, non-array object with non-empty
string own properties `id`, `type`, and `receivedAt`. Event IDs must be
pairwise distinct across the complete array. Event `payload` and all
additional event fields are structurally opaque: `payload` may be absent or
may hold any JSON value. Job, approval, and outbox elements are wholly opaque;
only the fact that their top-level collections are arrays is validated.

The command validates the complete event array and ID uniqueness before
counting. An event contributes one only when its `payload` value is a non-null,
non-array JSON object, that object has an immediate own property whose key is
exactly the supplied `<key>`, and that property's stored value is a string
strictly equal to the supplied `<value>`. Both comparisons are case-sensitive
and use the supplied strings without trimming, parsing, decoding, case-folding,
Unicode normalization, or other coercion. The command does not traverse nested
values or consult the payload object's prototype. Missing, `null`, array,
string, number, and boolean payloads are valid but contribute zero for every
pair. Object payload properties holding arrays, objects, numbers, booleans, or
null are also valid but cannot equal the supplied string. Empty key and value
strings are valid and match an own empty key whose stored value is the empty
string. No match is a successful query, not an error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"eventsWithPayloadValue":<nonnegative integer count>}
```

The count is the number of events in the validated `events` array that satisfy
the frozen predicate. Neither supplied argument is echoed. No stored event ID,
type, payload key or value, `receivedAt`, additional event field, job,
approval, outbox, or metadata value is emitted.

## Ambiguity log

1. **What payloads can participate?** [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec)
   names `payload` without constraining its JSON value, while the backlog
   requires an exact own-property key. The established q78 event-payload-key
   contract and shipped event tools resolve this to immediate own entries on
   non-null, non-array JSON objects only. Missing, null, primitive, and array
   payloads remain structurally valid opaque event content but do not match;
   Fixture A freezes each representative.
2. **What does “exact string value” exclude?** The backlog bans coercion and
   normalization. The contract therefore requires the stored property itself
   to be a string and compares it with JavaScript strict equality. AC2 freezes
   empty, whitespace-prefixed, and composed-Unicode successes; AC3 freezes
   number/string, boolean/string, null/string, case, whitespace, and composed/
   decomposed mismatches.
3. **Do special, inherited, or nested keys participate?** Exact own-key
   semantics make an owned `constructor` and an owned empty key eligible,
   while inherited `constructor`/`toString`, nested `nestedOnly`, boxed-string
   index `0`, and array index `0` do not. This follows the q78 payload-key
   contract and is frozen in AC2-AC3 rather than left to Builder judgment.
4. **How much state is structurally validated?** The protected
   [`event-metadata` acceptance suite](../../app/tests/event-metadata.test.js)
   and shipped [`event-type-count` command](../../app/tools/event-type-count.js)
   establish complete event validation and unique IDs while sibling
   collection elements and payload values remain opaque. The contract adopts
   that exact event envelope and validates it before counting.
5. **Are additional top-level or event fields allowed?** Existing offline
   event tools accept and ignore them, and Relay's persisted state may evolve.
   Fixtures A and B therefore freeze additional metadata as accepted but never
   emitted.
6. **What are error precedence and privacy boundaries?** The shipped offline
   commands establish arity, read, parse, structure, then projection. The
   backlog explicitly requires fixed redacted errors, so the contract freezes
   three byte-exact error lines, zero stdout on failure, and sentinels spanning
   both supplied arguments, filesystem paths, every event content class,
   sibling collections, and malformed stored bytes.
7. **Could another in-flight ticket own the same implementation surface?**
   All local ownership declarations and remote q79 leased contracts for T-223
   and T-224 were inspected. Their approval/outbox paths are distinct; q78
   T-219 through T-221 paths are also distinct. No conflict requires operator
   resolution.
8. **Do protected tests admit the planned source boundary and visible text?**
   `app/tests/event-metadata.test.js` inspects only its own tool, no protected
   test enumerates the tool directory or snapshots the planned file, and the
   pinned `ticket-readiness.py` returned `READINESS PASS`. Separate checks for
   every frozen shell-visible literal returned `GLOBAL TEXT PASS`, so
   `Protected-Test-Conflicts: none` and the reference-only `Fixture-Seams`

9. **Does deployment, authentication, or sending need a topology decision?**
   No. [`factory/PROJECT.env`](../PROJECT.env) declares `app/tools/` and

   introduces no network or external-send surface. No domain, cookie, CORS,
   credential, preview, auth, or `external` label decision is needed.
10. **Does fixture cleanup require protected setup ownership?** No. Each test
    case owns one fresh temporary directory and synchronously deletes it in
