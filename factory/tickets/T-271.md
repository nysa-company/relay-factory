## Spec'd description

Add one zero-dependency Node 18+ command, `node app/tools/pending-jobs.js
<state-file>`, that reads a persisted Relay state file without starting the
service, validates every stored job, and emits a compact JSON array of only
the jobs whose `status` is `pending`, sorted by `id` in code-point order, each
projected to exactly `id`, `eventId`, `attempts`, and `retries`. This gives an
operator a durable, offline view of outstanding work while withholding
`status`, `attemptsSinceRetry`, `lastError`, event payloads, approval content,
and outbox content.

Product-doc sources:

- [`SPEC.md` behavior 2](../../SPEC.md#behavior-spec) defines durable job
  `attempts`, `retries`, and the three-attempt dead-letter boundary that this
  command projects verbatim for pending jobs.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the complete
  persisted state file Relay's durable source of truth; this command reads
  that artifact without participating in service startup or crash recovery.
- [`SPEC.md` test cases 1 and 3](../../SPEC.md#test-cases-the-conformance-suite)
  establish that an accepted event's job is visible in state `pending` before
  it settles, which is exactly the population this command lists.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/` as the
  zero-dependency conformance product and Factory controls outside application
  work. [`AGENTS.md` Verification](../../AGENTS.md#verification) defines the
  later full-app and immutability checks.

The job shape and status enum come from [`app/server.js`](../../app/server.js)
(`acceptEvent`, `processJob`, `retryJob`): every job is created with
`id = "job-" + eventId`, `status` in `{"pending","done","dead"}`, and
`attempts`/`retries`/`attemptsSinceRetry` as non-negative integers that only
ever increase or reset to `0`. The list-and-project shape, sort order, and
error-message/exit-code envelope come from the two closest existing
diagnostics: [`app/tools/dead-jobs.js`](../../app/tools/dead-jobs.js) (status
filter, four-field projection, code-point sort) and
[`app/tools/job-attempts.js`](../../app/tools/job-attempts.js) /
[`app/tools/job-progress.js`](../../app/tools/job-progress.js) (the
newer four-category `usage` / `unreadable` / `not valid JSON` / `invalid Relay
state` failure envelope with distinct exit codes, and whole-`jobs`-array
validation including `id` uniqueness before any downstream step).

This ticket adds no endpoint, UI, schema, retry rule, server behavior,
package, dependency, lockfile, Factory control, authentication path,
deployment topology, or external-send behavior.

### Command-line interface

- Repository-root invocation: `node app/tools/pending-jobs.js <state-file>`.
- Exactly one positional argument is accepted; it is used verbatim (not
  trimmed, decoded, or normalized) as a filesystem path.
- Any other arity exits `2`, writes empty stdout, reads no state path, and
  writes exactly this single LF-terminated stderr line:

  ```text
  usage: node app/tools/pending-jobs.js <state-file>
  ```

- After arity validation, the command synchronously establishes that
  `<state-file>` is a readable regular file via `fs.statSync` followed by
  `isFile()` (matching `app/tools/job-attempts.js` and
  `app/tools/job-progress.js`), reads it as UTF-8, parses it with
  `JSON.parse`, and validates the complete frozen structure below before
  computing any output.
- Success exits `0`, writes empty stderr, and writes one compact JSON array
  plus exactly one LF to stdout. The array contains every job whose `status`
  is exactly `pending`, sorted ascending by `id` using JavaScript's default
  `<`/`>` string comparison (UTF-16 code-unit / code-point order, matching
  `app/tools/dead-jobs.js`). Each element is an object with exactly these
  keys in this order:

  ```json
  {"id":<stored id>,"eventId":<stored eventId>,"attempts":<stored attempts>,"retries":<stored retries>}
  ```

  Values are copied without transformation. `status`, `attemptsSinceRetry`,
  `lastError`, and any additional job property are never emitted. An empty
  result is exactly `[]`.
- The command computes its result in memory and exits. It does not import,
  require, spawn, or start `app/server.js`; open a socket or listener; issue
  a request; or leave a timer or child process running.

### Valid state and failure protocol

A valid state is a parsed, non-null, non-array JSON object with exactly four
own properties: `events`, `jobs`, `approvals`, and `outbox`, each an array.
Entries in `events`, `approvals`, and `outbox` are opaque because this
command does not consume them. Every element of `jobs` must be a non-null,
non-array object with:

- a non-empty string `id`;
- a non-empty string `eventId`;
- `status` exactly `pending`, `done`, or `dead`;
- integer `attempts`, `retries`, and `attemptsSinceRetry`, each greater than
  or equal to zero; and
- `lastError` equal to `null` or a string.

Job `id` values must be pairwise distinct across the entire `jobs` array, and
job `eventId` values must independently be pairwise distinct across the
entire `jobs` array (not only among pending jobs). Additional job properties
are allowed and ignored. The validator does not impose a relationship among
the three counters. The whole `jobs` array is validated — every element,
both uniqueness rules — before any status filtering occurs; a valid pending
job does not override an invalid sibling (S26).

After arity validation, failures have this exact precedence:

1. A filesystem failure while establishing a readable regular file or
   reading its bytes, including a nonexistent path, directory path, or OS
   read denial, exits `1`, writes empty stdout, and writes exactly
   `pending-jobs: state file is unreadable\n` to stderr.
2. Readable bytes rejected by `JSON.parse` exit `1`, write empty stdout, and
   write exactly `pending-jobs: state file is not valid JSON\n` to stderr.
3. Parsed JSON that fails any frozen structural rule (including either
   uniqueness rule) exits `1`, writes empty stdout, and writes exactly
   `pending-jobs: state file has invalid Relay state\n` to stderr.
4. Filtering, projection, and sorting occur only after whole-state
   validation succeeds.

No error includes an input path, supplied argument, operating-system error,
parser text, stack trace, state content, or a second line. Every displayed
error line ends with exactly one LF. No path is written, renamed, deleted,
chmodded, or created.

The arity tests use fresh empty temporary parents. The two-argument case
supplies two paths that do not exist, both of which remain absent
afterward, proving arity validation precedes file access.
