## Spec'd description

Add `app/tools/approval-status-reason-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while Relay is offline,
validates the complete stored approval collection, and reports how many
approvals have an own `status` exactly equal to a supplied value **and** an
own `reason` whose value is a string with at least one UTF-16 code unit. The
result is exactly `{"approvalsWithStatusAndReason":<count>}`. This gives
operators a deterministic, filtered count without starting Relay, changing
durable state, or exposing reasons, approval IDs, job links, actions,
statuses, proposal timestamps, event details, job details, outbox details, or
unrelated content.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/approval-status-reason-count.js <state-file> <status>`.
- Exactly two user-supplied positional arguments are accepted: the state-file
  path and the status query value. Any other arity (zero, one, three, or
  more) exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not read or create a
  candidate state path:

  ```text
  usage: node app/tools/approval-status-reason-count.js <state-file> <status>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  approval-status-reason-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  approval-status-reason-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  approval-status-reason-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then filtering and counting. The status query value
  never participates in structural validation and is never itself validated,
  restricted, trimmed, or case-folded; any string, including the empty
  string, is an accepted query value.
- Every error is one fixed line terminated by exactly one LF. No error
  includes the state path, OS error, parser text, input bytes, stack trace,
  approval field, rejection reason, action value, event field, job field,
  outbox field, query value, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture
  matrix; if `readFileSync` throws for either, the frozen read-error result
  applies.

### Structurally valid state and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string own properties `id`, `jobId`, and `proposedAt`;
- an own `status` property exactly equal to `pending`, `sent`, `rejected`, or
  `blocked_recipient`;
- an own `action` property that is a non-null, non-array object with own
  `to`, `subject`, and `body` properties; and
- either no own `reason` property, or an own `reason` whose value is `null`
  or a string, including the empty string.

Approval IDs must be pairwise distinct across the complete array. The values
of `action.to`, `action.subject`, and `action.body` are opaque. Additional
action and approval properties are allowed and ignored. Event, job, and
outbox elements are wholly opaque; only the fact that their top-level
collections are arrays is validated. A `jobId` need not resolve to a stored
job. No relationship is imposed among `status`, `action`, `proposedAt`, and
`reason` beyond this contract's own filtering predicate.

The command validates the complete approval array and ID uniqueness before
filtering and counting. An approval contributes exactly one to the count only
when **both**:

- its own `status` is exactly, case-sensitively, byte-for-byte equal to the
  second positional argument (`args[1]`); and
- it has an own `reason`, `typeof approval.reason === "string"`, and
  `approval.reason.length > 0`.

The command does not trim, case-fold, decode, or Unicode-normalize either the
stored `status`, the stored `reason`, or the query value. In particular,
`""`, `null`, and an absent `reason` property do not count, while `" "`
counts; a `status` differing only in case from the query value does not
count.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON
object followed by exactly one LF. Its only key is:

```json
{"approvalsWithStatusAndReason":<nonnegative integer count>}
```

No stored reason, approval ID, `jobId`, action value, status, `proposedAt`,
additional approval field, event, job, outbox, top-level metadata value, or
the query value itself is emitted.

## Ambiguity log

1. **What exactly is a "non-empty string" reason?** Resolved from the
   ticket's selected-field wording and JavaScript persistence model as
   `typeof reason === "string" && reason.length > 0`, with no trimming or
   normalization. Fixture A freezes `""` as non-counting and `" "` as
   countable, matching [T-208's](T-208.md#structurally-valid-state-and-successful-output)
   already-frozen reason predicate.
2. **What does "status exactly matches" mean, and is the query
   case-sensitive?** Resolved from the ticket's "counts... approvals whose
   status exactly matches a supplied value" wording and from the shipped
   [`job-status-count`](../../app/tools/job-status-count.js) convention
   (`job.status === args[1]`, no case-folding). Fixture A freezes a same-data
   `rejected` vs. `REJECTED` query pair proving byte-exact, case-sensitive
   comparison with zero trimming or normalization of either side.
3. **Must the reason property be own, and which no-reason forms are valid?**
   The [`app/server.js` rejection path](../../app/server.js) and protected
   [`reject-reason` suite](../../app/tests/reject-reason.test.js) persist
   exact strings and use `null` for a non-string request value. Existing
   approvals created before rejection have no reason. Resolved by accepting
   absent, `null`, and any string, counting only an own non-empty string,
   and rejecting any present non-null non-string — identical to T-208's
   frozen rule.
4. **Is the status query value restricted to the four-value enum?** The
   query is user-supplied at the CLI and is not itself state; the shipped
   `job-status-count` and `outbox-recipient-count` tools impose no domain
   restriction on their query argument. Resolved by accepting any string,
   including one outside the enum (which then simply matches zero stored
   approvals) or the empty string.
5. **What approval structure is validated before filtering and counting?**
   Resolved from [`app/server.js`](../../app/server.js), the shipped
   [`approval-reason-count` command](../../app/tools/approval-reason-count.js),
   and its acceptance suite: require all four arrays; validate every
   approval's identity, job link, action object and own message keys, exact
   status, proposal timestamp, optional reason domain, and unique ID; leave
   sibling collection elements opaque.
6. **Are action values strings, must timestamps be ISO-8601, or must job
   links resolve?** Existing persisted action values originate from webhook
   payloads and existing offline validators treat them as opaque; proposal
   timestamps and links are validated locally without parsing or relation
   lookup. Resolved by requiring own action keys and non-empty string
   `proposedAt` and `jobId`, but no value typing for action keys, ISO
   parsing, or job lookup.
7. **How are failures classified without leaking input?** Raw OS and parser
   errors can reveal paths or state. Resolved using the shipped
   count-command convention: usage exit `2`, operational exits `1`, fixed
   single-line redacted errors, empty opposite streams, and precedence from
   arity through complete structure to filtering.
8. **Should the output echo the query value, as `event-type-count` does?**
   The ticket's own AC1 fixes the success envelope as "compact JSON
   containing exactly one `approvalsWithStatusAndReason` integer," matching
   the `job-status-count`/`outbox-recipient-count` convention (no echo)
   rather than `event-type-count`'s two-key convention. Resolved by emitting
   only the count key; the query value is never echoed.
9. **How are offline, read-only, and self-terminating claims proved?**

   exact file and directory fingerprints, isolated teardown, and a
   production source boundary admitting only `node:fs` and `readFileSync`.
