## Spec'd description

Add `app/tools/approval-recipient-status-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while Relay is offline,
validates the complete stored approval collection, and counts approvals only
when both the stored `action.to` and stored `status` are exactly equal to the
operator-supplied `<recipient>` and `<status>`. The supplied status must be one
of Relay's four persisted approval statuses and is validated before the state
path is read. The command reports only
`{"approvalsWithRecipientAndStatus":<count>}`, allowing an operator to inspect
the intersection without starting Relay, changing durable state, approving or
rejecting an action, creating an outbox receipt, performing a real send, or
exposing supplied filters, stored actions, approval identities, job links,
reasons, proposal timestamps, events, jobs, outbox records, or unrelated
state.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/approval-recipient-status-count.js <state-file> <recipient> <status>`.
- Exactly three user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not validate a status or read
  or create a candidate state path:

  ```text
  usage: node app/tools/approval-recipient-status-count.js <state-file> <recipient> <status>
  ```

- After arity validation and before any file access, `<status>` must be
  strictly equal to one of `pending`, `sent`, `rejected`, or
  `blocked_recipient`. Any other supplied string exits `2`, writes zero stdout
  bytes, writes exactly the following single LF-terminated line to stderr,
  and does not read or create the candidate state path:

  ```text
  approval-recipient-status-count: unsupported status
  ```

- After status validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  approval-recipient-status-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  approval-recipient-status-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  approval-recipient-status-count: invalid Relay state
  ```

- Failure precedence is argument count, supplied-status domain, file read,
  JSON parse, complete structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error
  includes the state path, supplied recipient, supplied status, OS error,
  parser text, input bytes, stack trace, approval field, action value, reason,
  event field, job field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either after a supported status is supplied,
  the frozen read-error result applies. The directory fixture freezes the
  exact command envelope, not any errno, error class, or operating-system text.

### Structurally valid state, exact intersection, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string own properties `id`, `jobId`, and `proposedAt`;
- an own `status` property exactly equal to `pending`, `sent`, `rejected`, or
  `blocked_recipient`;
- an own `action` property that is a non-null, non-array object with own `to`,
  `subject`, and `body` properties; and
- either no own `reason` property, or an own `reason` whose value is `null` or
  a string, including the empty string.

Approval IDs must be pairwise distinct across the complete array. The values
of `action.to`, `action.subject`, and `action.body` are opaque. Additional
action and approval properties are allowed and ignored. Event, job, and outbox
elements are wholly opaque; only the fact that their top-level collections are
arrays is validated. A `jobId` need not resolve to a stored job. No
relationship is imposed among `status`, `action`, `proposedAt`, and `reason`.

The command validates the complete approval array and ID uniqueness before
counting. An approval contributes one to the count only when both
`approval.action.to === <recipient>` and `approval.status === <status>` using
case-sensitive JavaScript strict equality. The command does not coerce, trim,
case-fold, decode, or Unicode-normalize either filter or stored value. Because
command-line arguments are strings, an opaque non-string stored `action.to`
never matches. An empty recipient is a valid second positional argument. An
unsupported or empty status is the frozen CLI-domain error, not a zero-match
query. A supported pair with no matches is a successful query with count zero;
there is no not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"approvalsWithRecipientAndStatus":<nonnegative integer count>}
```

`approvalsWithRecipientAndStatus` is the number of elements in the validated
`approvals` array whose stored recipient and status both match their supplied
filters exactly. Neither supplied filter is echoed. No stored action value,
approval ID, `jobId`, reason, status, proposal timestamp, additional approval
field, event, job, outbox, or top-level metadata value is emitted.

## Ambiguity log

1. **Does a match require both filters or either filter?** Resolved from the
   ticket title and description as a logical AND: one approval contributes
   only when both strict comparisons succeed. AC3's stored other-recipient
   approval with a mismatched status proves recipient-only matches do not
   count.
2. **What counts as an exact recipient match?** Neither the product spec nor
   [`factory/rulings.md`](../rulings.md) defines recipient normalization.
   Resolved from the ticket's exact-match requirement and the shipped
   [`approval-recipient-count` convention](../../app/tools/approval-recipient-count.js)
   as case-sensitive JavaScript strict equality with no coercion, trimming,
   case folding, decoding, or Unicode normalization. AC2 and AC3 make each
   material distinction observable with direct literals.
3. **Which supplied statuses are supported, and may they be normalized?**
   Resolved from the ticket's explicit domain and [`SPEC.md` behaviors
   3-5](../../SPEC.md#behavior-spec): exactly `pending`, `sent`, `rejected`,
   and `blocked_recipient`, compared without normalization. AC2 exercises all
   four; AC5 freezes case, leading-space, trailing-space, unknown, and empty
   rejections.
4. **What is the unsupported-status failure envelope and precedence?** The
   ticket requires a fixed redacted error before file access but does not name
   bytes or exit code. Resolved consistently with the shipped CLI convention:
   invalid operator input exits `2`, writes only
   `approval-recipient-status-count: unsupported status\n`, and follows arity
   but precedes file access. AC4 and AC5 make both precedence boundaries
   observable.
5. **Is an empty recipient or a supported pair with no match an error?**
   Resolved from the exact three-argument interface and count contract: an
   empty recipient is still supplied, while an empty status is outside the
   domain. Every no-match query with a supported status exits `0` with
   `{"approvalsWithRecipientAndStatus":0}\n`.
6. **Are supplied filters echoed?** The original ticket requires exactly one
   integer property. Resolved by freezing a count-only object whose single key
   is `approvalsWithRecipientAndStatus`; supplied and stored filters are
   forbidden from both streams.

   [`app/server.js`](../../app/server.js), the shipped
