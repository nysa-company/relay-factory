## Spec'd description

Add `app/tools/job-inspect.js`, a zero-dependency Node 18+ command that reads
one persisted Relay state file while the service is offline and selects one job
by exact ID. It emits only the stored job's `id`, `eventId`, `status`,
`attempts`, `retries`, and `attemptsSinceRetry`. This gives an operator a
deterministic lifecycle lookup without starting Relay, changing state, or
exposing `lastError`, event payloads, approval actions, or outbox contents.

Product-doc sources:

- [`SPEC.md` behavior 2](../../SPEC.md#behavior-spec) defines the background
  job lifecycle, three-attempt dead-letter boundary, and visible job attempts.
- [`SPEC.md` behaviors 6-7](../../SPEC.md#behavior-spec) define persisted
  on-disk state and the job collection this command reads offline.
- [`SPEC.md` conformance cases 3-4 and 7](../../SPEC.md#test-cases-the-conformance-suite)
  require attempts to be recorded, permanently failing jobs to remain visible
  as dead, and persisted work to survive restart.
- The current [`app/server.js` durable-state model](../../app/server.js)
  establishes the exact stored job fields, statuses, retry counters, and
  job-to-event `eventId` link.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps the app
  zero-dependency, and [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

The command is a read-only projection over the existing state file. It does
not start the service, process or retry a job, emit an event or approval,
write an outbox record, or change the server, persisted schema, worker,
package manifest, dependencies, UI, or Factory controls.

### Command-line interface and errors

- Repository-root invocation is exactly
  `node app/tools/job-inspect.js <state-file> <job-id>`.
- Exactly two positional arguments are accepted.
- Zero, one, or three positional arguments produce exit code `2`, empty
  stdout, and exactly this single LF-terminated stderr line:

  ```text
  usage: node app/tools/job-inspect.js <state-file> <job-id>
  ```

- The command reads `<state-file>` directly as UTF-8. Any read failure,
  including an absent path, a directory in place of a file, or an OS read
  denial, produces exit code `1`, empty stdout, and exactly:

  ```text
  job-inspect: cannot read state file
  ```

- Bytes rejected by `JSON.parse` produce exit code `1`, empty stdout, and
  exactly:

  ```text
  job-inspect: state file is not valid JSON
  ```

- A parsed value that fails the frozen structural rules produces exit code
  `1`, empty stdout, and exactly:

  ```text
  job-inspect: invalid Relay state
  ```

- A valid state with no job whose stored `id` is strictly equal to the
  supplied `<job-id>` produces exit code `1`, empty stdout, and exactly:

  ```text
  job-inspect: job not found
  ```

- Validation precedence is argument count, read, JSON parse, complete
  structural validation, then job lookup.
- Errors never contain the state path, job ID, OS error, parser text, input
  bytes, stack trace, event content, `lastError`, approval content, outbox
  content, or a second line. Every displayed error is terminated by exactly
  one LF.
- No path is written, renamed, deleted, chmodded, or created.

### Structurally valid state and successful output

For this command, structurally valid state is a non-null, non-array JSON object
with own `events`, `jobs`, `approvals`, and `outbox` properties whose values
are arrays.

Every `jobs` element must be a non-null, non-array object with these own
properties:

- non-empty string `id`;
- non-empty string `eventId`;
- string `status` equal to exactly `pending`, `done`, or `dead`; and
- non-negative integer `attempts`, `retries`, and `attemptsSinceRetry`.

Job IDs must be pairwise distinct. Contents of `events`, `approvals`, and
`outbox`, additional top-level properties, and additional job properties are
opaque to structural validation. In particular, `lastError` may be present
but is never copied to output.

The lookup uses exact, case-sensitive JavaScript string equality and does not
trim, normalize, decode, or case-fold either ID. Success exits `0`, writes
zero stderr bytes, and writes one compact JSON object plus exactly one LF. Its
only keys, in order, are:

```json
{"id":<stored id>,"eventId":<stored eventId>,"status":<stored status>,"attempts":<stored attempts>,"retries":<stored retries>,"attemptsSinceRetry":<stored attemptsSinceRetry>}
```

Numbers are copied without conversion. No endpoint, HTTP shape, route, UI
selector, or global page-shell text is introduced.

## Ambiguity log

1. **Exact lookup and error protocol.** The seed did not specify ID
   normalization, error text, exit codes, or validation precedence. No entry
   in [`factory/rulings.md`](../rulings.md) addresses offline inspection.
   Resolved as strict case-sensitive equality, usage exit `2`, operational
   exits `1`, four path-independent error lines, and the frozen precedence,
   matching the shipped offline-command convention.
2. **Structural-validation depth.** The product has no general state-file
   validator. Resolved narrowly from the
   [`app/server.js` durable-state model](../../app/server.js): validate all
   four collections and every job field needed for selection or output;
   enforce unique job IDs from idempotent one-job-per-event intake; leave
   events, approvals, outbox entries, `lastError`, and additive fields opaque.
3. **Counter and serialization semantics.** The seed named fields but did not
   freeze numeric validity, key order, whitespace, or line ending. Resolved
   from the persisted model as non-negative integer counters, copied numbers,
   compact `JSON.stringify` output, the listed key order, and one LF.
4. **Sensitive-data boundary.** “Operational metadata” did not supply
   fixtures proving excluded data stays private. Fixture A gives event
   payload, selected and unselected `lastError`, approval, outbox, and
   additive metadata unique `-MUST-NOT-LEAK` sentinels; exact streams make
   leakage mechanically observable.
5. **Unreadable input portability.** Permission-denial fixtures are
   unreliable under privileged users. All OS read failures share one frozen
   result; an absent path and a directory path are the portable
   representatives.
6. **Cross-ticket file ownership.** A grep of all Markdown tickets under
   `factory/tickets/` found no other declaration of either T-178-owned path.
   Active and remote leased ticket branches were inspected: T-177 owns the
   distinct event inspector, T-170 through T-172 own completed distinct
   offline-command paths, and T-163 through T-165 own `app/server.js`. No
   implementation-surface conflict exists.
7. **Protected source and global text.** All tracked tests were inspected.
   The declared `app/tests/dead-jobs.test.js` seam constrains only its own test
   and `dead-jobs.js`; no allowlist or snapshot constrains the new file. The
   pinned readiness script accepted every fixed shell-visible literal, so no
   protected-test conflict declaration or seam expansion is required.
8. **Topology, lifecycle, generated values, and external effects.** This is
   an offline local file read with isolated temporary fixtures and no
   database, generated expectation, HTTP route, auth, cookie, CORS, origin,
