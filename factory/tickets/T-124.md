## Spec'd description

Add a read-only `GET /api/approvals/:id` endpoint to the zero-dependency Relay
API. Operators can already see all approvals through `GET /api/state`; this
detail endpoint returns one stored approval together with the job that produced
it, without changing either record or triggering the approval action.

This is the detail-read counterpart to Relay's proposed-action model in
[SPEC.md § Behavior spec](../../SPEC.md#behavior-spec), especially the rule
that a successful job creates a pending approval, and it preserves the
approval gate asserted by
[SPEC.md § Test cases](../../SPEC.md#test-cases-the-conformance-suite):
reading is not approval and cannot add an outbox record. The implementation
remains in the zero-dependency `app/` product and follows
[AGENTS.md § Boundaries](../../AGENTS.md#boundaries); the separate,
test-before-implementation commits and verification commands come from
[AGENTS.md § Workflow](../../AGENTS.md#workflow) and
[AGENTS.md § Verification](../../AGENTS.md#verification).

## Acceptance criteria

1. After the frozen fixture has produced `appr-detail-approval-1`,
   `GET /api/approvals/appr-detail-approval-1` returns HTTP `200`,
   `Content-Type: application/json`, and a JSON object with exactly the two
   top-level keys `approval` and `job` in that order; `approval` is deeply
   equal to the stored approval captured from `GET /api/state`, `job` is
   deeply equal to the stored job captured from `GET /api/state`, and
   `response.job.id === response.approval.jobId`.
2. `GET /api/approvals/appr-missing` returns HTTP `404`,
   `Content-Type: application/json`, and the exact response body
   `{"error":"no such approval"}`.
3. For the frozen fixture, the successful detail GET leaves the complete
   `GET /api/state` JSON deeply equal before and after the request, leaves the
   durable `DATA_DIR/state.json` bytes unchanged, and leaves the number of
   outbox records at `0`.
4. The test-author commit adds only
   `app/tests/approval-detail.test.js` and precedes implementation; Builder
   commits change only the approval-detail GET route in `app/server.js`;
   `app/package.json`, existing tests, and Factory controls remain unchanged,
   and both `npm test --prefix app` and
   `.github/scripts/test-immutability-check.sh` exit `0`.

### Endpoint

`GET /api/approvals/:id`, where `:id` is one non-empty path segment and is
matched exactly against the `id` field of an object in `state.approvals`.
There is no request body, authentication, cookie, query parameter, or UI
surface in this contract.

For an existing approval, return HTTP `200` through the existing JSON response
helper with `Content-Type: application/json` and exactly:

```json
{
  "approval": "<the complete stored state.approvals object with the matching id>",
  "job": "<the complete stored state.jobs object whose id equals approval.jobId>"
}
```

The two top-level keys are exactly `approval` and `job` in that order. Neither
stored object is projected, renamed, supplemented, or stripped: after JSON
parsing, each is deeply equal to its corresponding object from
`GET /api/state`. Relay creates an approval only from a successful stored job,
so a dangling `jobId` is outside the valid durable-state model and this ticket
adds no invented response for that impossible state.

For an `:id` absent from `state.approvals`, return HTTP `404`,
`Content-Type: application/json`, and exactly:

```json
{"error":"no such approval"}
```

The response has no `ok`, `code`, `approval`, or `job` key. The existing
generic `{"error":"not found"}` response is not used for this matched route.

Both branches are read-only: they do not mutate in-memory state, call
`persist()`, write `DATA_DIR/state.json`, change an approval or job, or add an
outbox record. Existing `POST /api/approvals/:id/approve` and
`POST /api/approvals/:id/reject` behavior is unchanged.

### Deterministic fixture

`app/tests/approval-detail.test.js` starts the real `app/server.js` as a child
process on a test-owned free port with a fresh temporary `DATA_DIR`,
`WORKER_MS=20`, and `ALLOWLIST=test@example.com`. It submits:

```json
{
  "id": "detail-approval-1",
  "type": "meeting",
  "payload": {
    "to": "test@example.com",
    "subject": "Approval detail subject",
    "body": "Approval detail body"
  }
}
```

to `POST /webhook/event`, then polls `GET /api/state` until
`appr-detail-approval-1` exists. Immediately before the detail request it
captures these complete stored records:

```json
{
  "approval": {
    "id": "appr-detail-approval-1",
    "jobId": "job-detail-approval-1",
    "action": {
      "to": "test@example.com",
      "subject": "Approval detail subject",
      "body": "Approval detail body"
    },
    "status": "pending",
    "proposedAt": "<the generated ISO-8601 timestamp>"
  },
  "job": {
    "id": "job-detail-approval-1",
    "eventId": "detail-approval-1",
    "status": "done",
    "attempts": 1,
    "lastError": null,
    "retries": 0,
    "attemptsSinceRetry": 1
  }
}
```

The generated `proposedAt` value is asserted by equality with the captured
stored approval rather than by freezing the wall clock. `appr-missing` is the
unknown-ID fixture. The test waits until no job is pending before taking the
before/after state and file snapshots, so worker activity cannot mask a read
mutation.
