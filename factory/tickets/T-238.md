## Spec'd description

Add `app/tools/event-type-timestamp-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while Relay is offline,
validates the complete stored event collection, and counts only events whose
stored `type` and stored `receivedAt` are both exactly equal to two
operator-supplied strings. It emits only the integer count, allowing an
operator to distinguish events that share a type or timestamp without
starting Relay, changing durable state, parsing timestamps, or exposing the
filters, event records, payloads, sibling collections, or metadata.

Product-doc and repository sources:

- [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec) defines accepted events
  with `{id, type, payload}` and exact event-ID idempotency.
- [`SPEC.md` behaviors 6 and 7](../../SPEC.md#behavior-spec) define the
  atomically persisted state file as Relay's durable source and expose the
  event collection to operators; [`SPEC.md` conformance cases 1, 2, and
  7](../../SPEC.md#test-cases-the-conformance-suite) require accepted events
  to remain visible, duplicate IDs not to duplicate work, and persisted work
  to survive restart.
- The current [`app/server.js` state model](../../app/server.js) establishes
  the four stored collections and persists each accepted event with `id`,
  `type`, `payload`, and `receivedAt`.
- The shipped
  [`event-type-count` command](../../app/tools/event-type-count.js) and its
  [acceptance suite](../../app/tests/event-type-count.test.js) establish exact
  event-type matching, complete event validation, redacted failures, and the
  read-only offline count convention. The shipped
  [`event-timestamp` command](../../app/tools/event-timestamp.js) and its
  [acceptance suite](../../app/tests/event-timestamp.test.js) establish that
  `receivedAt` is returned verbatim rather than parsed or normalized.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency, and [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

No endpoint, HTTP shape, UI selector, global-shell UI text, persisted schema,
server behavior, package, dependency, lockfile, Factory control,
authentication path, deployment topology, or external-send behavior changes.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/event-type-timestamp-count.js <state-file> <type> <timestamp>`.
- Exactly three user-supplied positional arguments are required, and `<type>`
  and `<timestamp>` must each have length greater than zero. Any wrong arity
  or empty filter exits `2`, writes zero stdout bytes, writes exactly this
  single LF-terminated line to stderr, and does not read or create the
  candidate state path:

  ```text
  usage: node app/tools/event-type-timestamp-count.js <state-file> <type> <timestamp>
  ```

- After argument validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  event-type-timestamp-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  event-type-timestamp-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  event-type-timestamp-count: invalid Relay state
  ```

- Failure precedence is argument arity, non-empty type, non-empty timestamp,
  file read, JSON parse, complete structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied filters, OS error, parser text, input bytes, stack
  trace, event field, sibling-collection field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state, exact conjunction, and successful output

A structurally valid state is a parsed non-null, non-array JSON object with
own `events`, `jobs`, `approvals`, and `outbox` properties whose values are
arrays. Additional top-level properties are allowed and ignored.

Every `events` element must be a non-null, non-array object with non-empty
string own properties `id`, `type`, and `receivedAt`. Event IDs must be
pairwise distinct across the complete array. Event `payload` and all
additional event fields are opaque. Job, approval, and outbox elements are
wholly opaque; only their top-level collections being arrays is validated.

The command validates the complete event array and ID uniqueness before
counting. An event contributes one only when both `event.type === type` and
`event.receivedAt === timestamp` are true for the two supplied arguments.
Matching uses case-sensitive JavaScript string equality. Neither stored nor
supplied value is trimmed, parsed, case-folded, decoded, coerced,
Unicode-normalized, or timezone-converted. The two predicates must match the
same event. No matches is a successful query with count zero.

Success exits `0`, writes zero stderr bytes, and writes this compact object
followed by exactly one LF, with no other key:

```json
{"eventsWithTypeAndTimestamp":<nonnegative integer count>}
```

The supplied filters are not echoed. No event ID, stored type, `receivedAt`,
payload, additional event field, job, approval, outbox, or metadata value is
emitted.

## Ambiguity log

1. **Do the two predicates apply independently or to the same event?** The
   ticket says events whose type and timestamp both match. Resolved as one
   conjunctive predicate on each event; Fixture A's `email`/`12:00:01.000Z`
   query has each value in the collection but never on the same event.
2. **What does exact timestamp matching mean?** Neither
   [`SPEC.md`](../../SPEC.md) nor [`factory/rulings.md`](../rulings.md) defines
   timestamp parsing for offline queries. Resolved from the ticket's explicit
   no-parsing/no-timezone-conversion rule and the shipped
   [`event-timestamp` behavior](../../app/tools/event-timestamp.js): strict
   string equality. The direct offset literal makes conversion observable.
3. **Are empty filters read errors, zero matches, or argument errors?** The
   original ticket requires both supplied strings to be non-empty and invalid
   arguments to fail before file access. Resolved as the exact usage envelope
   with exit `2`; both empty-filter positions are exercised against an absent
   path.
4. **What is returned on success, and are filters echoed?** The original
   acceptance text requires exactly one `eventsWithTypeAndTimestamp` integer.
   Resolved as a one-key count-only object; all filters are forbidden from
   both streams.
5. **What state structure is validated?** Resolved from `app/server.js`, the
   shipped `event-type-count` validator, and both declared fixture seams:
   require the four arrays; validate every event's non-empty string `id`,
   `type`, and `receivedAt` plus unique IDs; leave payloads, extra event fields,
   and sibling elements opaque.
6. **Must timestamps be ISO-8601?** No. The server-produced values currently
   use timestamps, but the ticket forbids parsing and the shipped timestamp
   command preserves a non-ISO string verbatim. Structurally valid
   `receivedAt` is therefore any non-empty string.
7. **How are failures classified without leaks?** Resolved using the shipped
   offline conventions: usage/empty-filter exit `2`; read, parse, and invalid
   state exit `1`; fixed LF-terminated redacted errors; empty opposite stream;
   and precedence through complete validation before counting.
