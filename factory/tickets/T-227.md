## Spec'd description

Add `app/tools/outbox-recipient-subject-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while Relay is offline,
validates the complete sandbox-outbox collection, and counts receipts for which
both stored `to` and stored `subject` are strictly equal to the two supplied
strings. It reports only
`{"outboxWithRecipientAndSubject":<count>}`, allowing an operator to inspect
the cardinality of one recipient-and-subject pair without starting Relay,
changing durable state, creating a receipt, performing a real send, or exposing
either query, any stored message field, receipt identity, timestamp, sibling
collection value, or unrelated metadata.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/outbox-recipient-subject-count.js <state-file> <recipient>
  <subject>` on one physical command line.
- Exactly three user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated physical line to stderr, and does not read or create a
  candidate state path:

  ```text
  usage: node app/tools/outbox-recipient-subject-count.js <state-file> <recipient> <subject>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  outbox-recipient-subject-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  outbox-recipient-subject-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  outbox-recipient-subject-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, either supplied query, OS error, parser text, input bytes,
  stack trace, outbox field, event field, job field, approval field, or second
  line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.
  The directory fixture freezes the command envelope, not any errno, error
  class, or operating-system text.

### Structurally valid state, conjunction match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `outbox` element must be a non-null, non-array object with:

- own `to`, `subject`, and `body` properties, whose values are opaque;
- a non-empty string own `approvalId` property; and
- a non-empty string own `sentAt` property.

Outbox `approvalId` values must be pairwise distinct across the complete array.
Additional outbox properties are allowed and ignored. Event, job, and approval
elements are wholly opaque; only the fact that their top-level collections are
arrays is validated. An outbox `approvalId` need not resolve to a stored
approval. No relationship is imposed among `to`, `subject`, `body`,
`approvalId`, and `sentAt` beyond each field's individual rule.

The command validates the complete outbox array and approval-ID uniqueness
before counting. A receipt contributes one only when both
`receipt.to === <recipient>` and `receipt.subject === <subject>` using
case-sensitive JavaScript strict equality. Both comparisons apply to the same
receipt; matches from different receipts are never combined. The command does
not coerce, trim, case-fold, decode, parse, or Unicode-normalize either stored
value or supplied string. Because command-line arguments are strings, opaque
non-string stored values never match. Empty strings are accepted as either
query argument. A pair with no match is a successful query with count zero;
there is no not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"outboxWithRecipientAndSubject":<nonnegative integer count>}
```

The value is the number of elements in the validated `outbox` array for which
both comparisons are true. Neither supplied string is echoed. No stored
recipient, subject, body, approval ID, send timestamp, additional outbox field,
event, job, approval, or top-level metadata value is emitted.

## Ambiguity log

1. **Does a match require both fields on the same receipt?** Resolved from the
   ticket phrase "entries whose recipient and subject exactly match" as a
   per-receipt conjunction. The crossed-existing-fields fixture makes this
   observable: each field exists, but on different receipts, so the result is
   zero.
2. **What does exact matching mean for each field?** Neither `SPEC.md` nor
   [`factory/rulings.md`](../rulings.md) defines normalization. Resolved from
   the ticket's exact-match/no-coercion requirement and the shipped strict
   field-matching convention as JavaScript strict equality with no trimming,
   case folding, decoding, parsing, or Unicode normalization. Direct literals
   make every distinction mechanically observable.
3. **Is a pair with no matching receipt an error?** Resolved from the original
   ticket acceptance text: a valid zero-match query writes exactly
   `{"outboxWithRecipientAndSubject":0}\n`; there is no lookup error.
4. **Are supplied or stored values echoed?** The original ticket requires
   exactly one output integer. Resolved as a count-only object with the sole
   `outboxWithRecipientAndSubject` key and a complete sensitive-token ban on
   both streams.
5. **What state structure is required before counting?** Resolved from the
   four collections and receipt fields in
   [`app/server.js`](../../app/server.js), the shipped
   [`outbox-count` contract](T-206.md#structurally-valid-state-and-successful-output),
   and the declared
   [`outbox-detail` fixture seam](../../app/tests/outbox-detail.test.js): require
   all four arrays, validate every receipt's five persisted properties and
   unique `approvalId`, allow extra properties, and leave sibling collection
   elements opaque.
6. **Must message fields be strings, timestamps parse as ISO-8601, or receipt
   IDs resolve to approvals?** The server stores action values originating in
   webhook payloads, while the shipped validator treats `to`, `subject`, and
   `body` as opaque. Resolved by preserving that rule: non-string values are
   structurally valid but cannot strictly equal CLI strings; `approvalId` and
   `sentAt` are non-empty strings; no cross-record or timestamp-parse rule is
   invented.
7. **Why require unique outbox `approvalId` values?** The
   [outbox-detail contract](T-169.md#http-interface) records at most one receipt
   per approval, and
   [`SPEC.md` conformance case 7](../../SPEC.md#test-cases-the-conformance-suite)
   requires recovery without duplication. S19 proves duplicates are rejected
   before counting.
8. **How are failures classified without leaking input?** Resolved from the
   shipped offline-count convention: usage exit `2`, operational exits `1`,
   fixed one-line redacted errors, empty opposite streams, and precedence from
   arity through complete structural validation.
9. **How are offline, read-only, deterministic, and self-terminating claims
   proved?** Resolved with synchronous child invocations under a `5_000` ms
   timeout, exact file and directory fingerprints, repeated success, isolated
   teardown, and a source boundary admitting only `node:fs`/`readFileSync`.
10. **Are derived fixtures or generated expectations involved?** Invalid and
    variant inputs are frozen direct literals, every serialization is pairwise
    compared, and all expected values come from literal setup. No initializer,
    reset, sequence, counter, generated identifier, or clock participates.
11. **Does cleanup have hidden relational dependencies?** No service or
    database is started. Each case owns one temporary directory removed after
    its child exits, so there are no parent rows, sibling tables, foreign keys,
    cascades, resets, or teardown ordering.
12. **Do sibling or concurrently leased tickets overlap ownership?** A grep of
    every local ticket and inspection of every remote `origin/ticket/T-*`
    record found no other owner of either T-227 path. T-225 and T-226 use
    distinct event and approval filenames.
13. **Do protected tests reject the new module specifier or source?** Direct
    inspection of the protected outbox seam, existing count suites, Factory
    contract test, and immutability script found only path-specific checks and
    no enumeration or snapshot of the new Builder path. No protected-test
    conflict declaration is needed.
14. **Does protected global text collide?** The pinned global-literal checker
    returned `GLOBAL TEXT PASS` for every non-empty shell-visible literal
    frozen by this contract. No UI or accessible name is added.
15. **Are deployment, authentication, or external-send details applicable?**
    No. The complete topology is one local process reading one local file and
    writing stdout/stderr; there is no network, UI, credential, preview, or
    send path, so no `external` label is required.
16. **Does an existing operator ruling change the contract?**
    [`factory/rulings.md`](../rulings.md) was checked before freeze. Its
    detail-route ruling is consistent with the cited receipt shape, and its
    T-178 verification ruling confirms the targeted test, full app suite, and
    immutability as the post-implementation set. No new decision is required.
