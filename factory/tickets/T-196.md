## Spec'd description

Add `app/tools/event-job-count.js`, a zero-dependency Node 18+ command that
reads one persisted Relay state file while the service is offline, selects one
event by case-sensitive exact ID, and counts every stored job whose `eventId`
is strictly equal to that selected event's stored `id`. It emits only the
selected `eventId` and the integer `jobs` count. This gives an operator a
deterministic relationship summary, including an exact zero result, without
starting Relay, changing durable state, or exposing event payloads, job
contents, approval actions, outbox content, or unrelated state.

Product-doc sources:

- [`SPEC.md` behaviors 1 and 2](../../SPEC.md#behavior-spec) define exact event
  IDs and the persisted event-to-job relationship.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the atomically
  persisted state file Relay's durable state, which this command reads without
  participating in startup or recovery.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) makes events and jobs
  operator-visible collections, while
  [`SPEC.md` conformance cases 1, 2, and 7](../../SPEC.md#test-cases-the-conformance-suite)

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/event-job-count.js <state-file> <event-id>`.
- Exactly two user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and performs no state-file read:

  ```text
  usage: node app/tools/event-job-count.js <state-file> <event-id>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  event-job-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  event-job-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen count-valid structure exits `1`, writes
  zero stdout bytes, and writes exactly:

  ```text
  event-job-count: invalid Relay state
  ```

- A count-valid state with no event whose stored `id` is strictly equal to
  `<event-id>` exits `1`, writes zero stdout bytes, and writes exactly:

  ```text
  event-job-count: event not found
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, exact event lookup, then job counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, event ID, OS error, parser text, input bytes, stack trace,
  payload, job field, approval field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Count-valid state, exact lookup, and successful output

A count-valid state is a parsed non-null, non-array JSON object with own
`events`, `jobs`, `approvals`, and `outbox` properties whose values are arrays.
Additional top-level properties are allowed and ignored.

Every `events` element must be a non-null, non-array object with a non-empty
string own property `id`. Event IDs must be pairwise distinct across the
complete array. Event `type`, `payload`, `receivedAt`, and all additional event
fields are opaque.

Every `jobs` element must be a non-null, non-array object with a non-empty
string own property `eventId`. Job `id`, `status`, attempts, errors, retry
fields, and all additional job fields are opaque. Job `eventId` values need
not be unique and need not reference a stored event; these rules allow the
command to count every exact match and to inspect an event with zero matches
without imposing a new persisted-schema invariant. Approval and outbox
elements are wholly opaque; only the fact that their top-level collections are
arrays is validated.

The command validates the complete event and job arrays before lookup or
counting. Event lookup and job matching use exact, case-sensitive JavaScript
string equality. The command does not trim, case-fold, decode, or normalize
either stored or requested IDs.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only keys, in this order, are:

```json
{"eventId":<selected stored id>,"jobs":<non-negative integer match count>}
```

`eventId` copies the selected event's stored `id`. `jobs` is the number of
elements in the complete `jobs` array whose stored `eventId` is strictly equal
to that selected stored ID. No event field other than `id`, job content,
approval content, outbox content, metadata, or unrelated state is emitted.

## Ambiguity log

1. **What does “jobs link to an event” mean?** Resolved from
   [`SPEC.md` behavior 2](../../SPEC.md#behavior-spec) and the current
   [`app/server.js`](../../app/server.js): the persisted relationship is the
   job's own `eventId`, copied from the accepted event's `id`. Counting uses
   strict equality against the selected stored event ID.
2. **Can zero or more than one matching job be reported?** The ticket
   explicitly freezes zero as valid and asks for a count rather than a Boolean.
   Fixture A therefore freezes the observable outcomes `3`, `1`, and `0`;
   this does not change the persisted schema or claim that normal intake
   creates multiple jobs.
3. **How exact is event selection and matching?** Resolved from
   [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec), the current server's
   strict-ID lookup, and the shipped exact-ID offline-command convention as
   case-sensitive JavaScript string equality. Direct literal `Event-alpha`
   makes case folding observable, and duplicate stored event IDs are invalid
   before lookup.
4. **What structure must a count-only reader validate?** The product has no
   general-purpose state-file validator. Resolved narrowly from the four
   current collections in `app/server.js`: require all four arrays, validate
   every event's consumed `id` plus uniqueness, and validate every job's
   consumed `eventId`. Unconsumed fields and collection elements remain opaque.
   Fixture A proves event/job field opacity; Fixture B proves dangling job
   links and approval/outbox element opacity.
5. **Should dangling job links invalidate the file?** No product doc requires
   this read-only diagnostic to add referential-integrity enforcement, and the
   ticket asks only for links to the selected stored event. Resolved by
   freezing dangling links as ignored nonmatches; Fixture B distinguishes the
   resulting not-found error from a structural error.
6. **How are failures classified without leaking input?** Raw OS and parser
   errors can reveal paths or content. Resolved using the shipped offline-tool
   convention: usage exit `2`, operational exits `1`, fixed single-line
   redacted errors, empty opposite streams, and precedence from arity through
   lookup.
7. **How are read-only, offline, and self-terminating claims proved?** Resolved
   with synchronous child invocations under a `5_000` ms timeout, exact file
   and directory fingerprints, repeated success, isolated teardown, and a
   production source boundary admitting only `node:fs` and `readFileSync`.
8. **Are derived fixtures or generated counts involved?** No invalid fixture
   is derived at runtime. The case-distinct lookup is a direct literal, all
   serialized fixtures are pairwise checked, and all three expected counts
   are evaluated directly from Fixture A's literal jobs before invocation.
9. **Does fixture cleanup have hidden dependencies?** No database or service
   is started. Each test owns one temporary directory removed after its child
   exits, so there are no parent rows, sibling tables, foreign keys, or reset
   ordering.
10. **Do sibling or concurrently leased tickets overlap ownership?** A grep of
