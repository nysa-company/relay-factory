## Spec'd description

Add `app/tools/job-error-count.js`, a zero-dependency CommonJS command that
reads one persisted Relay state file while Relay is offline, validates the
complete stored job collection, and reports how many jobs have an own
`lastError` value that is a string of at least one UTF-16 code unit as
`{"jobsWithErrors":<count>}`. This gives operators a deterministic indication
of recorded job failures without starting Relay, changing durable state, or
exposing job IDs, event links, statuses, counters, error text, event payloads,
approval details, outbox details, or unrelated stored content.

Product-doc and repository sources:

- [`SPEC.md` behavior 2](../../SPEC.md#behavior-spec) defines retrying jobs,
  recorded attempts, and the visible dead-letter outcome.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the atomically
  persisted state file Relay's durable source, which this command reads
  without participating in startup or recovery.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) makes jobs and their
  attempts operator-visible, while
  [`SPEC.md` conformance cases 3, 4, and 7](../../SPEC.md#test-cases-the-conformance-suite)
  require transient failures, permanent failures, and recovered work to

- The current [`app/server.js` state model](../../app/server.js) establishes
  the four stored collections, the complete persisted job shape, and the
  lifecycle in which a failed pending job carries a string `lastError`, a dead
  job retains one, and a successful job carries `null`.
- The shipped [`job-count` command](../../app/tools/job-count.js) and its

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/job-error-count.js <state-file>`.
- Exactly one user-supplied positional argument is accepted. Any other arity
  exits `2`, writes zero stdout bytes, writes exactly the following single
  LF-terminated line to stderr, and does not read or create a candidate state
  path:

  ```text
  usage: node app/tools/job-error-count.js <state-file>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  job-error-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  job-error-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  job-error-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, OS error, parser text, input bytes, stack trace, job field,
  event field, approval field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with exactly four own properties: `events`, `jobs`, `approvals`,
and `outbox`, each an array.

Every `jobs` element must be a non-null, non-array object with:

- non-empty string own properties `id` and `eventId`;
- an own `status` property exactly equal to `pending`, `done`, or `dead`;
- own `attempts`, `retries`, and `attemptsSinceRetry` properties that are
  integers greater than or equal to zero; and
- an own `lastError` property equal to `null` or a string.

Job IDs must be pairwise distinct across the complete array. Additional job
properties are allowed and ignored. Event, approval, and outbox elements are
wholly opaque; only the fact that their top-level collections are arrays is
validated. Event IDs need not match job `eventId` values. No relationship is
imposed among `status`, the three counters, and `lastError` beyond each field's
individual rule.

The command validates the complete job array and ID uniqueness before
counting. A job contributes exactly one to the count if and only if its
validated `lastError` is a string with `.length > 0`; `null` and the empty
string contribute zero. Whitespace-only strings are non-empty and contribute
one; no trimming, normalization, parsing, or status filter is applied.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"jobsWithErrors":<nonnegative integer count>}
```

No stored job ID, `eventId`, status, counter, error, additional job field,
event, approval, or outbox value is emitted.

## Ambiguity log

1. **What does "recorded errors" count?** Resolved from the ticket's
   non-empty-string requirement and the current
   [`app/server.js` job lifecycle](../../app/server.js): count each fully
   validated job whose own `lastError` is a string with `.length > 0`.
   `null` and `""` count zero. No trimming, normalization, status filtering,
   deduplication by error text, or interpretation of the error is performed.
2. **Can a pending job with an error count, and can a dead job with an empty
   error remain valid?** `app/server.js` persists a string error while a failed
   job remains pending between attempts, and shipped job validators impose no
   relationship among status, counters, and `lastError`. Resolved by keeping
   those fields independent. Fixture A makes the pending error count and
   leaves a dead job with `""` valid but uncounted.
3. **What state structure is required before counting?** The product has no
   single general-purpose state validator. Resolved from the four collections
   and job fields in [`app/server.js`](../../app/server.js), the shipped
   [`job-count` validator](../../app/tools/job-count.js), and the declared
   [`job-detail` seam](../../app/tests/job-detail.test.js): require exactly
   four array collections, validate every job's complete persisted shape and
   unique ID, allow additional job fields, and leave sibling collection
   elements opaque.
