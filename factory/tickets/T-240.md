## Spec'd description

Add `app/tools/approval-status-recipient-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while Relay is offline,
validates a required approval-status filter and non-empty recipient before any
file access, validates the complete stored approval collection, and counts
approvals for which both the stored `status` and stored `action.to` strictly
equal the supplied strings. It reports only
`{"approvalsWithStatusAndRecipient":<count>}`. This gives operators a narrow,
deterministic intersection count without starting Relay, changing durable
state, approving or rejecting an action, creating an outbox receipt, performing
a real send, or exposing either supplied filter, approval identities, actions,
reasons, proposal timestamps, events, jobs, outbox records, or unrelated state.

### Command-line interface, filter validation, and failure precedence

- Repository-root invocation is exactly
  `node app/tools/approval-status-recipient-count.js <state-file> <status>
  <recipient>`.
- Exactly three user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following one
  LF-terminated line to stderr, and performs no filter validation or candidate
  state-path access:

  ```text
  usage: node app/tools/approval-status-recipient-count.js <state-file> <status> <recipient>
  ```

- After arity validation, `<status>` must be exactly one of `pending`, `sent`,
  `rejected`, or `blocked_recipient`. Any other string, including `""`,
  `PENDING`, `done`, or a whitespace-padded value, exits `2`, writes zero
  stdout bytes, writes exactly the following one LF-terminated line to stderr,
  and does not read or create the candidate state path:

  ```text
  approval-status-recipient-count: invalid status
  ```

- After status validation, `<recipient>` must contain at least one UTF-16 code
  unit. The exact empty string exits `2`, writes zero stdout bytes, writes
  exactly the following one LF-terminated line to stderr, and does not read or
  create the candidate state path:

  ```text
  approval-status-recipient-count: recipient must be non-empty
  ```

  A whitespace-only recipient is non-empty and therefore valid; it is not
  trimmed.
- After all argument validation, the command synchronously reads
  `<state-file>` directly as UTF-8. Any `readFileSync` failure, including an
  absent path, a directory in place of a regular file, or an OS read denial,
  exits `1`, writes zero stdout bytes, and writes exactly:

  ```text
  approval-status-recipient-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  approval-status-recipient-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  approval-status-recipient-count: invalid Relay state
  ```

- Failure precedence is argument count, status validation, recipient
  validation, file read, JSON parse, complete structural validation, then
  counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied status, supplied recipient, OS error, parser text,
  input bytes, stack trace, approval field, action value, reason, event field,
  job field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state, exact intersection, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string own properties `id`, `jobId`, and `proposedAt`;
- an own `status` property exactly equal to `pending`, `sent`, `rejected`, or
  `blocked_recipient`;
- an own `action` property that is a non-null, non-array object with own `to`,
  `subject`, and `body` properties; and
- either no own `reason` property, or an own `reason` whose value is `null` or
  a string, including the empty string.

Approval IDs must be pairwise distinct across the complete array. The values
of `action.to`, `action.subject`, and `action.body` are opaque. Additional
action and approval properties are allowed and ignored. Event, job, and outbox
elements are wholly opaque; only the fact that their top-level collections are
arrays is validated. A `jobId` need not resolve to a stored job. No
relationship is imposed among `status`, `action`, `proposedAt`, and `reason`.

The command validates the complete approval array and approval-ID uniqueness
before counting. An approval contributes one exactly when both
`approval.status === <status>` and `approval.action.to === <recipient>` using
case-sensitive JavaScript strict equality. Neither stored nor supplied values
are coerced, trimmed, case-folded, decoded, or Unicode-normalized. Because
command-line arguments are strings, an opaque non-string stored `action.to`
never matches. A valid filter pair with no matching approval is a successful
query with count zero; there is no not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"approvalsWithStatusAndRecipient":<nonnegative integer count>}
```

The value is the number of approvals in the validated `approvals` array that
match both filters. Neither supplied filter is echoed. No stored action value,
approval ID, `jobId`, reason, status, proposal timestamp, additional approval
field, event, job, outbox, or top-level metadata value is emitted.

## Ambiguity log

1. **What does matching both filters mean?** Resolved from the ticket's exact
   status-and-recipient requirement and the shipped strict field-match
   convention as one approval satisfying both case-sensitive JavaScript strict
   equalities. AC3 includes rows that match either individual filter but not
   both, so an OR implementation fails mechanically.
2. **Which status arguments are accepted, and what is their precedence?**
   Resolved from [`SPEC.md` behaviors 3-5](../../SPEC.md#behavior-spec), the
   server status domain, and the ticket's explicit filter constraint: exactly
   `pending`, `sent`, `rejected`, or `blocked_recipient`. Arity is checked
   first, then status, then recipient, before file access. Empty, uppercase,
   unknown, and whitespace-padded status values are invalid.
3. **What is a non-empty recipient?** Resolved as a command-line string with at
   least one UTF-16 code unit. `""` is invalid, while a whitespace-only string
   is valid and untrimmed. This follows the ticket's non-empty requirement
   without inventing email parsing that the product docs do not specify.
4. **Are argument-validation errors usage failures or state failures?** The
   product docs do not assign CLI exit codes. Resolved from the shipped CLI
   convention: wrong arity and invalid operator-supplied filters exit `2`;
   file, parse, and state failures exit `1`; each gets a fixed redacted line.
5. **Are the supplied status or recipient echoed?** The original ticket
   requires exactly one `approvalsWithStatusAndRecipient` integer. Resolved by
   freezing a count-only object whose single key is that property; supplied
   and stored filters are forbidden from both streams.
6. **What approval structure is validated before counting?** Resolved from
   [`app/server.js`](../../app/server.js), the shipped
   [`approval-count`](../../app/tools/approval-count.js),
   [`pending-approvals`](../../app/tools/pending-approvals.js), and
   [`approval-recipient-count`](../../app/tools/approval-recipient-count.js)
   commands: require all four arrays; validate every approval's identity, job
   link, action object and own message keys, exact status, proposal timestamp,
   optional reason domain, and unique ID; leave sibling collection elements
   opaque.
7. **Must recipient, subject, and body be strings; timestamps parse as ISO-8601;
   or job links resolve?** Persisted action values originate in webhook
   payloads, and shipped validators treat them as opaque. Resolved by requiring
   own action keys, non-empty string `proposedAt` and `jobId`, and no
   action-value typing, ISO parse, or relationship lookup. Numeric `action.to`,
   `null` subject, `false` body, unresolvable links, and
   `not-an-iso-instant` make those choices observable.
8. **Which reason forms are valid, and must reason agree with status?** Resolved
   from the server rejection path and shipped recipient-count validator:
   reason may be absent, `null`, or any string, including `""` and `" "`; no
   status-to-reason relationship is imposed.
9. **Why reject duplicate approval IDs?** The stored ID is the durable approval
   identity used by approval and rejection operations, and
   [`SPEC.md` conformance case 7](../../SPEC.md#test-cases-the-conformance-suite)
   requires recovery without duplication. Resolved consistently with
   `approval-count`; S29 makes uniqueness-before-counting observable.
10. **How are failures classified without leaking input?** Raw OS and parser
    errors can expose paths or state. Resolved using the shipped offline
    command convention: fixed single-line redacted errors, empty opposite
    streams, and precedence from arity through complete structure.
11. **How are offline, read-only, and self-terminating claims proved?** Resolved

    production source boundary admitting only `node:fs` and `readFileSync`.
