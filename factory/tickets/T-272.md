## Description

Relay provides offline lists for pending and blocked approvals, but not for the
approvals already sent. Add the symmetric sent-approval diagnostic while
keeping message content and recipients private.

## Acceptance criteria

1. `node app/tools/sent-approvals.js <state-file>` exits `0`, writes one compact
   JSON array line, and writes zero stderr bytes for valid state.
2. The array contains only approvals with status `sent`, sorted by approval ID
   in code-point order. Each entry has exactly `id`, `jobId`, and `proposedAt`
   in that order. Empty or all-non-sent approvals emit `[]`.
3. Approval records require a non-empty approval ID unique across the
   `approvals` array, a non-empty job ID (job IDs need not be unique across
   records), a non-empty proposed timestamp, and one of the four supported
   statuses. Invalid records fail before filtering.
4. Usage, unreadable-file, invalid-JSON, and invalid-state failures use fixed
   redacted one-line stderr messages, the established exit codes, and zero
   stdout bytes. No recipients, actions, reasons, state contents, or paths
   leak.
5. Repeated invocation is byte-for-byte deterministic. The command is offline,
   zero-dependency, read-only, and self-terminating, and changes no input bytes,
   metadata, or sibling paths.
6. Tests precede implementation; the targeted test, full app suite, and
   immutability check pass without other product or Factory changes.

### Interface

`node app/tools/sent-approvals.js <state-file>`

Byte-identical structure, messages, and exit codes to the sibling tools
`app/tools/pending-approvals.js` and `app/tools/blocked-approvals.js`, with
the filter status changed to `sent` and one added cross-record validation
rule (approval-ID uniqueness). Tool name in messages is `sent-approvals`.

**Exit codes**

| Condition | stdout | stderr | exit |
|---|---|---|---|
| valid state | one compact JSON array line + `\n` | (none) | `0` |
| arg count `!== 1` | (none) | `usage: node app/tools/sent-approvals.js <state-file>\n` | `2` |
| file unreadable (missing, directory, permission) | (none) | `sent-approvals: cannot read state file\n` | `1` |
| file content not valid JSON | (none) | `sent-approvals: state file is not valid JSON\n` | `1` |
| JSON parses but fails state validation | (none) | `sent-approvals: invalid Relay state\n` | `1` |

These four stderr strings are exact and fixed (no interpolation of paths,
IDs, or state contents).

### State validation (`isValidState`)

Top-level `state` must be a non-null, non-array object with own array
properties `events`, `jobs`, `approvals`, `outbox` (presence and
`Array.isArray`, extra top-level keys allowed — matching
`pending-approvals.js`/`blocked-approvals.js`, not the stricter
`Object.keys(state).length === COLLECTIONS.length` check used by
`dead-jobs.js`/`job-status-count.js`).

Every entry of `state.approvals` must satisfy, in this order, else the whole
state is invalid:

1. non-null, non-array object;
2. `id`: non-empty string, and not equal to any earlier approval's `id`
   (first-seen-wins `Set` check — duplicate approval IDs invalidate the
   state);
3. `jobId`: non-empty string (no cross-record uniqueness check);
4. `proposedAt`: non-empty string;
5. `status`: one of exactly `"pending"`, `"sent"`, `"rejected"`,
   `"blocked_recipient"`.

Validation runs over every record before any filtering; one invalid record
invalidates the entire state (AC3).

### Output projection

```
state.approvals
  .filter(approval => approval.status === "sent")
  .map(({ id, jobId, proposedAt }) => ({ id, jobId, proposedAt }))
  .sort((a, b) => a.id < b.id ? -1 : a.id > b.id ? 1 : 0)
```

Serialized with `JSON.stringify` (compact, no whitespace) plus a trailing
`\n`. Key order per entry is exactly `id`, `jobId`, `proposedAt`. Empty or
all-non-`sent` input emits `[]\n`.

### AC2 (repaired) — ordering definition (answers finding 1)

Original wording ("sorted by approval ID in code-point order") is ambiguous
between true Unicode code-point order and JavaScript's default relational
string comparison, which compares UTF-16 code units. The frozen projection
uses, and this contract requires, the **UTF-16 code-unit comparator**
`(a, b) => a.id < b.id ? -1 : a.id > b.id ? 1 : 0` — the exact comparator
already implemented by the sibling tools `pending-approvals.js:75` and
`blocked-approvals.js:75`. This is *not* true Unicode code-point order; the
two orders diverge for approval IDs containing a code point above U+FFFF
compared against one in the U+E000–U+FFFF range, and Fixture D below pins
the divergent case so a builder cannot satisfy the contract with true
code-point ordering.
