## Spec'd description

Add `app/tools/outbox-timestamp-count.js`, a zero-dependency CommonJS command
that reads one persisted Relay state file while Relay is offline, validates the
complete stored sandbox-outbox collection, and counts receipts whose stored
`sentAt` string is strictly equal to one operator-supplied `<timestamp>`. It
reports only `{"outboxEntriesAtTimestamp":<count>}`, allowing an operator to
measure one exact stored send-time value without starting Relay, changing
durable state, parsing or converting time, looking up or echoing a receipt,
creating a receipt, performing a real send, or exposing the supplied
timestamp, stored timestamps, recipients, subjects, bodies, approval IDs,
events, jobs, approvals, or unrelated state.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/outbox-timestamp-count.js <state-file> <timestamp>`.
- Exactly two user-supplied positional arguments are accepted. Any other arity
  exits `2`, writes zero stdout bytes, writes exactly the following single
  LF-terminated line to stderr, and does not read or create a candidate state
  path:

  ```text
  usage: node app/tools/outbox-timestamp-count.js <state-file> <timestamp>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  outbox-timestamp-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  outbox-timestamp-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  outbox-timestamp-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied timestamp, OS error, parser text, input bytes, stack
  trace, outbox field, recipient, subject, body, approval ID, send timestamp,
  event field, job field, approval field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state, exact match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `outbox` element must be a non-null, non-array object with:

- own `to`, `subject`, and `body` properties, whose values are opaque;
- a non-empty string own `approvalId` property; and
- a non-empty string own `sentAt` property.

Outbox `approvalId` values must be pairwise distinct across the complete array.
Additional outbox properties are allowed and ignored. Event, job, and approval
elements are wholly opaque; only the fact that their top-level collections are
arrays is validated. An outbox `approvalId` need not resolve to a stored
approval. No relationship is imposed among `to`, `subject`, `body`,
`approvalId`, and `sentAt` beyond each field's individual rule. Different
receipts may have the same `sentAt` string.

The command validates the complete outbox array and approval-ID uniqueness
before counting. A receipt contributes one only when its stored `sentAt` is
strictly equal to the supplied `<timestamp>` using case-sensitive JavaScript
string equality. Neither value is parsed as a date, trimmed, case-folded,
decoded, coerced, normalized, or converted between timezones. The empty string
is an accepted positional argument but cannot equal any structurally valid
non-empty stored `sentAt`. A supplied timestamp with no match is a successful
query with count zero; there is no receipt lookup and no not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"outboxEntriesAtTimestamp":<nonnegative integer count>}
```

`outboxEntriesAtTimestamp` is the number of elements in the validated
`outbox` array whose stored `sentAt` matches the supplied timestamp exactly.
The supplied timestamp is not echoed. No stored send timestamp, recipient,
subject, body, approval ID, additional outbox field, event, job, approval, or
top-level metadata value is emitted.

## Ambiguity log

1. **What counts as an exact timestamp match?** Resolved from the reconciled
   ticket's explicit prohibition on parsing, normalization, coercion, and
   timezone conversion, plus the shipped exact field-matching command
   convention: case-sensitive JavaScript strict string equality. Direct
   case-distinct, leading-space, and `+00:00` literals make the forbidden
   transformations observable.
2. **Is an unknown, equivalent-instant, or empty timestamp an error?** No.
   Resolved from the original ticket criterion that no exact match returns
   `{"outboxEntriesAtTimestamp":0}\n` and from exactly-two-argument arity.
   AC3 passes an actual zero-byte second argument; AC7 proves it cannot bypass
   state validation.
3. **Can a positive count exceed one?** Yes. The shipped outbox validators
   require unique `approvalId`, not unique `sentAt`, and `app/server.js`
   records wall-clock strings without declaring timestamp uniqueness.
   Fixture A therefore freezes two distinct receipts with one identical
   `sentAt`, and the result is `2` without deduplication.
4. **Does “timestamp” require ISO-8601 syntax?** No. The repository state model
   stores a server-generated ISO string, but the shipped outbox validators
   require only a non-empty string and the Ready contract explicitly forbids
   parsing. The fourth Fixture A receipt freezes a non-ISO `sentAt` as
   structurally valid; this command does not introduce a new date validator.
5. **What state structure is required before counting?** Resolved from the
   four collections and receipt fields in
   [`app/server.js`](../../app/server.js), the shipped outbox-count and
   outbox-recipient-count commands, and the declared

   require all four arrays, validate every outbox receipt's five persisted
   properties and unique `approvalId`, allow additional top-level and receipt
   fields, and leave sibling collection elements opaque.
6. **Must message values be strings or receipt IDs resolve to approvals?** No.
   Action values originate in webhook payloads and merged outbox validators
   treat `to`, `subject`, and `body` as opaque. The frozen rules preserve that
   behavior, require only non-empty string `approvalId` and `sentAt`, and add
   no cross-record relationship.
