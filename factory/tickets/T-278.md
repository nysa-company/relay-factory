## Spec'd description

Relay creates one job per accepted event, but the offline `job-status-count`
report ([`app/tools/job-status-count.js`](../../app/tools/job-status-count.js),
shipped by [T-210](T-210.md)) accepts two jobs that reference the same event
ID and can count both. Extend the command's existing complete-state
validation to also reject a `jobs` array containing two elements with the
same non-empty `eventId`, using the identical fixed, redacted
`job-status-count: invalid Relay state` failure already used for every other
structural-validity violation. No new error line, output field, argument, or
dependency is introduced.

Product-doc and repository sources:

- [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec) and
  [conformance case 2](../../SPEC.md#test-cases-the-conformance-suite)
  establish that a repeated event `id` is idempotent at intake and "never
  creates a second job" — exactly one job per event ID is the invariant this
  offline report must not silently violate by double-counting a state that
  already broke it.
- [`app/server.js`](../../app/server.js) establishes the persisted job shape,
  including `eventId`, and that Relay's own intake path is what is meant to
  keep jobs one-per-event; this command is read-only and does not enforce
  that invariant at write time, only refuses to report over a state that
  already violates it.
- [T-210's frozen contract version 1](T-210.md#frozen-contract--version-1)
  establishes the complete current interface this ticket extends unchanged:
  the two-argument CLI, failure precedence (arity, read, parse, structural
  validation, then counting), the four-collection/job-field/status/counter/
  `lastError` structural rules, pairwise-distinct job `id` validation, the
  exact `{"jobsWithStatus":<count>}` success envelope, the three fixed
  redacted error lines, the complete sensitive-token privacy sweep, the
  read-only/offline/self-terminating lifecycle proof, and the `node:fs`
  /`readFileSync`-only source boundary. This ticket's Builder ownership is
  restricted to widening the existing structural-validity check by one rule;
  every other frozen behavior in T-210's contract is preserved byte-for-byte.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency, and [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

No endpoint, HTTP shape, UI selector, global-shell UI text, persisted schema,

Event-collection uniqueness is explicitly out of scope (AC4); only the `jobs`

## Acceptance criteria

1. A state containing two otherwise valid jobs with the same non-empty
   `eventId` exits `1`, writes exactly the existing invalid-state stderr line,
   and writes zero stdout bytes.
2. Duplicate event IDs are invalid whether both jobs match the requested
   status or only one does. Complete job validation and uniqueness checking
   precede filtering and counting.
3. Valid jobs with unique event IDs retain the existing output shape, field
   order, literal status matching, exit statuses, and stderr messages
   byte-for-byte. Empty state and zero matches remain valid.
4. Existing collection, job-field, status, counter, last-error, and unique job
   ID validation remain unchanged. Event records are not made unique here.
5. Failures remain redacted and leak no requested status, job or event ID,
   error text, state bytes, input path, parser detail, or operating-system
   detail.
6. The command remains offline, zero-dependency, deterministic, read-only, and
   self-terminating. Tests precede implementation; the targeted test, full app
   suite, and immutability check pass without other product or Factory changes.

### New rule: duplicate non-empty job `eventId` is a structural-validity violation

Within the existing single pass that already tracks job `id` uniqueness, the
Builder additionally tracks the set of `eventId` values seen across
`state.jobs` in array order. If a job's `eventId` (already guaranteed a
non-empty string by the unchanged per-job shape rule) has already been seen
earlier in the array, the state is structurally invalid — same class, same
exact fixed stderr line, same exit `1`, same zero stdout bytes as every other
structural violation. This check is independent of and additional to the
existing job-`id` uniqueness check; either violation alone is sufficient to
invalidate the state. No relationship is required between which job in a
duplicate `eventId` pair appears first and whether it matches the queried
`<status>`.

Reference implementation shape (Builder is not required to match this
verbatim, only its externally observable behavior):

```js
const jobIds = new Set();
const eventIds = new Set();
for (const job of state.jobs) {
  if (!isValidJob(job) || jobIds.has(job.id) || eventIds.has(job.eventId)) {
    return false;
  }
  jobIds.add(job.id);
  eventIds.add(job.eventId);
}
```
