## Spec'd description

Add `app/tools/outbox-recipient-body-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while Relay is offline,
validates the complete stored sandbox-outbox collection, and counts receipts
whose own `to` and `body` values both strictly equal the operator-supplied
`<recipient>` and `<body>` strings on the same receipt. It emits only
`{"outboxWithRecipientAndBody":<count>}`, allowing an operator to inspect the
cardinality of one exact recipient/body pair without starting Relay, changing
durable state, creating a receipt, performing a real send, or exposing query
values or stored content.

Product-doc and repository sources:

- [`SPEC.md` behavior 3](../../SPEC.md#behavior-spec) defines each proposed
  send action with `to`, `subject`, and `body`.
- [`SPEC.md` behavior 4](../../SPEC.md#behavior-spec) defines approval as the
  operation that creates one allowlisted sandbox outbox record and defines a
  blocked recipient as creating no send.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/outbox-recipient-body-count.js <state-file> <recipient>
  <body>`.
- Exactly three user-supplied positional arguments are accepted. Empty
  `<recipient>` and `<body>` strings are present arguments and are accepted.
  Any other arity exits `2`, writes zero stdout bytes, writes exactly the
  following single LF-terminated line to stderr, and does not read or create a
  candidate state path:

  ```text
  usage: node app/tools/outbox-recipient-body-count.js <state-file> <recipient> <body>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  outbox-recipient-body-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  outbox-recipient-body-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  outbox-recipient-body-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting. Empty query strings do not alter that
  precedence.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied recipient or body, OS error, parser text, input
  bytes, stack trace, stored field, event, job, approval, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state, exact conjunction, and successful output

A structurally valid state is a parsed non-null, non-array JSON object with own
`events`, `jobs`, `approvals`, and `outbox` properties whose values are arrays.
Additional top-level properties are allowed and ignored.

Every `outbox` element must be a non-null, non-array object with:

- own `to`, `subject`, and `body` properties, whose values are opaque;
- a non-empty string own `approvalId` property; and
- a non-empty string own `sentAt` property.

Outbox `approvalId` values must be pairwise distinct across the complete array.
Additional outbox properties are allowed and ignored. Event, job, and approval
elements are wholly opaque; only the fact that their top-level collections are
arrays is validated. An outbox `approvalId` need not resolve to a stored
approval. No relationship is imposed among `to`, `subject`, `body`,
`approvalId`, and `sentAt` beyond each field's individual rule.

The command validates the complete outbox array and approval-ID uniqueness
before counting. A receipt contributes exactly one only when both
`receipt.to === recipientArgument` and `receipt.body === bodyArgument` are
true for that same receipt. Matching is case-sensitive JavaScript strict
equality. The command does not trim, case-fold, coerce, or Unicode-normalize
stored or supplied values. Because command-line arguments
are strings, opaque non-string stored `to` or `body` values never match their
textual forms. Values found on different receipts never combine. A supplied
pair with no matches is a successful query with count zero; there is no
not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"outboxWithRecipientAndBody":<nonnegative integer count>}
```

The count is the number of elements in the validated `outbox` array whose own
`to` and `body` values both match the corresponding supplied strings exactly.
Neither query value is echoed. No stored recipient, subject, body, approval ID,
send timestamp, additional outbox field, event, job, approval, or top-level
metadata value is emitted.

## Ambiguity log

1. **Must recipient and body match on the same receipt?** The seed says an
   outbox entry whose recipient and body match. Resolved as a conjunction on
   one element, not two independent existence tests. Fixture A places each
   requested value alone on different receipts, and AC2 freezes the cross-pair
   count at zero.
2. **What does exact matching exclude?** Neither [`SPEC.md`](../../SPEC.md) nor
   [`factory/rulings.md`](../rulings.md) defines normalization. Resolved from
   the ticket's explicit no-trimming/no-normalization/no-coercion requirement
   and the shipped strict field-match convention as case-sensitive JavaScript
   strict equality. Direct leading-space, case-distinct, composed/decomposed,
   and numeric/string traps make each exclusion observable for both fields.
3. **Are empty recipient and body strings usage errors?** No. Arity counts
   positional arguments, not their contents, and the ticket requires exact
   string matching. AC3 freezes a successful zero count for two present empty
   strings; AC7 proves they cannot short-circuit structural validation.
4. **Is a pair with no matching receipt an error?** No. Resolved from the
   original ticket criterion: a valid no-match emits zero. Frozen Fixture B,
   cross-field, strict-typing, canonical-distinction, and empty-string cases
   all return the exact zero envelope.
5. **What state structure is required before counting?** Resolved from the
   four collections and receipt fields in [`app/server.js`](../../app/server.js),
   the shipped [outbox-count contract](T-206.md#structurally-valid-state-and-successful-output),
   the active [outbox-recipient-count contract](T-209.md#frozen-contract--version-2),
   and the declared [outbox-detail fixture seam](../../app/tests/outbox-detail.test.js):
   require all four arrays, validate every receipt's five persisted properties
   and unique `approvalId`, allow additional top-level and receipt fields, and
   leave sibling collection elements opaque.
6. **Must message values be strings, timestamps parse as ISO-8601, or receipt
   IDs resolve to approvals?** The current server persists the five keys, but
   action values originate in webhook payloads and shipped outbox validators
   treat `to`, `subject`, and `body` as opaque. Resolved by preserving those
   rules: opaque non-strings are structurally valid but cannot strictly match
   CLI strings; `approvalId` and `sentAt` are non-empty strings; no cross-record
   relationship or ISO parse is added.
7. **Why reject duplicate outbox approval IDs?** The
   [outbox-detail contract](T-169.md#http-interface) records one receipt per
   approval, and [`SPEC.md` conformance case 7](../../SPEC.md#test-cases-the-conformance-suite)
   requires recovery without duplication. S19 makes duplicate identity an
   invalid-state result before counting.
8. **How are failures classified without leaking input?** Raw OS and parser
   errors can reveal paths or state bytes. Resolved using the shipped offline
   count convention: usage exit `2`, operational exits `1`, fixed single-line
   redacted errors, empty opposite streams, and precedence from arity through
   complete structure.
9. **How are offline, read-only, and self-terminating claims proved?** Resolved
   with synchronous child invocations under a `5_000` ms timeout, exact file
   and directory fingerprints, repeated success, isolated teardown, and a
   production source boundary admitting only `node:fs` and `readFileSync`.
10. **Are derived fixtures or generated expectations involved?** No invalid
    fixture or query is transformed from valid data. The Unicode strings are
    direct literals with frozen code points rather than normalization results.
    All serialized fixtures are pairwise byte-compared, and every expected ID,
    timestamp, argument, and count comes from literal setup.
11. **Does fixture cleanup have hidden dependencies?** No service or database
