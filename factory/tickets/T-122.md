## Description

Add a focused, read-only `GET /api/events/:id` endpoint to the zero-dependency
Relay API. The endpoint returns one accepted event together with the one job
created for it, so an operator can inspect that relationship without fetching
and searching all of `GET /api/state`.

This is an additive read surface over the state already required by
[Behavior spec items 1, 2, and 7](../../SPEC.md#behavior-spec): accepted events
are durable, each accepted event enqueues one job, and the API exposes that
state as JSON. It makes the focused lookup mechanically testable using the
[walking-skeleton acceptance case](../../SPEC.md#test-cases-the-conformance-suite)
while preserving the repository's
[zero-dependency product boundary](../../AGENTS.md#boundaries) and
[verification contract](../../AGENTS.md#verification).

## Acceptance criteria

1. With the frozen `evt-detail-001` state fixture loaded, `GET
   /api/events/evt-detail-001` returns HTTP `200`, header `Content-Type:
   application/json`, and a JSON object exactly equal to the frozen success
   response, including the stored event and its `job-evt-detail-001` job.
2. With the same fixture loaded, `GET /api/events/evt-missing` returns HTTP
   `404`, header `Content-Type: application/json`, and exactly
   `{"error":"no such event"}`.
3. After one successful lookup and one unknown-event lookup against the frozen
   fixture, both `GET /api/state` and the bytes of `DATA_DIR/state.json` are
   unchanged from their values immediately before the two requests.
4. Repository history and diffs show `app/tests/event-detail.test.js` committed
   before the implementation change, the implementation change modifies only
   `app/server.js`, `app/package.json` remains byte-for-byte unchanged, and no
   tracked path under `factory/` other than this ticket changes during test
   authoring or implementation.

### HTTP interface

- Method and path: `GET /api/events/:id`.
- `:id` is one non-empty path segment and is compared by exact string equality
  with `event.id`.
- The selected event is the unique event in `state.events` whose
  `id === :id`. Its related job is the unique job in `state.jobs` whose
  `eventId === event.id`. Relay's idempotent-acceptance and one-job-per-event
  invariants guarantee this uniqueness; manually corrupted state that violates
  [Behavior spec items 1 and 2](../../SPEC.md#behavior-spec) is out of scope.
- An existing event returns status `200`, `Content-Type: application/json`,
  and this exact top-level shape, with no additional keys:

  ```json
  {
    "event": "<the selected event object verbatim>",
    "job": "<the related job object verbatim>"
  }
  ```

  “Verbatim” means every stored key and value is serialized without filtering,
  renaming, deriving, or adding fields. JSON object-member order is not part of
  the contract.
- If no event has the requested ID, return status `404`, `Content-Type:
  application/json`, and exactly:

  ```json
  {"error":"no such event"}
  ```

- Both outcomes are read-only: they do not mutate the in-memory state, call
  `persist()`, or change `DATA_DIR/state.json`.
- No authentication, cookies, CORS behavior, cross-origin call, external send,
  UI, or preview-deploy behavior is added. The endpoint uses the same-origin
  HTTP server and existing JSON response convention as `/api/state`.

## Ambiguity log

- **What is the success envelope?** The seed ticket required the stored event
  and related job but did not name the keys. Resolved as the minimal
  `{"event":...,"job":...}` envelope, preserving both stored objects verbatim
  and adding no new product state. This follows
  [Behavior spec items 1, 2, and 7](../../SPEC.md#behavior-spec).
- **How is the related job selected?** Resolved by the documented invariant
  that every accepted event enqueues one job: exact
  `job.eventId === event.id` matching. Corrupted persisted state with zero or
  multiple related jobs is outside this ticket rather than left for the
  builder to define.
- **How is “read-only” measured?** Resolved as equality of both the public
  `/api/state` value and the persisted `state.json` bytes before and after one
  success and one `404`, directly exercising
  [Behavior spec items 6 and 7](../../SPEC.md#behavior-spec).
- **Does the route need auth, cross-origin, UI, deploy, or external-send
  behavior?** No. The current Relay API is one same-origin HTTP server and this
  ticket only reads its durable state. `External: no` remains correct.
- **Do sibling tickets overlap this implementation surface?** Yes. A grep of
  local sibling tickets and inspection of every other leased remote branch
  (`origin/ticket/T-123`, `origin/ticket/T-124`, and
  `origin/ticket/T-125`) found that all four tickets declare
  `app/server.js` as builder-owned. Their test files and endpoint paths are
  distinct, but their additive route-dispatch edits can conflict textually.
  T-122 remains one-session sized and isolated on its own branch; bounded
  concurrency does not make any sibling contract part of this one. The
  dispatcher must serialize integration/rebase conflict resolution rather
  than let a builder edit a sibling ticket or broaden this contract.
- **Was there a prior operator ruling?** No `factory/rulings.md` exists, and no
  product or security ambiguity requires an operator decision for version 1.
