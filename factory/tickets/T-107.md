## Spec'd description

Add one product-owned, ticket-independent command that selects Relay's sealed
software-factory release from `factory/KIT_PIN` and composes that release's two
existing public non-task checks:

1. `scripts/adapters/contract-test.sh --adapters codex,cursor-openai,claude-code,cursor-anthropic`
2. `scripts/adapters/contract-test.sh --routes`

The command reports all four configured adapters, then the production/OpenAI
and checking/Anthropic startup routes. Its exit status is the route check's
status, not the all-adapter check's status: a disabled optional fallback remains
visible without making a ready primary route unsafe. Relay does not source
`scripts/lib/backend-policy.sh`, reproduce its adapter/family map or resolver,
change the sealed release, accept ticket/task text, or invoke a task-bearing
adapter.

This is the external-product version of the useful behavior and deterministic
non-task guarantees frozen on superseded T-106 at software-factory commit
`cc80aa9`. File ownership and tests move to Relay; kit policy stays behind the
pinned release's public commands.

### Entrypoint and arguments

Operator invocation from the Relay repository root:

```bash
factory/backend-readiness.sh
```

File location: `factory/backend-readiness.sh`. The script accepts no arguments,
does not read stdin, and never accepts a ticket, role, adapter list, or task.
Any argument is a usage error with exit `2`, no stdout, and exactly:

```text
usage: factory/backend-readiness.sh
```

### Pinned release selection

The script reads `factory/KIT_PIN` relative to its own repository location,
not the caller's working directory. The file must contain exactly one line
matching `^[0-9a-f]{40}$`. The selected check must be the executable regular
file at:

```text
$HOME/.factory/kits/releases/<KIT_PIN>/scripts/adapters/contract-test.sh
```

No symlink or alternate release path is accepted. Selection errors occur
before either check is invoked, exit `2`, emit no stdout, and emit exactly one
of these stderr lines:

```text
backend-readiness: factory/KIT_PIN must contain exactly one lowercase 40-character SHA
backend-readiness: pinned adapter contract check is unavailable
```

Tests set `HOME` to an isolated fixture directory; there is no product-specific
release-root override.

### Composed non-task calls

The selected entrypoint is invoked exactly twice, sequentially, with the
caller's environment and these exact arguments:

```text
--adapters codex,cursor-openai,claude-code,cursor-anthropic
--routes
```

The first call's status is reported but does not determine the wrapper exit;
this keeps disabled optional fallback distinct from an unsafe required route.
The second call's exit status is authoritative. Relay does not interpret,
rewrite, filter, or duplicate kit-owned probe and route policy.

### Output and exit status

The wrapper writes these headings/result lines to stdout and passes through
each check's stdout and stderr byte-for-byte in call order:

```text
[relay-readiness] adapters=openai:codex,cursor-openai;anthropic:claude-code,cursor-anthropic
<adapter check stdout>
[relay-readiness] adapter_check_exit=<adapter exit>
[relay-readiness] routes=production/openai;checking/anthropic
<route check stdout>
[relay-readiness] route_check_exit=<route exit>
[relay-readiness] result=<SAFE|UNSAFE>
```

`result=SAFE` and wrapper exit `0` occur only when the route check exits `0`.
For every nonzero route-check status, the wrapper emits `result=UNSAFE` and
exits `1`. Wrapper validation/usage failures exit `2` as specified above.

The provider labels in wrapper headings are operator presentation only. Route
selection, state/reason meanings, fallback eligibility, prerequisites, model
allowlisting, authentication probes, and adapter exit behavior remain entirely
owned by the pinned `contract-test.sh` and its release-private policy.

  T-106's deterministic trace technique: the fixture separately logs calls and

  task trace.

  The operator explicitly requested composition from `factory/KIT_PIN`; the
  pinned architecture makes that full SHA the product's engine selection.
- **Does this command trigger an external send?** No. It accepts no task and
  invokes only non-task adapter/route probes, so `External: no` remains correct
  and no `external` label is required.
