## Spec'd description

Add `app/tools/job-status-retry-count.js`, a zero-dependency CommonJS command
that reads one persisted Relay state file while Relay is offline, validates
the complete stored job collection, and counts only jobs whose stored `status`
and stored `retries` value both equal operator-supplied filters. It emits only
`{"jobsWithStatusAndRetries":<count>}`, allowing an operator to distinguish
retry histories within one queue state without starting Relay, changing
durable state, summing attempts or retries, or exposing job IDs, event links,
errors, counters, sibling collections, or other stored content.

- [`SPEC.md` behavior 2](../../SPEC.md#behavior-spec) defines Relay's durable
  background-job attempt, retry, and visible dead-letter lifecycle.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/job-status-retry-count.js <state-file> <status> <retries>`.
- Exactly three user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not read or create a candidate
  state path:

  ```text
  usage: node app/tools/job-status-retry-count.js <state-file> <status> <retries>
  ```

- After arity validation, `<status>` must be exactly one of the three direct
  lowercase literals `pending`, `done`, or `dead`. Any other string exits `2`,
  writes zero stdout bytes, writes exactly the following LF-terminated line to
  stderr, and does not read or create `<state-file>`:

  ```text
  job-status-retry-count: invalid status
  ```

- After status validation, `<retries>` must match the ASCII decimal grammar
  `0|[1-9][0-9]*`. There is no accepted sign, leading zero on a multi-digit
  value, decimal point, exponent, radix prefix, whitespace, empty string, or
  non-ASCII digit. There is no separate accepted-value upper bound; the
  decimal is interpreted losslessly as a nonnegative mathematical integer.
  A nonmatching string exits `2`, writes zero stdout bytes, writes exactly the
  following LF-terminated line to stderr, and does not read or create
  `<state-file>`:

  ```text
  job-status-retry-count: invalid retries
  ```

- If both filters are invalid, status validation wins. Failure precedence is
  argument count, status validation, retry-syntax validation, file read, JSON
  parse, complete structural validation, then counting.
- After argument validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  job-status-retry-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  job-status-retry-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  job-status-retry-count: invalid Relay state
  ```

- Every error is one fixed line terminated by exactly one LF. No error
  includes the state path, supplied filter, OS error, parser text, input bytes,
  stack trace, job ID, event link, status, attempt or retry counter,
  `lastError`, event field, approval field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.
  The directory fixture freezes the command envelope, not an errno, error
  class, or operating-system message.

### Structurally valid state, exact predicates, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with exactly four own properties: `events`, `jobs`, `approvals`,
and `outbox`, each an array.

Every `jobs` element must be a non-null, non-array object with:

- non-empty string own properties `id` and `eventId`;
- an own `status` property exactly equal to `pending`, `done`, or `dead`;
- own `attempts`, `retries`, and `attemptsSinceRetry` properties that are
  JavaScript numbers satisfying `Number.isInteger(value) && value >= 0`; and
- an own `lastError` property equal to `null` or a string, including `""`.

Job IDs must be pairwise distinct across the complete array. Additional job
properties are allowed and ignored. Event, approval, and outbox elements are
wholly opaque; only the fact that their top-level collections are arrays is
validated. A job `eventId` need not resolve to a stored event. No relationship
is imposed among `status`, the three counters, and `lastError` beyond each
field's individual rule.

The command validates the complete job array and job-ID uniqueness before
counting. A job contributes exactly one only when both of these are true:

1. `job.status === <status>` using case-sensitive JavaScript strict equality;
2. the mathematical integer represented by `job.retries` equals the
   mathematical integer represented by the canonical decimal `<retries>`.

The retry comparison is exact and does not parse through a lossy decimal
round-trip; `BigInt(job.retries) === BigInt(<retries>)` after the frozen
validations is one conforming evaluation. Neither filter is trimmed,
case-folded, normalized, coerced from a noncanonical spelling, treated as a
minimum, or treated as a substring. The values of `attempts`,
`attemptsSinceRetry`, and `lastError` do not affect the count after structural
validation. Retry values are compared, never summed. A valid filter pair with
no match is a successful zero-count query.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"jobsWithStatusAndRetries":<nonnegative integer count>}
```

`jobsWithStatusAndRetries` is the number of elements in the validated `jobs`
array satisfying both frozen predicates. No supplied filter, stored job ID,
`eventId`, status, counter, `lastError`, additional job field, event,
approval, or outbox value is emitted.

## Ambiguity log

1. **Which retry measure does the filter use?** Resolved from the ticket's
   explicit `retry count`, the persisted job shape, and
   [`app/server.js`](../../app/server.js): use the stored `retries` counter,
   which increments on explicit dead-job retry. Do not use cumulative
   `attempts`, resettable `attemptsSinceRetry`, or a sum.
2. **What is a canonical nonnegative integer argument?** Resolved by making
   the ticket's word `canonical` mechanically observable: accept only ASCII
   decimal `0|[1-9][0-9]*`, with no sign, leading zero, decimal, exponent,
   radix prefix, whitespace, or Unicode digit. Interpret the accepted decimal
   losslessly, so the contract does not introduce an undocumented safe-integer
   ceiling or lossy coercion.
3. **Are invalid filters no-match queries or usage failures?** The reconciled
   ticket requires invalid arguments to be rejected before file access.
   Therefore unsupported status and noncanonical retry spellings exit `2`
   with separate fixed errors; when both are invalid, status wins. Valid
   filters with no matching job exit `0` with count zero.
4. **How much of persisted state is validated?** Resolved from the shipped
   [`job-status-count` command](../../app/tools/job-status-count.js),
   [`job-attempts` command](../../app/tools/job-attempts.js), and their
   protected suites: require exactly the four top-level Relay collections,
   validate every job and unique job ID before counting, permit additional job
   fields, and treat sibling collection elements as opaque.
5. **Do plausible job-field combinations impose extra invariants?** No.
   Resolved from the same shipped validators: status, attempts, retries,
   attempts-since-retry, and last error each satisfy their individual rule;
   no cross-field relationship or event foreign-key lookup is added.
6. **What is observable on failures?** Resolved from the existing offline job
   command convention: fixed one-line redacted errors with zero stdout. Arity
   and filter failures do not access the path; read, parse, and structural

7. **Can the command mutate, start, or contact Relay?** No. Resolved from the
