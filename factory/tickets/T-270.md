## Description

Operators can count one event type at a time via `app/tools/event-type-count.js`,
but cannot obtain a compact breakdown without repeatedly reading the same state
file. Add `app/tools/event-type-summary.js`, a zero-dependency offline command
that reports counts for every valid stored event type in one deterministic
result. This follows the established offline-diagnostic family in
`app/tools/event-count.js`, `app/tools/event-type-count.js`,
`app/tools/event-metadata.js`, and `app/tools/event-timestamp.js`: same state
shape, same read-only/fixed-error-envelope conventions, same
`node --test tests/*.test.js` verification path (`app/package.json`). No
separate engine/acceptance spec doc exists in this product repo (`docs/`
contains only `git-flow.md`); the sibling tool source and tests are the
authoritative convention for everything this contract does not itself decide.
`factory/rulings.md` was checked and contains no ruling applicable to this
ticket.

## Acceptance criteria

1. `node app/tools/event-type-summary.js <state-file>` exits `0`, writes one
   compact JSON line shaped as `{"eventTypes":[{"type":<stored-type>,"count":N}]}`,
   and writes zero stderr bytes for valid state.
2. Entries are ordered deterministically: strings by code-point order before
   numbers by ascending numeric value. Each distinct string or non-zero finite
   JSON number is counted exactly once; strings and numbers never coerce.
3. Empty input produces `{"eventTypes":[]}`. Repeated invocation is
   byte-for-byte deterministic.
4. Missing or empty types, zero, booleans, objects, arrays, non-finite values,
   invalid event IDs or timestamps, and duplicate event IDs are invalid before
   summarization.
5. Usage, unreadable-file, invalid-JSON, and invalid-state failures use fixed
   redacted one-line stderr messages, the established exit codes, and zero
   stdout bytes. No state contents or paths leak.
6. The command remains offline, zero-dependency, read-only, and
   self-terminating. Tests precede implementation; the targeted test, full app
   suite, and immutability check pass without other product or Factory changes.

## Ambiguity log

- **Can `type` be a number as well as a string?** Not ambiguous — the
  pre-existing AC2/AC4 text on this ticket already says so explicitly
  ("distinct string or non-zero finite JSON number"). Frozen below as: valid
  `type` is a non-empty string, or a `typeof === "number"` value that is
  `Number.isFinite` and `!== 0`.
- **What makes an event ID or `receivedAt` invalid?** Not answered by product
  docs (none exist beyond `AGENTS.md`/`docs/git-flow.md`). Resolved by
  matching the established sibling convention in `app/tools/event-count.js`,
  `app/tools/event-type-count.js`, `app/tools/event-metadata.js`, and
  `app/tools/event-timestamp.js`: `id` and `receivedAt` must each be an own,
  non-empty string; no additional format (e.g. ISO-8601) is enforced anywhere
  in the existing family, so none is added here.
- **Do `jobs`/`approvals`/`outbox` entries need structural validation?**
  Resolved no, matching the established sibling convention: those collections
  need only exist and be arrays (`isValidState`'s `COLLECTIONS` check); their
  element contents are opaque and unvalidated, exactly as proven by
  `app/tests/event-type-count.test.js` Fixture B (`jobs:[null]`,
  `approvals:[7]`, `outbox:["...opaque..."]` yields a valid, zero-count
  result).
- **What does "code-point order" mean operationally?** Resolved as ordinary
  JavaScript string comparison (`<`/`>` on UTF-16 code units). Every frozen
  fixture type string is single-code-unit-per-character (ASCII), so code-unit
  order and code-point order coincide and there is no surrogate-pair edge case
  to additionally decide.
- **Does "zero" (invalid) include `-0`?** Resolved yes: `-0 === 0` is `true`
  in JS, so a bare `value !== 0` zero-check already rejects both `0` and `-0`

  the AC text.

### Command interface

`node app/tools/event-type-summary.js <state-file>` — exactly one positional
argument.

### Validation (`isValidState`)

Same `COLLECTIONS = ["events", "jobs", "approvals", "outbox"]` structural gate
as every sibling tool: `state` must be a non-null, non-array object with own
array-valued properties for all four names. `jobs`, `approvals`, and `outbox`
element contents are not further validated (matches sibling convention; see
ambiguity log).

For every element of `state.events`:

- must be a non-null, non-array object;
- own `id`: non-empty string; not equal to any earlier event's `id`
  (duplicate IDs invalidate the whole state);
- own `receivedAt`: non-empty string;
- own `type`: **either** a non-empty string **or** a `number` with
  `Number.isFinite(value) && value !== 0`. Anything else (missing, `""`,
  `0`/`-0`, boolean, object, array, non-finite number) invalidates the whole
  state.

Any failure anywhere in `state.events` makes the entire state invalid (exit
`1`, `invalid Relay state`) — summarization never runs on a partially valid
state.

### Output (valid state)

Group counts into two maps keyed by the exact `type` value: one for strings,
one for numbers (never the same map — this is what guarantees string `"3"`
and number `3` never coincide). Build `eventTypes` as: string entries first,
sorted by `type` ascending via ordinary `<` (code-unit order), each as
`{"type":<string>,"count":<N>}`; then number entries, sorted by `type`
ascending numerically, each as `{"type":<number>,"count":<N>}`. Serialize with
`JSON.stringify({ eventTypes })` (compact, no added whitespace) plus a single
trailing `\n`. Exit `0`. Zero stderr bytes.

| Case | stderr (exact bytes) | exit |

| `argv.length !== 1` | `usage: node app/tools/event-type-summary.js <state-file>\n` | `2` |
