## Spec'd description

Add one zero-dependency, read-only Node 18+ command,
`node app/tools/approval-outbox-count.js <state-file> <approval-id>`, that
selects one persisted approval by exact, case-sensitive ID while Relay is
offline and counts every stored outbox element whose `approvalId` is strictly
equal to that stored approval ID. It emits only the stored approval ID and the
integer count under the exact keys `approvalId` and `outboxEntries`. A stored
approval with no linked outbox element succeeds with count `0`; repeated
outbox links are counted individually.

This gives an operator a deterministic, data-minimized way to inspect whether
an approval has zero, one, or duplicate sandbox outbox records without
starting Relay, changing durable state, or printing recipient, subject, body,
timestamps, approval actions, rejection reasons, event payloads, job errors,
or unrelated state.

### Valid state, relationship rules, and result shape

For this command, structurally valid state is a non-null, non-array JSON object
with own `events`, `jobs`, `approvals`, and `outbox` properties whose values
are arrays.

Every `approvals` element must be a non-null, non-array object with a non-empty
string own property `id`. Approval IDs must be pairwise distinct.

Every `outbox` element must be a non-null, non-array object with a non-empty
string own property `approvalId`. Every stored outbox `approvalId` must
strictly equal one stored approval `id`. Repeated outbox `approvalId` values
are valid and each matching element contributes one to the count.

Contents of `events` and `jobs`, additional top-level keys, and additional
approval and outbox keys are opaque. Approval action, status, reason, job link,
and proposal timestamp; outbox recipient, subject, body, and send timestamp;
event records and payloads; and job records and errors are never copied to
output.

After complete validation, select the approval whose stored `id` strictly
equals `<approval-id>`. Count every `outbox` element whose stored
`approvalId` strictly equals that selected stored ID. Success exits `0`, writes
zero stderr bytes, and serializes one new object with keys in this exact order:

```json
{"approvalId":<stored approval id>,"outboxEntries":<nonnegative integer count>}
```

Use compact `JSON.stringify` formatting and append exactly one LF byte. There
are no endpoint paths, HTTP request or response shapes, UI routes, UI
selectors, or global page-shell text in this contract.

## Ambiguity log

1. **What is being counted?** The seed says “stored outbox entries link to
   that approval.” Resolved from
   [`app/server.js`](../../app/server.js): compare every outbox element's
   stored `approvalId` with the selected approval's stored `id`. Count array
   elements, not unique IDs, message fields, or timestamps.
2. **Can the result exceed one?** Normal Relay execution creates at most one
   outbox record for an approval because approval status leaves `pending`
   after the first send, and conformance case 7 forbids duplicated effects.
   The ticket asks for a count over persisted entries, so the offline
   diagnostic accepts and counts repeated links rather than hiding a duplicate
   persisted effect. Fixture A freezes `2` as observable.
3. **What makes state structurally valid?** The product has no general
   state-file validator. Resolved narrowly from the fields consumed here:
   require all four collection arrays, unique non-empty approval IDs,
   non-empty outbox approval links, and closure of every outbox link to a
   stored approval. Unconsumed records and additional fields remain opaque.
4. **Can a valid target bypass an invalid sibling?** No. Complete validation
   precedes lookup and counting so output is not produced from an
   untrustworthy file. S19 and S20 make invalid approval and outbox siblings
   independently observable.
5. **What does exact ID selection mean?** The seed did not state whether
   trimming or case folding was forbidden. Resolved as strict equality over
   the literal argument, matching current server lookups. Uppercase and
   trailing-space misses distinguish both alternatives.
6. **Exact errors and precedence.** The seed required fixed redacted errors
   but did not freeze text, exit codes, or ordering. No entry in
