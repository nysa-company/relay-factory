## Spec'd description

Add `app/tools/approval-job-status-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while Relay is offline,
validates the complete stored approval collection, and counts approvals whose
stored `jobId` and `status` are both exactly equal to two operator-supplied
arguments, `<job-id>` and `<status>`. It reports only
`{"approvalsWithJobAndStatus":<count>}`, allowing an operator to inspect
job/status cardinality without starting Relay, changing durable state,
approving or rejecting an action, creating an outbox receipt, performing a
real send, or exposing the supplied job ID, supplied status, stored actions,
approval identities, recipients, reasons, proposal timestamps, events, jobs,
outbox records, or unrelated state.

Unlike the shipped `job-status-count` and `approval-recipient-count`
commands, this command's two match arguments are constrained before any file
access: `<job-id>` must be non-empty and `<status>` must exactly equal one of
Relay's four approval statuses. This is an explicit, stricter contract than
`job-status-count.js`'s convention of treating an out-of-domain status
argument as an ordinary zero-match query; see Ambiguity log item 1.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/approval-job-status-count.js <state-file> <job-id>
  <status>`.
- Exactly three user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not read or create a
  candidate state path:

  ```text
  usage: node app/tools/approval-job-status-count.js <state-file> <job-id> <status>
  ```

- With exactly three arguments, `<job-id>` must be a non-empty string and
  `<status>` must be exactly one of `pending`, `sent`, `rejected`, or
  `blocked_recipient` (case-sensitive JavaScript strict equality against the
  literal enum members). Either violation exits `2`, writes zero stdout
  bytes, writes the identical usage line above to stderr, and does not read
  or create a candidate state path. This value check and the arity check
  produce byte-identical output; their relative order is not externally
  observable and is not specified beyond "both precede any file access."
- After the two argument checks pass, the command synchronously reads
  `<state-file>` directly as UTF-8. Any `readFileSync` failure, including an
  absent path, a directory in place of a regular file, or an OS read denial,
  exits `1`, writes zero stdout bytes, and writes exactly:

  ```text
  approval-job-status-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  approval-job-status-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  approval-job-status-count: invalid Relay state
  ```

- Failure precedence is: argument count, argument-value validity (job ID
  non-empty, status in the enum), file read, JSON parse, complete structural
  validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error
  includes the state path, supplied job ID, supplied status, OS error,
  parser text, input bytes, stack trace, approval field, action value,
  reason, event field, job field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture
  matrix; if `readFileSync` throws for either, the frozen read-error result
  applies. The directory fixture freezes the exact command envelope, not any
  errno, error class, or operating-system text.

### Structurally valid state, exact match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string own properties `id`, `jobId`, and `proposedAt`;
- an own `status` property exactly equal to `pending`, `sent`, `rejected`, or
  `blocked_recipient`;
- an own `action` property that is a non-null, non-array object with own
  `to`, `subject`, and `body` properties; and
- either no own `reason` property, or an own `reason` whose value is `null`
  or a string, including the empty string.

Approval IDs must be pairwise distinct across the complete array. The values
of `action.to`, `action.subject`, and `action.body` are opaque and never
consulted by this command. Additional action and approval properties are
allowed and ignored. Event, job, and outbox elements are wholly opaque; only
the fact that their top-level collections are arrays is validated. A `jobId`
need not resolve to a stored job. No relationship is imposed among `status`,
`action`, `proposedAt`, and `reason`.

The command validates the complete approval array and ID uniqueness before
counting. An approval contributes one to the count only when
`approval.jobId === <job-id>` **and** `approval.status === <status>`, both
using case-sensitive JavaScript strict equality. The command does not
coerce, trim, case-fold, decode, or Unicode-normalize either value. A
supplied pair with no matches is a successful query with count zero; there
is no not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON
object followed by exactly one LF. Its only key is:

```json
{"approvalsWithJobAndStatus":<nonnegative integer count>}
```

`approvalsWithJobAndStatus` is the number of elements in the validated
`approvals` array whose stored `jobId` and `status` both match the supplied
arguments exactly. Neither supplied argument is echoed. No stored action
value, approval ID, reason, proposal timestamp, additional approval field,
event, job, outbox, or top-level metadata value is emitted.

## Ambiguity log

1. **Must an out-of-domain `<status>` (or empty `<job-id>`) be rejected
   before file access, or treated as an ordinary zero-match query?** The
   shipped `job-status-count.js` treats any status string as an opaque
   filter value and never pre-validates it (an unrecognized status simply
   yields count zero after full state validation). This ticket's own
   Acceptance criteria 2-3 state explicitly: "Job ID must be non-empty.
   Status must exactly equal one Relay approval status... Invalid arguments
   are rejected before file access." That text is the ticket's own
   authority and takes precedence over the older command's convention for
   this new command. Resolved: both value checks run before any file
   access, alongside the arity check, sharing byte-identical output. Sibling
   ticket T-254 uses the same "non-empty is required" resolution for its own
   free-form ID argument, though it uses no additional enum constraint; T-253
   requires two non-empty string arguments with no enum. Neither sibling
   ticket's file paths overlap this one's.
2. **What exact error text and exit code apply to an invalid argument
   value?** No shipped tool in this family has a value-validity class of
   pre-file-access failure to imitate (only arity is checked pre-file-access
   elsewhere). Resolved by extending the existing usage-line convention:
   reusing the identical single-line usage envelope and exit code `2` for
   every pre-file-access rejection (arity, empty job ID, out-of-enum status)
   avoids inventing new frozen error text, and is externally indistinguishable
   from arity failure by design — see the Command-line interface section.
3. **What counts as an exact `(jobId, status)` match?** Neither the product
   spec nor [`factory/rulings.md`](../rulings.md) defines match
   normalization. Resolved from the ticket's exact-match requirement and the
   shipped strict field-match convention (`approval-recipient-count.js`,
   `job-status-count.js`) as case-sensitive JavaScript strict equality on
   both fields independently, with no coercion, trimming, case folding,
   decoding, or Unicode normalization. AC2 and AC3 make each material
   distinction, including cross-field independence, observable with direct
   literals.
4. **Is a `(jobId, status)` pair with no matching approval an error?**
   Resolved from the ticket's requirement "zero matches is valid": every
   no-match query against structurally valid state and in-domain arguments
   exits `0` with `{"approvalsWithJobAndStatus":0}\n`.

   `approvalsWithJobAndStatus` integer. Resolved by freezing a count-only
   object whose single key is `approvalsWithJobAndStatus`; both supplied
   arguments and every stored value are forbidden from both output streams.
