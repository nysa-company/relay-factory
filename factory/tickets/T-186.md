## Spec'd description

Add one zero-dependency, read-only Node 18+ command,
`node app/tools/approval-state.js <state-file> <approval-id>`, that selects one
persisted Relay approval by an exact, case-sensitive ID while the service is
offline. It emits only the selected approval's `approvalId`, `jobId`, and
`status`. This gives an operator a minimal lifecycle lookup without exposing
the approval action, rejection reason, related event payload or job error,
outbox content, or unrelated persisted state.

Product-doc sources:

- [`SPEC.md` behavior 3](../../SPEC.md#behavior-spec) defines a proposed action,
  its approval record, and its initial `pending` status.
- [`SPEC.md` behaviors 4-5](../../SPEC.md#behavior-spec) define the `sent`,
  `blocked_recipient`, and `rejected` approval outcomes.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the atomically
  persisted state file Relay's durable source of truth.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) establishes the persisted
  state collections; this command reads the same state representation without
  starting the service.
- [`SPEC.md` conformance cases 5-7](../../SPEC.md#test-cases-the-conformance-suite)
  require the approval gate, blocked-send record, and crash-recovered state to
  remain observable without duplicate effects.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) requires `app/` to remain
  zero-dependency and keeps Factory controls outside application work.
  [`AGENTS.md` Verification](../../AGENTS.md#verification) defines the later
  full-app and immutability checks.

The command is a data-minimized projection over an existing regular file. It
does not start Relay, execute or reject an approval, write an outbox record,
change the persisted schema, or modify the server, worker, UI, package
manifest, dependencies, lockfiles, or Factory controls.

### Command-line interface

- Repository-root invocation:
  `node app/tools/approval-state.js <state-file> <approval-id>`.
- Exactly two positional arguments are accepted. The approval ID is used
  verbatim; it is not trimmed, case-folded, decoded, normalized, or prefixed.
- Zero, one, or three positional arguments produce exit code `2`, empty
  stdout, and exactly this single LF-terminated stderr line:

  ```text
  usage: node app/tools/approval-state.js <state-file> <approval-id>
  ```

- The command reads the named regular file directly as UTF-8. It does not
  import, require, spawn, or otherwise execute `app/server.js`; open an HTTP or
  other network listener; make an outbound request; or leave a timer or child
  process running.
- A read failure, including a nonexistent path, a directory in place of a
  regular file, or an OS read denial, produces exit code `1`, empty stdout, and
  exactly:

  ```text
  approval-state: cannot read state file
  ```

- Bytes rejected by `JSON.parse` produce exit code `1`, empty stdout, and
  exactly:

  ```text
  approval-state: state file is not valid JSON
  ```

- A parsed value that fails the frozen structural rules produces exit code
  `1`, empty stdout, and exactly:

  ```text
  approval-state: invalid Relay state
  ```

- A valid state with no approval whose `id` is strictly equal to the supplied
  ID produces exit code `1`, empty stdout, and exactly:

  ```text
  approval-state: no such approval
  ```

- No error includes the input path, approval ID, OS error, parser text, input
  content, stack trace, or a second line. Every displayed line above ends with
  one LF byte.
- Validation precedence is argument count, read, JSON parse, structure, then
  exact-ID lookup. No path is written, renamed, deleted, chmodded, or created.

The arity tests use fresh empty temporary parents. The one-argument case
supplies nonexistent `<tmp>/state-a.json`. The three-argument case supplies
nonexistent `<tmp>/state-a.json`, `appr-pending`, and `extra`. The usage result
rather than the read-failure result proves arity validation precedes file
access.

### Valid state and successful result

For this command, a structurally valid state is a non-null, non-array JSON
object with own `events`, `jobs`, `approvals`, and `outbox` properties whose
values are arrays.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string `id`;
- non-empty string `jobId`; and
- string `status` equal to exactly one of `pending`, `sent`, `rejected`, or
  `blocked_recipient`.

Approval IDs must be pairwise distinct. Contents of `events`, `jobs`, and
`outbox`, additional top-level keys, and additional approval keys are opaque to
structural validation. In particular, `action`, `reason`, and `proposedAt` may
be present but are never copied to output. A referenced job need not exist;
the stored `jobId` is reported without joining another collection.

On an exact-ID match, serialize one new object with keys in this exact order:

```json
{"approvalId":<stored id>,"jobId":<stored jobId>,"status":<stored status>}
```

Use compact `JSON.stringify` formatting and append exactly one LF byte.
Success exits `0` with empty stderr. There are no endpoint paths, HTTP request
or response shapes, UI routes, or UI selectors in this contract.

## Ambiguity log

1. **Exact error protocol.** The seed required fixed privacy-safe errors but
   did not freeze text, exit codes, or validation precedence. No entry in
   [`factory/rulings.md`](../rulings.md) addresses offline commands. Resolved
   as exact path-independent usage, read, parse, structure, and lookup
   outcomes, following the shipped offline-command convention.
2. **Meaning of structurally valid.** The product docs establish the four
   persisted collections and approval outcomes but do not define a general
   state-file validator. Resolved narrowly: validate every collection as an
   array and only the approval fields this command matches or emits; treat
   unrelated contents and additive fields as opaque.
3. **Duplicate approval IDs.** Exact-ID selection is ambiguous if two
   approvals share an ID. Relay derives approval IDs from idempotent event IDs
   in [`app/server.js`](../../app/server.js), so persisted duplicates are
   unreachable. The command rejects such state, and S16 makes that result
   observable instead of leaving array-order behavior to the Builder.
4. **Output naming and byte determinism.** The seed named `approvalId`,
   `jobId`, and `status` but did not specify key order, whitespace, or line
   ending. Resolved as the frozen key order, compact `JSON.stringify`, and one
   final LF, with byte-exact expectations for all four statuses.
5. **Exact lookup semantics.** “Exact ID” did not state whether case folding,
   trimming, or normalization was forbidden. Resolved as JavaScript strict
   string equality over the literal argument; the uppercase and trailing-space
   unknown IDs distinguish those alternatives.
6. **Sensitive-field proof.** The seed names private field categories but no
   sentinels. Fixture A gives each category a `-MUST-NOT-LEAK` literal, and
   Fixture B embeds malformed-state content; exact stream checks make leakage
   testable.
7. **Unreadable input portability.** Permission-denial fixtures are unreliable
   under privileged users. All OS read failures share one frozen result; an
   absent path and a directory path are the two portable representatives.
8. **Cross-ticket file ownership.** A grep of every Markdown ticket found no
   other declaration of `approval-state.js` or
   `approval-state.test.js`. T-180 and T-183 describe related approval
   inspectors but own distinct paths. The concurrently leased T-184 and T-185
   branches were inspected from `origin/ticket/T-184` and
   `origin/ticket/T-185`; they own distinct event and job-progress paths.
9. **Protected source and global text.** Inspection of the associated
   approval-detail seam and all tracked tests found no source boundary
   affecting the new file. The pinned readiness script accepted the ticket and
   every new shell-visible literal, so no `Protected-Test-Conflicts`
   declaration or fixture-seam edit is required.
10. **Topology, lifecycle, generated values, and external effects.** This is a
    local file-to-stdout command with isolated temporary fixtures and no
    database or network path. Auth, cookies, CORS, deployment domains,
    generated values, dependent rows, UI selectors, and external sends do not
    apply.
