## Spec'd description

Add `app/tools/outbox-receipt.js`, a zero-dependency Node 18+ command that reads
one persisted Relay state file while the service is offline and selects one
sandbox outbox receipt by exact approval ID. It emits only the stored
`approvalId` and `sentAt`. This gives an operator a deterministic receipt
lookup without starting Relay, changing state, or exposing the recipient,
subject, body, event payloads, job errors, approval content, or unrelated
state.

Product-doc sources:

- [`SPEC.md` behavior 4](../../SPEC.md#behavior-spec) defines an approved
  allowlisted send as a sandbox outbox record.
- [`SPEC.md` behaviors 6-7](../../SPEC.md#behavior-spec) define persisted
  on-disk state and the outbox collection this command reads offline.
- [`SPEC.md` conformance cases 5-7](../../SPEC.md#test-cases-the-conformance-suite)
  require sends to appear only after approval, blocked sends not to appear,
  and persisted work not to duplicate across restart.
- [`SPEC.md` known modeling limitation](../../SPEC.md#known-modeling-limitation)
  establishes that Relay's receipt is the persisted in-process outbox record,
  not evidence of real delivery.
- The current [`app/server.js` durable-state model](../../app/server.js)
  establishes the stored receipt fields and approval-ID link.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps the app
  zero-dependency, and [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

The command is a read-only projection over the existing state file. It does
not start the service, approve or reject an action, send a message, write an
outbox record, or change the server, persisted schema, worker, package
manifest, dependencies, UI, or Factory controls.

### Command-line interface and errors

- Repository-root invocation is exactly
  `node app/tools/outbox-receipt.js <state-file> <approval-id>`.
- Exactly two positional arguments are accepted. The state path is read
  directly; acceptance tests use absolute temporary paths.
- Zero, one, or three positional arguments produce exit code `2`, empty
  stdout, and exactly this single LF-terminated stderr line:

  ```text
  usage: node app/tools/outbox-receipt.js <state-file> <approval-id>
  ```

- The command reads `<state-file>` directly as UTF-8. Any read failure,
  including an absent path, a directory in place of a regular file, or an OS
  read denial, produces exit code `1`, empty stdout, and exactly:

  ```text
  outbox-receipt: cannot read state file
  ```

- Bytes rejected by `JSON.parse` produce exit code `1`, empty stdout, and
  exactly:

  ```text
  outbox-receipt: state file is not valid JSON
  ```

- A parsed value that fails the frozen structural rules produces exit code
  `1`, empty stdout, and exactly:

  ```text
  outbox-receipt: invalid Relay state
  ```

- A valid state with no outbox item whose stored `approvalId` is strictly
  equal to the supplied `<approval-id>` produces exit code `1`, empty stdout,
  and exactly:

  ```text
  outbox-receipt: outbox receipt not found
  ```

- Validation precedence is argument count, read, JSON parse, complete
  structural validation, then receipt lookup.
- Errors never contain the state path, approval ID, OS error, parser text,
  input bytes, stack trace, event content, job content, approval content,
  recipient, subject, body, or a second line. Every displayed error is
  terminated by exactly one LF.
- No path is written, renamed, deleted, chmodded, or created.

### Structurally valid state and successful output

For this command, structurally valid state is a non-null, non-array JSON object
with own `events`, `jobs`, `approvals`, and `outbox` properties whose values
are arrays.

Every `outbox` element must be a non-null, non-array object with these own
properties:

- non-empty string `approvalId`; and
- non-empty string `sentAt`.

Outbox approval IDs must be pairwise distinct. Contents of `events`, `jobs`,
and `approvals`, additional top-level properties, and additional outbox
properties are opaque to structural validation. In particular, `to`,
`subject`, and `body` may be present but are never copied to output. `sentAt`
is copied as stored without date parsing or normalization.

The lookup uses exact, case-sensitive JavaScript string equality and does not
trim, normalize, decode, or case-fold either ID. Success exits `0`, writes
zero stderr bytes, and writes one compact JSON object plus exactly one LF. Its
only keys, in order, are:

```json
{"approvalId":<stored approvalId>,"sentAt":<stored sentAt>}
```

No endpoint, HTTP request or response shape, route, UI selector, or global
page-shell text is introduced.

## Ambiguity log

1. **Receipt identity and safe output.** The seed names exact approval-ID
   lookup and exactly `approvalId` and `sentAt` but does not freeze
   serialization. [`SPEC.md` behavior 4](../../SPEC.md#behavior-spec) and the
   current [`app/server.js` outbox write](../../app/server.js) identify those
   as the non-message receipt fields. Resolved as the exact two-key compact
   object above, with stored values copied unchanged.
2. **Meaning of structurally valid.** The product has no general state-file
   validator. Resolved narrowly: validate all four collections, then every
   outbox field needed for exact lookup and output; treat unrelated
   collections, message fields, and additive fields as opaque.
3. **Duplicate receipt IDs.** The docs do not state a generic duplicate-row
   policy. The current server derives one approval ID per event and refuses a
   second approval execution after status leaves `pending`, while conformance
   case 7 requires no duplicate send after restart. Duplicate outbox
   `approvalId` values are therefore invalid rather than selected by array
   order.
4. **Exact lookup and errors.** The seed does not specify normalization, error
   text, exit codes, or precedence. No entry in
   [`factory/rulings.md`](../rulings.md) addresses offline receipt
   inspection. Resolved by the shipped offline-command convention: strict
   case-sensitive equality, usage exit `2`, operational exits `1`, fixed
   path-independent lines, and the frozen precedence above.
5. **Sensitive-data boundary.** “Without printing message contents” does not
   provide test values for every prohibited field. Fixture A gives selected
   and unselected receipt message fields and every related collection a
   distinct `-MUST-NOT-LEAK` token; exact stream checks make leakage
   mechanically observable.
6. **Read-only and self-termination proof.** Resolved with explicit `5_000` ms
   child timeouts, error and signal checks, repeated invocation,
   byte/stat/directory-entry comparisons, and the exact production module/API
   boundary. No service or network module is admitted.
7. **Cross-ticket file ownership.** Repository-wide ticket grep found no other
   declaration of either T-187-owned path. The other concurrently leased
   branches T-188 and T-189 were inspected with `git show`; they own distinct
   job-link and approval-timestamp paths. Related in-flight T-181 has an
   equivalent receipt-inspection goal but owns the distinct
   `outbox-inspect.js` pair. There is no file-boundary conflict.
8. **Protected source and global text.** The declared
   `app/tests/outbox-detail.test.js` seam and all tracked tests contain no
   static boundary for the new file. The pinned readiness check accepted
   every fixed shell-visible literal and output property name, so no
   protected-test conflict declaration or fixture-seam expansion is required.
9. **Topology, lifecycle, generated values, and external effects.** This is an
   offline local file read with isolated literal temporary fixtures and no
   database or network path. Auth, cookies, CORS, origins, credentials,
   preview deployment, generated values, dependent rows, UI selectors, and
   external sends do not apply. `External: no` remains correct.

Findings from this pass:

1. `sentAt` is frozen as "copied as stored without date parsing or
   normalization", but every fixture `sentAt` is already canonical ISO-8601, so
   an implementation that round-trips through `new Date(value).toISOString()`
   satisfies AC1 byte-for-byte. Non-blocking: `app/server.js` only ever writes
   `new Date().toISOString()`, so no reachable product state distinguishes the
   two implementations today.
   SPEC-WARN: add one valid fixture whose stored `sentAt` is a non-canonical
   string (for example `2026-08-23T12:00:01Z`) and assert it is echoed
   unchanged.
2. The uniqueness rule is stated over the whole outbox, but S19's duplicate
   pair is also the looked-up ID, so an implementation that rejects duplicates
   only when they equal `<approval-id>` passes AC6. Non-blocking: the
   ambiguity resolved in ambiguity-log entry 3 — which of two identical IDs
   would be returned — is exactly the case S19 covers.
   SPEC-WARN: add a structural-invalid fixture whose duplicated `approvalId`
   differs from the supplied lookup ID.
3. Opacity of `events`, `jobs`, and `approvals` contents is exercised only with
   object-shaped elements (Fixture A), so an implementation that over-validates
   those elements still passes. Non-blocking: over-validation fails closed to
   `invalid Relay state` and cannot leak or mutate.
   SPEC-WARN: extend Fixture B or add a valid fixture carrying scalar members
   in the three opaque collections.
4. Selection is proven only where the match is the last outbox element, so an
   implementation that returns the final rather than the first match passes.
   Non-blocking: uniqueness is enforced structurally, so at most one match can
   exist in a valid state.
   SPEC-WARN: have one valid fixture place the matching receipt at index `0`.
5. The contract names an OS read denial as a `cannot read state file` case; AC4
   exercises only the absent path and the directory-in-place permutations.
   Non-blocking: these are equivalent read failures under the grouping rule,
   and a chmod-based case is unreliable when tests run as root in CI.
   SPEC-WARN: leave the grouping as is and record the denial permutation as
   deliberately out of scope in the contract text.
