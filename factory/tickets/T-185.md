## Spec'd description

Add `app/tools/job-progress.js`, a zero-dependency Node 18+ command that reads
one persisted Relay state file without starting the service, selects one job by
case-sensitive exact ID, and writes only that job's safe lifecycle progress:
`jobId`, `status`, cumulative `attempts`, and `retries`. This gives an operator
a deterministic offline progress check while withholding `eventId`,
`attemptsSinceRetry`, `lastError`, event payloads, approval content, and outbox
content. The command is read-only and does not change retry behavior, the
persisted schema, the server, or the UI.

### Command interface

- Invocation is exactly
  `node app/tools/job-progress.js <state-file> <job-id>`.
- Exactly two user-supplied arguments are accepted. Any other arity exits `2`,
  writes no stdout, writes exactly
  `usage: node app/tools/job-progress.js <state-file> <job-id>\n` to stderr,
  and reads no state file.
- After arity validation, the command synchronously reads `<state-file>` as
  UTF-8, parses it as JSON, validates the progress-relevant Relay structure
  below, and selects the one job whose stored `id` is case-sensitively equal to
  `<job-id>`. Whitespace and object-key order in the input are not significant.
- Success exits `0`, writes no stderr, and writes one compact JSON object
  followed by one LF to stdout. The object has exactly four keys in this order:
  `jobId`, `status`, `attempts`, `retries`. `jobId` copies the stored job's
  `id`; the other values copy the same-named stored fields without
  transformation.
- The exact success shape is
  `{"jobId":<string>,"status":<"pending"|"done"|"dead">,"attempts":<nonnegative integer>,"retries":<nonnegative integer>}`.
  No `eventId`, `attemptsSinceRetry`, `lastError`, event, approval, outbox, or
  other input field is emitted.
- If the valid state has no exact ID match, the command exits `1`, writes no
  stdout, and writes exactly `job-progress: no such job\n` to stderr. This
  lookup error does not include the supplied ID.
- The command computes its result in memory and exits. It does not import,
  require, or start `app/server.js`; open a socket; issue a request; or write,
  rename, delete, chmod, or create any path.

### Input validation and error precedence

A progress-valid Relay state is a parsed, non-null, non-array JSON object with
exactly four own properties: `events`, `jobs`, `approvals`, and `outbox`, each
an array. Entries in `events`, `approvals`, and `outbox` are not validated
because this command never consumes them. Every `jobs` element must be a
non-null, non-array object with:

- a non-empty string `id`;
- a non-empty string `eventId`;
- `status` exactly one of `pending`, `done`, or `dead`;
- integer `attempts`, `retries`, and `attemptsSinceRetry`, each greater than or
  equal to zero; and
- `lastError` equal to `null` or a string.

Job IDs must be unique across the `jobs` array. Unconsumed additional fields on
a job are allowed and ignored. These rules validate only the persisted
structure needed to identify one job and return trustworthy progress counters;
they do not migrate or repair state.

After arity validation, failures are classified in this order:

1. Any filesystem read failure, including a nonexistent path or a path that is
   not a readable regular file, exits `1`, writes no stdout, and writes exactly
   `job-progress: state file is unreadable\n` to stderr.
2. Readable bytes rejected by `JSON.parse` exit `1`, write no stdout, and write
   exactly `job-progress: state file is not valid JSON\n` to stderr.
3. Parsed JSON that fails the progress-valid structure exits `1`, writes no
   stdout, and writes exactly
   `job-progress: state file has invalid Relay state\n` to stderr.
4. Only after all state validation succeeds is the exact-ID lookup performed;
   an absent ID has the frozen `job-progress: no such job\n` result above.

No error includes an input path, supplied ID, operating-system error, parser
text, stack trace, or state content.

   `app/server.js` job lifecycle: cumulative attempts and retry count are
