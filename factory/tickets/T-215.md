## Spec'd description

Add `app/tools/approval-status-count.js`, a zero-dependency CommonJS command
that reads one persisted Relay state file while Relay is offline, validates the
complete stored approval collection, and counts approvals whose stored
`status` is strictly equal to one operator-supplied `<status>`. It emits only
`{"approvalsWithStatus":<count>}`, giving an operator status cardinality
without starting Relay, changing durable state, approving or rejecting an
action, creating an outbox receipt, performing a real send, or exposing the
supplied status, approval identities, job links, actions, reasons, proposal
timestamps, events, jobs, outbox records, or unrelated state.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/approval-status-count.js <state-file> <status>`.
- Exactly two user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not read or create a candidate
  state path:

  ```text
  usage: node app/tools/approval-status-count.js <state-file> <status>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  approval-status-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  approval-status-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  approval-status-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied status, OS error, parser text, input bytes, stack
  trace, approval ID, job link, action, reason, proposal timestamp, event
  field, job field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.
  For the directory fixture, the frozen observable is the exact command
  envelope above, not any errno, error class, or operating-system text.

### Structurally valid state, exact match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string own properties `id`, `jobId`, and `proposedAt`;
- an own `status` property exactly equal to `pending`, `sent`, `rejected`, or
  `blocked_recipient`;
- an own `action` property that is a non-null, non-array object with own `to`,
  `subject`, and `body` properties; and
- either no own `reason` property, or an own `reason` whose value is `null` or
  a string, including the empty string.

Approval IDs must be pairwise distinct across the complete array. The values
of `action.to`, `action.subject`, and `action.body` are opaque. Additional
action and approval properties are allowed and ignored. Event, job, and outbox
elements are wholly opaque; only the fact that their top-level collections are
arrays is validated. A `jobId` need not resolve to a stored job. No
relationship is imposed among `status`, `action`, `proposedAt`, and `reason`.

The command validates the complete approval array and ID uniqueness before
counting. An approval contributes one only when
`approval.status === <status>` using case-sensitive JavaScript string
equality. The command does not trim, case-fold, decode, or Unicode-normalize
either string. Both operands are strings after structural validation and CLI
argument construction, so type coercion cannot create an additional matching
case. The supplied argument need not be a member of the stored status enum;
any supplied string with no exact match, including `Pending`, ` pending`,
fullwidth `ｐｅｎｄｉｎｇ`, and `""`, is a successful query with count zero.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"approvalsWithStatus":<nonnegative integer count>}
```

`approvalsWithStatus` is the number of elements in the validated `approvals`
array whose stored `status` matches the supplied status exactly. The supplied
status is not echoed. No stored approval ID, `jobId`, action value, reason,
status, proposal timestamp, additional approval field, event, job, outbox, or
top-level metadata value is emitted.

## Ambiguity log

   field-matching convention in
   [`approval-recipient-count`](../../app/tools/approval-recipient-count.js):
   use case-sensitive JavaScript strict equality without trimming, case
   folding, decoding, or Unicode normalization. Direct literals `Pending`,
   ` pending`, and `ｐｅｎｄｉｎｇ` make those transformations observable.

   The stored approval must use the exact enum, but the reconciled ticket

   two-argument query therefore proceeds through state validation and returns
   a count, including an empty argument.

   structural validation requires every stored status to be a string and
   command-line arguments are strings. The strict comparison is frozen, and
   the contract does not invent an invalid numeric status as a successful
   fixture merely to distinguish equivalent operators on two strings.

   one `approvalsWithStatus` integer and redacted status values. Resolved by
