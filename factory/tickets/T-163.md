## Spec'd description

Specify the additive, read-only `GET /api/jobs/:id` detail interface so a
caller can retrieve one durable Relay job together with the event that created
it, without downloading and filtering the aggregate `GET /api/state`
document.

The requested interface and its protected acceptance test are already present
on the protected baseline as the delivered result of T-167. Consequently,
T-163 version 1 is a preservation-and-certification unit: it freezes the exact
observable interface and requires no duplicate route, duplicate test, or
application-file edit while the baseline artifacts remain conformant. If a
later baseline no longer conforms, version 1 is not authority to repair it;
T-163 must return to Ready and receive a new contract version with explicit
repair ownership.

### HTTP interface

- Method and path: `GET /api/jobs/:id`, where `:id` is exactly one non-empty,
  URL-parsed path segment.
- Lookup: select the stored `state.jobs` entry whose string `id` exactly
  equals `:id`, then select the stored `state.events` entry whose string `id`
  exactly equals the selected job's `eventId`.
- Existing job: return HTTP `200`, header
  `Content-Type: application/json`, and a parsed JSON object exactly equal to
  `{"job":<complete stored job>,"event":<complete stored related event>}`.
  Neither stored object is projected, renamed, normalized, defaulted, or given
  an additional field.
- Unknown job: return HTTP `404`, header
  `Content-Type: application/json`, and parsed JSON exactly equal to
  `{"error":"no such job"}`.
- Both outcomes are read-only: they do not mutate any in-memory collection,
  invoke persistence, or change `<DATA_DIR>/state.json`.
- A manually corrupted state containing a job with no related event is outside
  this contract. Relay-created state persists an accepted event and its job
  together.
- No UI selector or accessible name is introduced. Authentication, cookies,
  CORS, cross-origin behavior, credentials, domains, and preview-deploy
  topology are unchanged; requests use the existing Relay server origin.

### Frozen Fixture A

`app/tests/job-detail.test.js` creates a fresh temporary `DATA_DIR` and writes
the following complete parsed JSON value to `<DATA_DIR>/state.json` before
starting the real server:

```json
{
  "events": [
    {
      "id": "event-job-detail",
      "type": "meeting",
      "payload": {
        "failTimes": 99
      },
      "receivedAt": "2026-07-28T12:00:00.000Z"
    }
  ],
  "jobs": [
    {
      "id": "job-event-job-detail",
      "eventId": "event-job-detail",
      "status": "dead",
      "attempts": 3,
      "lastError": "simulated failure on attempt 3",
      "retries": 0,
      "attemptsSinceRetry": 3
    }
  ],
  "approvals": [],
  "outbox": []
}
```

The existing-resource ID is exactly `job-event-job-detail`. The unknown ID is
the literal `job-missing`, which is byte-distinct from
`job-event-job-detail`; it is not produced by casing, normalization, or
mutation. Tests compare parsed JSON values, so object-property order and
insignificant serialized whitespace are not interface requirements.

No identifier, counter, sequence, or timestamp is generated during fixture
setup: all values above are written literally before process start. The dead
job is not selected by the pending-only worker, and `WORKER_MS=60000` further
bounds worker activity during each acceptance case.

### Fixture lifecycle

Each of the three existing acceptance cases owns a distinct loopback port
(`4761`, `4762`, or `4763`) and performs this closed lifecycle:

1. create a fresh temporary directory;
2. write Frozen Fixture A to its `state.json`;
3. start `app/server.js` with that directory as `DATA_DIR`,
   `WORKER_MS=60000`, and `ALLOWLIST=test@example.com`;
4. wait until `GET /health` succeeds before issuing acceptance requests;
5. consume each response body;
6. send `SIGKILL`, await the child process exit, and recursively remove the
   temporary directory in `finally`.

There is no database and no parent/child table cleanup. No setup state is
shared between cases, so no reset helper or cascading cleanup edit is needed.
The ports are distinct from the current suite's other fixed blocks
(`4719`, `4721-4722`, `4731-4733`, `4741-4745`, `4751-4756`,
`4771-4773`, and `4779`).

## Ambiguity log

1. **What is the exact successful response envelope?** `SPEC.md` defines the
   durable records but not a job-detail envelope. Resolved by the prior
   [`factory/rulings.md`](../rulings.md) decision as exactly
   `{"job":<stored job>,"event":<stored related event>}`.
2. **How is the related event selected?** Resolved from
   [`SPEC.md` behavior 2](../../SPEC.md#behavior-spec), the ruling, and the
   durable model: the job's `eventId` must exactly equal the event's `id`.
3. **The requested route and test already exist; should T-163 duplicate
   them?** No. Current protected state contains the exact T-167 route and
   acceptance artifacts, while the ticket freezes the same product behavior.
   Duplicating either would add no behavior and would conflict with the
   zero-dependency, protected-test, and narrow-ownership rules. Version 1
   therefore freezes an empty T-163 application diff; any discovered mismatch
   requires a new version.
4. **How is read-only behavior observable?** Resolved from
   [`SPEC.md` behavior 6-7](../../SPEC.md#behavior-spec): compare both the
   public aggregate state value and exact persisted file bytes before and
   after the success and missing-resource reads.
5. **How is an orphaned job handled?** Product docs specify Relay-created
   state, in which event acceptance persists the event and job together. They
   do not define manually corrupted state recovery, so orphan behavior is
   explicitly excluded rather than invented.
6. **Do sibling or leased tickets overlap file ownership?** A scan of
   `factory/tickets/` found historical detail tickets sharing
   `app/server.js`, plus T-167's already-merged use of the exact job-detail
   test path. Every other currently leased branch was inspected:
   `origin/ticket/T-164` and `origin/ticket/T-165` declare
   `app/server.js` with distinct protected test paths, while
   `origin/ticket/T-170`, `T-171`, and `T-172` own distinct `app/tools/` and
   test files. The existing
   [`concurrent-ownership ruling`](../rulings.md) permits the additive detail
   routes to share `app/server.js` with serialized protected publication.
   T-163 version 1's empty application diff creates no live conflict.
7. **Do fixture setup or ports conflict with concurrent tests?** No setup edit
   is authorized. The protected job-detail cases use `4761-4763`, which are
   distinct from every current suite block and from the protected files named
   by the other leased tickets.
8. **Does this require deploy, authentication, or external-send topology?**
   No. It is an unauthenticated, same-origin read over the existing server. It
   changes no domain, credential, cookie, SameSite, CORS, or preview behavior
   and cannot enter an approval/send path. `External: no` remains correct and
   no `external` label is required.
