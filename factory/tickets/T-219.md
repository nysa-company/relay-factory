## Spec'd description

Add `app/tools/event-payload-key-count.js`, a zero-dependency CommonJS command
that reads one persisted Relay state file while the service is offline,
validates the complete stored event collection, and counts events whose
payload is a JSON object with one exact operator-supplied own key. It reports
only `{"eventsWithPayloadKey":<count>}`, allowing an operator to inspect the
durable collection without starting Relay, changing state, coercing payloads,
walking nested values, consulting object prototypes, or exposing the supplied
key or any stored content.

  with `{id, type, payload}` and idempotency by exact event ID.

  persisted state file Relay's durable source, which this command reads

### Command-line interface and failure precedence

  `node app/tools/event-payload-key-count.js <state-file> <key>`.
- Exactly two user-supplied positional arguments are accepted. The second may
  be the empty string. Any other arity exits `2`, writes zero stdout bytes,
  writes exactly the following single LF-terminated line to stderr, and does
  not read or create a candidate state path:

  ```text
  usage: node app/tools/event-payload-key-count.js <state-file> <key>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  event-payload-key-count: cannot read state file
  ```

  and write exactly:

  ```text
  event-payload-key-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  event-payload-key-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied key, OS error, parser text, input bytes, stack trace,
  event field, job field, approval field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable

### Structurally valid state, own-key match, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `events` element must be a non-null, non-array object with non-empty
string own properties `id`, `type`, and `receivedAt`. Event IDs must be
pairwise distinct across the complete array. Event `payload` and all
additional event fields are structurally opaque: `payload` may be absent or
may hold any JSON value. Job, approval, and outbox elements are wholly opaque;
only the fact that their top-level collections are arrays is validated.

The command validates the complete event array and ID uniqueness before
counting. An event contributes one only when its `payload` value is a non-null,
non-array JSON object and that object has an own property whose key is exactly
the supplied `<key>`. Matching is case-sensitive and uses the supplied string
without trimming, parsing, decoding, case-folding, Unicode normalization, or
other coercion. It examines only the payload object's immediate own keys: it
does not traverse nested values or consult the object's prototype. Missing,
`null`, array, string, number, and boolean payloads are valid but contribute
zero for every key. The empty string is a valid supplied key and matches an
own empty-string property. No match is a successful query, not an error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"eventsWithPayloadKey":<nonnegative integer count>}
```

The count is the number of events in the validated `events` array that satisfy
the frozen predicate. The supplied key is not echoed. No stored event ID,
type, payload key or value, `receivedAt`, additional event field, job,
approval, outbox, or metadata value is emitted.

## Ambiguity log

1. **What counts as a payload key?** The backlog text requires an exact own
   property with no coercion, traversal, or prototype lookup. Combined with
   [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec), which names `payload`
   but does not constrain its JSON value, this resolves to immediate own keys
   on non-null, non-array JSON objects only. Missing, null, primitive, and
   array payloads remain valid opaque event content but do not match; Fixture A
   freezes each observable representative.
2. **Are `constructor`, inherited names, and the empty string valid queries?**
   Exact own-key semantics make an owned `constructor` and an owned empty key
   match, while inherited `constructor` or `toString` do not. Arity is the only
   argument validation, matching the shipped
