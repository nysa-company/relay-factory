## Description

Add a read-only `GET /api/events/:id` detail route to the zero-dependency Relay
API. It gives callers one stored event together with the one durable job created
for that event, without requiring them to retrieve the aggregate
`GET /api/state` document.

This is the focused read surface for the event and job relationship defined by
[`SPEC.md` behavior 1-2](../../SPEC.md#behavior-spec), over state persisted
under [behavior 6](../../SPEC.md#behavior-spec), and extends the API visibility
described by [behavior 7](../../SPEC.md#behavior-spec). The exact success
envelope and the concurrent `app/server.js` ownership decision come from the
dated [detail-route ruling](../rulings.md). The implementation remains inside
the zero-dependency app boundary in
[`AGENTS.md`](../../AGENTS.md#boundaries).

## Acceptance criteria

1. With the frozen `evt-detail-001` state fixture loaded, `GET
   /api/events/evt-detail-001` returns HTTP `200`, `Content-Type:
   application/json`, and the exact success body in Frozen contract version 1;
   the body has only the top-level keys `event` and `job`, and
   `job.eventId === event.id === "evt-detail-001"`.
2. With the same fixture loaded, `GET /api/events/evt-detail-missing` returns
   HTTP `404`, `Content-Type: application/json`, and the byte-for-byte body
   `{"error":"no such event"}`.
3. After one successful detail request and one unknown-event request, both the
   parsed `GET /api/state` response and the bytes of `DATA_DIR/state.json`
   equal their respective pre-request snapshots.
4. The acceptance-test commit adds only
   `app/tests/event-detail.test.js` and precedes every implementation commit;
   implementation commits modify only `app/server.js`. The branch adds no
   dependency metadata changes and no Factory-control changes beyond this
   Planner-owned ticket contract and the already-pinned route plan.

## Frozen contract — version 1

### Endpoint

- Method and path: `GET /api/events/:id`.
- Route match: pathname `^/api/events/([^/]+)$`; `:id` is matched exactly
  against `state.events[].id`. A request body is neither required nor read.
- Existing event: find the event whose `id` equals `:id`, then find the stored
  job whose `eventId` equals that event's `id`. Return HTTP `200` through the
  existing JSON response helper with exactly:

  ```json
  {"event":<stored event>,"job":<stored related job>}
  ```

  The top-level object has exactly the keys `event` then `job`, with no
  `ok`, `id`, or other envelope fields. Both nested records are returned
  verbatim from durable state; no nested field is omitted, renamed, derived,
  or added by this route.
- Unknown event: when no `state.events[]` record has `id === :id`, return HTTP
  `404` through the existing JSON response helper with exactly:

  ```json
  {"error":"no such event"}
  ```

- Both outcomes have `Content-Type: application/json`. Neither outcome
  mutates in-memory state, calls `persist()`, changes `DATA_DIR/state.json`, or
  triggers worker, approval, outbox, or external-send behavior.
- The product invariant in
  [`SPEC.md` behavior 1-2](../../SPEC.md#behavior-spec) supplies exactly one
  related job for every accepted event. Behavior for a manually corrupted
  state file containing an event without its job is outside this ticket.

### Acceptance fixture

`app/tests/event-detail.test.js` creates an isolated temporary `DATA_DIR` and
writes the following JSON value to `DATA_DIR/state.json` before starting the
real `app/server.js`. The dead job keeps the fixture stable without relying on
worker timing.

```json
{
  "events": [
    {
      "id": "evt-detail-001",
      "type": "meeting",
      "payload": {
        "to": "test@example.com",
        "subject": "Detail fixture"
      },
      "receivedAt": "2026-07-28T12:00:00.000Z"
    }
  ],
  "jobs": [
    {
      "id": "job-evt-detail-001",
      "eventId": "evt-detail-001",
      "status": "dead",
      "attempts": 3,
      "lastError": "simulated failure on attempt 3",
      "retries": 0,
      "attemptsSinceRetry": 3
    }
  ],
  "approvals": [],
  "outbox": []
}
```

For that fixture, the exact raw success body is:

```json
{"event":{"id":"evt-detail-001","type":"meeting","payload":{"to":"test@example.com","subject":"Detail fixture"},"receivedAt":"2026-07-28T12:00:00.000Z"},"job":{"id":"job-evt-detail-001","eventId":"evt-detail-001","status":"dead","attempts":3,"lastError":"simulated failure on attempt 3","retries":0,"attemptsSinceRetry":3}}
```

The acceptance suite uses localhost port `4761`, the existing default
allowlist `test@example.com`, and the unknown ID `evt-detail-missing`. It
captures both the parsed `/api/state` value and exact `state.json` bytes before
the detail requests, then compares both after the requests.

## Ambiguity log

- **Successful response envelope:** `SPEC.md` defines event intake, job
  creation, persistence, and aggregate state visibility, but not a detail
  response. The prior planning attempt correctly identified that
  “its stored event and related job” allowed incompatible envelopes. Resolved
  by the 2026-07-28
  [detail-route ruling](../rulings.md), which freezes exactly
  `{"event":<stored event>,"job":<stored related job>}`.
- **Related-job cardinality and malformed state:** the route needs one related
  job but the ticket did not define behavior for hand-edited state with no
  relation. Resolved from
  [`SPEC.md` behavior 1-2](../../SPEC.md#behavior-spec): every accepted event
  creates one job and duplicate delivery creates no second job. The contract
  covers valid product state; manually corrupted state is explicitly out of
  scope.
- **Meaning of read-only:** “does not change durable state” did not name an
  observable. Resolved from
  [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) and the current
  `DATA_DIR/state.json` persistence implementation by freezing both a parsed
  `/api/state` equality check and a byte-for-byte state-file equality check.
- **Cross-ticket file ownership:** the repository-wide sibling-ticket grep
  found repeated qualification tickets declaring `app/server.js`, and the
  currently leased T-167, T-168, and T-169 branches each declare that same
  Builder file. Their endpoint paths and Test-author files are distinct. The
  2026-07-28 [ruling](../rulings.md) explicitly permits these four additive
  detail routes to share ownership while protected publication remains
  serialized and each later branch refreshes from protected `main`.
- **Deploy and trust topology:** inspection of `app/server.js`,
  `Authentication-Seams: none`, and the requested read-only path found no
  cross-origin, authentication, cookie, CORS, credential, domain, or
  preview-deploy behavior to specify. The contract therefore freezes this as a
  same-origin, unauthenticated route with no topology changes.
- **External classification:** unlike approval execution, this route only
  reads event/job state. It cannot reach the outbox or perform a send, so the
  ticket does not receive the `external` label.
