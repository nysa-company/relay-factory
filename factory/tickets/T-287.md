## Description

Add a zero-dependency, read-only CommonJS command that counts persisted Relay
outbox entries whose approval and job reference an event with a supplied exact
type while Relay is offline.

## Acceptance criteria

1. `node app/tools/outbox-event-type-count.js <state-file> <event-type>` emits
   compact JSON containing exactly one `outboxEntriesForEventType` integer.
2. Type matching is exact and case-sensitive. Every outbox entry must
   reference exactly one valid approval, every referenced approval exactly one
   valid job, and every referenced job exactly one valid event; duplicate IDs,
   duplicate outbox references, and missing references are rejected before
   counting, and zero matches is valid.
3. Invalid arguments are rejected before file access. Unreadable, malformed,
   or structurally invalid state returns fixed redacted errors.
4. The command is offline, zero-dependency, deterministic, read-only, and
   self-terminating. Tests resolve fixtures from the test file, work from any
   current directory, use a five-second child timeout, and do not assume Git
   history depth.
5. Tests precede implementation. Targeted, full app, and immutability checks
   pass without dependency, server, schema, manifest, or Factory changes.

### State validation (exact algorithm, evaluated top to bottom; first
### violation makes the whole state invalid)

The state file must parse to a JSON object (not `null`, not an array) with
own properties `events`, `jobs`, `approvals`, `outbox`, each an array.

1. **Events** — walk `state.events` in order. Each element must be a plain
   object with own properties `id` (non-empty string), `type` (non-empty
   string), `receivedAt` (non-empty string). `id` must be unique across all
   events. Build a lookup `eventTypeById: id -> type`. Any other own
   properties on an event record are ignored/opaque.
2. **Jobs** — walk `state.jobs` in order. Each element must be a plain
   object with own properties `id` (non-empty string), `eventId` (non-empty
   string). `id` must be unique across all jobs. `eventId` must be a key of
   `eventTypeById` (i.e. reference a valid event from step 1). Build a
   lookup `jobEventTypeById: id -> eventTypeById[eventId]`. Any other own
   properties on a job record (e.g. `status`, `lastError`) are
   ignored/opaque.
3. **Approvals** — walk `state.approvals` in order. Each element must be a
   plain object with own properties `id` (non-empty string), `jobId`
   (non-empty string), `status` (string, one of exactly `"pending"`,
   `"sent"`, `"rejected"`, `"blocked_recipient"`). `id` must be unique
   across all approvals. `jobId` must be a key of `jobEventTypeById` (i.e.
   reference a valid job from step 2, which already resolves to a valid
   event). Build a lookup `approvalEventTypeById: id ->
   jobEventTypeById[jobId]`. Any other own properties (e.g. `action`,
   `proposedAt`, `reason`) are ignored/opaque.
4. **Outbox** — walk `state.outbox` in order. Each element must be a plain
   object with own properties `to`, `subject`, `body` (any value, presence
   only), `approvalId` (non-empty string), `sentAt` (non-empty string).
   `approvalId` must be a key of `approvalEventTypeById` (i.e. reference a
   valid approval from step 3, which already resolves to a valid job and
   event). No two outbox elements may share the same `approvalId` (at most
   one outbox entry per approval). Any other own properties are
   ignored/opaque.

If every step passes, the state is valid. `outboxEntriesForEventType` is the
count of outbox elements whose resolved `approvalEventTypeById[approvalId]`
is exactly (case-sensitive, `===`) equal to the supplied `<event-type>`
argument. Zero matches is a valid, successful `0` result, not an error.
