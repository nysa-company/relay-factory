## Spec'd description

Add `app/tools/event-timestamp.js`, a zero-dependency Node 18+ command that
reads one persisted Relay state file while the service is offline and selects
one event by case-sensitive exact ID. It writes only `eventId` and `createdAt`;
the operator-frozen `createdAt` output value is copied byte-for-byte from the
selected event's stored `receivedAt` field. This gives operators a
deterministic timestamp lookup without starting Relay, changing persisted
state, or exposing payloads, job errors, approval content, outbox content, or
unrelated state.

Product-doc sources:

- [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec) defines exact event-ID
  intake and one accepted event per ID.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) defines the persisted
  state file as Relay's durable state, which this command reads without
  participating in startup or recovery.
- [`SPEC.md` behavior 7](../../SPEC.md#behavior-spec) makes events an
  operator-visible collection, while
  [`SPEC.md` conformance cases 1, 2, and 7](../../SPEC.md#test-cases-the-conformance-suite)
  require accepted events to remain visible, duplicate IDs not to duplicate
  work, and persisted work to survive restart.
- The current [`app/server.js` durable-state model](../../app/server.js)
  establishes the four stored collections and writes each accepted event with
  `id`, `type`, `payload`, and `receivedAt`; its `receivedAt` initializer is
  `new Date().toISOString()`.
- The shipped
  [`event-metadata` command](../../app/tools/event-metadata.js) and its
  [acceptance suite](../../app/tests/event-metadata.test.js) establish the
  existing zero-dependency, exact-ID, redacted, read-only offline-command
  convention for the same persisted event collection.
- [`AGENTS.md` Boundaries](../../AGENTS.md#boundaries) keeps `app/`
  zero-dependency, and [`AGENTS.md` Verification](../../AGENTS.md#verification)
  defines the later full-suite and immutability checks.

No endpoint, UI, persisted schema, server behavior, package, dependency,

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/event-timestamp.js <state-file> <event-id>`.
- Exactly two user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and performs no filesystem access:

  ```text
  usage: node app/tools/event-timestamp.js <state-file> <event-id>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  event-timestamp: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  event-timestamp: state file is not valid JSON
  ```

- A parsed value that fails the frozen timestamp-valid structure exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  event-timestamp: invalid Relay state
  ```

- A timestamp-valid state with no event whose stored `id` is strictly equal to
  `<event-id>` exits `1`, writes zero stdout bytes, and writes exactly:

  ```text
  event-timestamp: event not found
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then exact event lookup.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, event ID, OS error, parser text, input bytes, stack trace,
  payload, job field, approval field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Timestamp-valid state, exact lookup, and successful output

A timestamp-valid state is a parsed non-null, non-array JSON object with own
`events`, `jobs`, `approvals`, and `outbox` properties whose values are arrays.
Additional top-level properties are allowed and ignored.

Every `events` element must be a non-null, non-array object with non-empty
string own properties `id` and `receivedAt`. Event IDs must be pairwise
distinct across the complete array. Event `type`, `payload`, and all additional
event fields are opaque. Job, approval, and outbox elements are wholly opaque;
only the fact that their top-level collections are arrays is validated.

The command validates the complete event array and ID uniqueness before
lookup. Lookup uses exact, case-sensitive JavaScript string equality. It does
not trim, case-fold, decode, or normalize either ID.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only keys, in this order, are:

```json
{"eventId":<selected stored id>,"createdAt":<selected stored receivedAt>}
```

`eventId` copies the selected event's stored `id`. The operator-frozen
`createdAt` key copies the same event's stored `receivedAt` string without
parsing, formatting, timezone conversion, or other transformation. No
`receivedAt`, `type`, `payload`, job, approval, outbox, metadata, or unrelated
event field is emitted.

## Ambiguity log

1. **What does `createdAt` mean when Relay stores `receivedAt`?** The
   operator-frozen ticket interface requires `createdAt`, while the current
   [`app/server.js`](../../app/server.js) event initializer and
   [`event-metadata` command](../../app/tools/event-metadata.js) expose the
   durable timestamp as `receivedAt`. Resolved by freezing `createdAt` as an
   output-only alias that copies the selected event's stored `receivedAt`
   string byte-for-byte. No persisted field is renamed or added.
2. **How exact is event selection?** Resolved from
   [`SPEC.md` behavior 1](../../SPEC.md#behavior-spec) and the current server's
   strict-ID lookup as case-sensitive JavaScript string equality. The direct
   literal `Event-alpha` makes case-folding observable, and duplicate stored
   IDs are invalid before lookup.
3. **What structure must an offline timestamp reader trust?** The product has
   no general-purpose state-file validator. Resolved narrowly from the four
   current collections in [`app/server.js`](../../app/server.js): require all
   four arrays, validate every event's two consumed fields and ID uniqueness,
   and leave unconsumed event fields and collection entries opaque. Fixture B
   makes opacity mechanically observable.
4. **How are failures classified without leaking input?** Raw OS and parser
   errors can reveal paths or content. Resolved using the shipped offline-tool
   convention: usage exit `2`, operational exits `1`, fixed single-line
   redacted errors, empty opposite streams, and precedence from arity through
   lookup.
5. **How are read-only, offline, and self-terminating claims proved?** Resolved
   with synchronous child invocations under a `5_000` ms timeout, exact file
   and directory fingerprints, repeated success, isolated teardown, and a
   production source boundary admitting only `node:fs` and `readFileSync`.
6. **Are fixture mutations or generated timestamps involved?** No invalid
   fixture is derived at runtime. The case-distinct lookup is an exact direct
   literal, all serialized fixtures are pairwise checked, and every expected
   timestamp is literal. The current server initializer explains the timestamp
   shape but is not run by the acceptance setup.
7. **Does fixture cleanup have hidden dependencies?** No database or service is
   started. Each test owns one temporary directory removed after its child
   exits, so there are no parent rows, sibling tables, foreign keys, or reset
   ordering.
8. **Do sibling or concurrently leased tickets overlap ownership?** A grep of
   all local `factory/tickets/*.md` declarations found no other owner of either
   T-190 path. The other active leased remote branches were inspected:
   T-191 owns the distinct `job-attempts` pair, and T-192 owns the distinct
   `approval-link` pair. No implementation-surface conflict exists.
9. **Do protected tests reject the new source boundary?** Direct inspection of
   `app/tests/event-metadata.test.js` and all tracked tests found only
   tool-specific source assertions. The new path and its sole `node:fs`
   specifier are admitted; no protected-test conflict or seam edit is needed.
10. **Does protected global text collide?** The pinned
    `ticket-readiness.py` check accepted every new shell-visible literal named
    in the criteria checklist. No accessible UI name is added.
11. **Are deployment, authentication, or external-send details applicable?**
    No. The complete topology is a local process reading one local path and
    writing stdout/stderr; there is no network, UI, credential, preview, or
    send path, so no `external` label is required.
12. **Does an existing operator ruling change the contract?**
