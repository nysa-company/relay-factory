## Spec'd description

Add one zero-dependency, read-only Node 18+ command,
`node app/tools/approval-job-link.js <state-file> <approval-id>`, that selects
one persisted approval by exact ID while Relay is offline and reports only the
approval ID, its stored job ID, the approval status, and the related job status.
If the approval exists but its stored job ID has no matching job, the report
preserves that job ID and emits `jobStatus: null`.

This gives an operator a deterministic approval-to-job lifecycle join without
starting Relay or exposing approval actions, rejection reasons, event payloads,
job errors, outbox content, or unrelated state.

### Command-line interface and errors

- Repository-root invocation:
  `node app/tools/approval-job-link.js <state-file> <approval-id>`.
- Exactly two positional arguments are accepted. Zero, one, three, or four
  arguments produce exit code `2`, empty stdout, and exactly this LF-terminated
  stderr line:

  ```text
  usage: node app/tools/approval-job-link.js <state-file> <approval-id>
  ```

- The command reads the named regular file directly as UTF-8. It does not
  import, require, spawn, or otherwise execute `app/server.js`; open an HTTP or
  other network listener; make an outbound request; or leave a timer or child
  process running.
- A read failure, including a nonexistent path, a directory in place of a
  file, or an OS read denial, produces exit code `1`, empty stdout, and
  exactly:

  ```text
  approval-job-link: cannot read state file
  ```

- Bytes rejected by `JSON.parse` produce exit code `1`, empty stdout, and
  exactly:

  ```text
  approval-job-link: state file is not valid JSON
  ```

- A parsed value that fails the frozen structural rules produces exit code
  `1`, empty stdout, and exactly:

  ```text
  approval-job-link: invalid Relay state
  ```

- A structurally valid state with no approval whose `id` exactly equals the
  supplied `<approval-id>` produces exit code `1`, empty stdout, and exactly:

  ```text
  approval-job-link: no such approval
  ```

- No error includes the input path, approval ID, OS error, parser text, input
  content, stack trace, or a second line. Every displayed line above ends with
  one LF byte.
- Validation precedence is argument count, read, JSON parse, structure, then
  approval lookup. No path is written, renamed, deleted, chmodded, or created.

For the argument-count cases, each invocation uses a fresh empty temporary
parent. The one-argument case supplies nonexistent `<tmp>/state-a.json`; the
three-argument case supplies that path, `appr-a`, and `extra-a`; the
four-argument case additionally supplies `extra-b`. The test requires the
parent's entry list to remain empty after each case.

### Valid state, selection, and report shape

For this command, a structurally valid state is a non-null, non-array JSON
object with own `events`, `jobs`, `approvals`, and `outbox` properties whose
values are arrays.

Every `approvals` element must be a non-null, non-array object with:

- a non-empty string `id`;
- a non-empty string `jobId`; and
- a string `status` equal to exactly one of `pending`, `sent`, `rejected`, or
  `blocked_recipient`.

Every `jobs` element must be a non-null, non-array object with:

- a non-empty string `id`; and
- a string `status` equal to exactly one of `pending`, `done`, or `dead`.

Contents of `events` and `outbox`, additional top-level keys, and additional
approval and job keys are opaque to structural validation. Approval actions,
rejection reasons, event payloads, job errors, counters, timestamps, and outbox
fields are never copied to output.

Select the approval whose stored `id` exactly equals `<approval-id>`. Select
the related job whose stored `id` exactly equals that approval's stored
`jobId`. Relay's persisted model derives unique approval and job IDs from an
idempotent event ID; duplicate approval or job IDs are outside this contract,
so no duplicate tie behavior is added.

For a related job, create a new object with keys in this exact order:

```json
{"approvalId":<stored approval id>,"jobId":<stored approval jobId>,"approvalStatus":<stored approval status>,"jobStatus":<stored related job status>}
```

If no job has the stored job ID, preserve `approvalId`, `jobId`, and
`approvalStatus` and set only `jobStatus` to JSON `null`. Status strings are
copied without casing, parsing, or normalization. Serialize the object with
compact `JSON.stringify` formatting and append exactly one LF byte. Success
exits `0` with empty stderr.

There are no endpoint paths, HTTP request or response shapes, UI routes, or UI
selectors in this contract.

## Ambiguity log

1. **Exact error protocol.** The seed required fixed privacy-safe errors but
   did not freeze their text, exit codes, or validation order. No entry in
   [`factory/rulings.md`](../rulings.md) addresses offline commands. Resolved
   as path-independent usage, read, parse, structure, and lookup outcomes,
   following the shipped offline-command convention.
2. **Meaning of structurally valid.** The product docs establish four
   persisted collections and the job and approval statuses but do not define a
   general-purpose state validator. Resolved narrowly: validate every
   collection as an array and only the approval and job fields this join
   selects or emits; treat unrelated contents and additive fields as opaque.
3. **Missing related job.** Relay normally creates an approval from a stored
   successful job, but the seed explicitly requires `jobStatus: null` when no
   job exists. The contract therefore preserves the approval's stored `jobId`
   and freezes only `jobStatus` as `null`; it does not reject or repair the
   state.
4. **Serialization details.** “Deterministic compact JSON” did not state key
   order or line termination. Resolved as the seed's field order, compact
   `JSON.stringify`, and one LF; status values are copied verbatim.
5. **Duplicate IDs.** Neither the seed nor product docs define duplicate
   selection. Relay derives approval and job IDs from an idempotent event ID,
   so duplicates are outside the persisted model rather than new behavior for
   this command.
6. **Sensitive-field proof.** The seed names private field categories but no
   sentinels. Fixture A gives each category a `-MUST-NOT-LEAK` value, and
   Fixture B embeds a malformed-state sentinel; byte-exact streams make
   leakage mechanically checkable.
7. **Unreadable input portability.** Permission-denial fixtures are unreliable
   under privileged users. All OS read failures share one result; an absent
   path and a directory path are the two portable representatives.
8. **Cross-ticket ownership and bounded concurrency.** A grep of every file
   under `factory/tickets/` found no other declaration of
   `approval-job-link.js` or `approval-job-link.test.js`. The other active
   worktrees are T-181 and T-182; `git show origin/ticket/T-181:factory/tickets/T-181.md`
   and the corresponding T-182 command show distinct outbox-inspect and
   event-job-link paths. Uncommitted contracts on another worktree remain
   outside what the required remote-branch check can observe.
9. **Protected source and global text.** The associated approval-detail seam
   and all tracked tests contain no source boundary affecting the new file.
   The pinned readiness script accepted all seven shell-visible literals, so
   no `Protected-Test-Conflicts` declaration or fixture-seam edit is needed.
10. **Topology, lifecycle, generated values, and external effects.** This is a
    local file-to-stdout command with isolated literal fixtures and no database
    or network path. Auth, cookies, CORS, deployment domains, counters,
    dependent rows, UI selectors, and external sends do not apply.

### Findings

1. **Blocking — a structurally valid state with empty collections is never
   exercised.** The contract accepts `events`, `jobs`, `approvals`, and
   `outbox` as arrays of any length, so
   `{"events":[],"jobs":[],"approvals":[],"outbox":[]}` is valid and any
   lookup against it must exit `1` with
   `approval-job-link: no such approval`. No criterion asserts this. AC1, AC2,
   and AC3 all use Fixture A, whose collections are non-empty, and every
   ticket fixture that does contain an empty array (S1-S21) expects
   `approval-job-link: invalid Relay state`. A Builder whose validator
   additionally requires a non-empty `approvals` or `jobs` array satisfies
   AC1-AC9 exactly while reporting `invalid Relay state` for a freshly started
   Relay state file — per `SPEC.md` behavior 6 and 7 the ordinary starting
   state — which is the wrong operator-visible outcome and the wrong exit
   branch. The sibling shipped commands pin this boundary explicitly
   (`app/tests/blocked-approvals.test.js` Fixture B). Add a frozen valid
   empty-collections fixture and a criterion fixing its exit code and stderr,
   or state in the contract that empty collections are rejected.

2. SPEC-WARN: no criterion asserts an output carrying `jobStatus` `"pending"`
   or `"dead"`, or `approvalStatus` `"sent"` or `"blocked_recipient"` —
   Fixture A contains `job-pending` and `job-dead` but no approval references
   them; add an `appr-sent` invocation and link one approval to a non-`done`
   job so the verbatim-copy rule is exercised across the lifecycle join the
   ticket is named for.

3. SPEC-WARN: `Fixture-Seams: app/tests/approval-detail.test.js` contradicts
   `Protected-Test-Conflicts: none`, the contract's "reference-only and is not
   edited", and AC9's unchanged-existing-tests requirement; set the field to
   `none`. Independent inspection confirms no conflict exists:
   `app/tests/approval-detail.test.js` has no allowlist, snapshot, or
   exact-source assertion; `app/tests/dead-jobs.test.js` and
   `app/tests/blocked-approvals.test.js` inspect only their own tool files; no
   tracked test enumerates `app/tools/` or `app/tests/`; and
   `app/tests/factory-contract.test.js` only pins
   `NONVISUAL_PATHS=app/tools/,app/tests/`, which already covers both new
   paths and confirms neither carries global-shell text.

4. SPEC-WARN: AC4's "every supplied path remains absent" is loose for the
   three- and four-argument cases, whose `appr-a`, `extra-a`, and `extra-b`
   values are not paths and would resolve against the process cwd rather than
   the temporary parent; name `<tmp>/state-a.json` as the only path asserted
   absent.

5. SPEC-WARN: AC9's full-suite gate is currently red on this branch for
   reasons outside T-183. Two consecutive `npm test --prefix app` runs on the
   unmodified worktree exited `1` with `spawnSync ... ETIMEDOUT` and

6. SPEC-WARN: non-object JSON roots other than `null` and `[]` (for example
