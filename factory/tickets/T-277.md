## Description

Relay creates one job per accepted event: `acceptEvent` in `app/server.js:36-52`
dedupes by event ID before ever pushing a job (`app/server.js:38-39`) and, for
a genuinely new event, pushes exactly one job whose `eventId` equals the
event's `id` (`app/server.js:41-49`). No product doc other than this
invariant governs the change; there is no `docs/` entry for the offline
report tools, so `app/server.js:36-52` is the cited source of truth.

The offline `job-progress` report (`app/tools/job-progress.js`) does not
enforce this invariant on its input: `isValidState`
(`app/tools/job-progress.js:34-52`) already rejects duplicate `job.id`
values (`app/tools/job-progress.js:51`) but has no equivalent check for
`job.eventId`, so a state file with two otherwise-valid jobs sharing one
`eventId` is currently accepted. Reject duplicate non-empty job `eventId`
values before lookup or reporting, mirroring the existing job-ID uniqueness
check.

## Acceptance criteria

1. A state containing two otherwise valid jobs with the same non-empty
   `eventId` exits `1`, writes exactly the existing invalid-state stderr line,
   and writes zero stdout bytes.
2. Duplicate event IDs are invalid whether the requested job is first,
   second, or absent and whether the jobs have different statuses. Complete
   job validation and uniqueness checking precede lookup.
3. Valid jobs with unique event IDs retain the existing output shape, field
   order, exact lookup, exit statuses, and stderr messages byte-for-byte.
4. Existing collection, job-field, status, counter, last-error, and unique job
   ID validation remain unchanged. Event records are not made unique here.
5. Failures remain redacted and leak no job or event ID, error text, state
   bytes, input path, parser detail, or operating-system detail.
6. The command remains offline, zero-dependency, deterministic, read-only, and
   self-terminating. Tests precede implementation; the targeted test, full app
   suite, and immutability check pass without other product or Factory changes.

## Frozen contract — version 1

### Scope

- Builder ownership: `app/tools/job-progress.js` only.
- Test-author ownership: `app/tests/job-progress.test.js` only.

### Interface freeze — `app/tools/job-progress.js`

- CLI invocation, exit codes (`0`/`1`/`2`), and all five stderr constants
  keep their exact current byte values, unchanged:
  - `USAGE = "usage: node app/tools/job-progress.js <state-file> <job-id>\n"`
  - `UNREADABLE = "job-progress: state file is unreadable\n"`
  - `NOT_JSON = "job-progress: state file is not valid JSON\n"`
  - `INVALID_STATE = "job-progress: state file has invalid Relay state\n"`
  - `NO_SUCH_JOB = "job-progress: no such job\n"`
- Success stdout shape is unchanged: exactly one line,
  `` `${JSON.stringify({jobId: job.id, status: job.status, attempts: job.attempts, retries: job.retries})}\n` ``,
  with that exact key order.
- `isValidJob`, `isNonEmptyString`, `isNonNegativeInteger`, `COLLECTIONS`,
  `STATUSES`, the collection/shape checks, and the existing job-`id`
  uniqueness check (`new Set(state.jobs.map(job => job.id)).size ===
  state.jobs.length`) are unchanged.
- New behavior: `isValidState` additionally requires event-ID uniqueness
  across `state.jobs`:
  `new Set(state.jobs.map(job => job.eventId)).size === state.jobs.length`.
  This is combined with (`&&`) the existing job-`id` uniqueness check (and
  all prior structural/per-job checks) to determine `isValidState`'s return
  value; either uniqueness check failing takes the identical existing
  `INVALID_STATE` failure path already wired in `main()` (exit `1`, stderr
  `INVALID_STATE`, stdout empty, job lookup never reached). Because
  `isValidJob` already requires every job's `eventId` to be a non-empty
  string, no separate empty-string case is needed.
- No new `require(...)`/import may be added. The frozen module-specifier
  set for `app/tools/job-progress.js`, as asserted by
  `app/tests/job-progress.test.js` AC7, remains exactly `["node:fs"]`, and
  the file must keep excluding `server.js`, `node:http`, `node:https`,
  `node:net`, `node:child_process`, and `fetch`.
