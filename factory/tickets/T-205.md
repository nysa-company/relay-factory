## Spec'd description

Add `app/tools/approval-count.js`, a zero-dependency CommonJS command that
reads one persisted Relay state file while Relay is offline, validates the
complete stored approval collection, and reports only its total cardinality as
`{"approvals":<count>}`. This gives operators a deterministic count without
starting Relay, changing durable state, or exposing approval IDs, job links,
actions, statuses, proposal timestamps, rejection reasons, event details, job
details, outbox details, or unrelated stored content.

  blocked-recipient, and rejected approval outcomes.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/approval-count.js <state-file>`.
- Exactly one user-supplied positional argument is accepted. Any other arity
  exits `2`, writes zero stdout bytes, writes exactly the following single
  LF-terminated line to stderr, and does not read or create a candidate state
  path:

  ```text
  usage: node app/tools/approval-count.js <state-file>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  approval-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  approval-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  approval-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, OS error, parser text, input bytes, stack trace, approval
  field, event field, job field, outbox field, or second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string own properties `id`, `jobId`, and `proposedAt`;
- an own `status` property exactly equal to `pending`, `sent`, `rejected`, or
  `blocked_recipient`; and
- an own `action` property that is a non-null, non-array object with own `to`,
  `subject`, and `body` properties.

Approval IDs must be pairwise distinct across the complete array. The values
of `action.to`, `action.subject`, and `action.body` are opaque. Additional
action and approval properties, including `reason`, are allowed and ignored.
Event, job, and outbox elements are wholly opaque; only the fact that their
top-level collections are arrays is validated. A `jobId` need not resolve to a
stored job. No relationship is imposed among `status`, `action`, `proposedAt`,
and `reason` beyond each field's individual rule.

The command validates the complete approval array and ID uniqueness before
counting. Success exits `0`, writes zero stderr bytes, and writes one compact
JSON object followed by exactly one LF. Its only key is:

```json
{"approvals":<nonnegative integer count>}
```

`approvals` is exactly the validated `approvals` array length. No stored
approval ID, `jobId`, action value, status, `proposedAt`, reason, additional
approval field, event, job, outbox, or top-level metadata value is emitted.

1. **Does "all approvals" mean array cardinality or a status-derived total?**
   Resolved from [`SPEC.md` behaviors 3-5](../../SPEC.md#behavior-spec), which
   make all four statuses durable outcomes in one approval collection, and the
   current server state model: after complete validation the result is exactly
   `state.approvals.length`; no status filtering or deduplication is performed.
2. **What state structure is required before counting?** The product has no
   single general-purpose state validator. Resolved from the four collections
   and approval fields in [`app/server.js`](../../app/server.js), the declared
   [`state-summary` fixture seam](../../app/tests/state-summary.test.js), the
   shipped [`approval-state` validator](../../app/tools/approval-state.js), and
   the shipped
   [`pending-approvals` validator](../../app/tools/pending-approvals.js):
   require all four arrays, validate every approval's core persisted shape and
   unique ID, allow additional top-level, action, and approval fields, and
   leave sibling collection elements opaque.
3. **Are action values strings, and must a `jobId` resolve to a stored job?**
   `app/server.js` always persists an action object with own `to`, `subject`,
   and `body` keys, but webhook payload values are not type-validated; existing
   offline approval validators do not resolve jobs. Resolved by requiring the
   three action keys while treating their values as opaque, and by imposing no
   cross-record relationship. Fixture A's blocked action uses `7`, `null`, and
   `false`, and its job IDs do not resolve against the opaque jobs collection.
4. **Does `reason` depend on status for structural validity?** The server adds
   `reason` only during rejection, but existing offline validators treat it as
   an unselected field. Resolved by allowing and ignoring `reason` and imposing
   no cross-field status relationship; Fixture A covers a rejected record with
   a reason and three other statuses without one.
5. **How are failures classified without leaking input?** Raw OS and parser
   errors can reveal paths or state bytes. Resolved using the shipped
   count-command convention: usage exit `2`, operational exits `1`, fixed
   single-line redacted errors, empty opposite streams, and precedence from
   arity through complete structure.
6. **How are offline, read-only, and self-terminating claims proved?** Resolved
   with synchronous child invocations under a `5_000` ms timeout, exact file

### Findings

1. SPEC-WARN: the frozen rule "no relationship is imposed among `status`,
   `action`, `proposedAt`, and `reason`" has no positive fixture for the most
   common real durable combination. `app/server.js` `reject()` sets
   `appr.reason = null` whenever the reject body carries no string reason, so a
   persisted rejected approval normally has an own `reason` key whose value is
   `null`. Frozen Fixture A pairs `rejected` with a non-empty string `reason`
   and gives the other three statuses no `reason` key at all, so a builder who
   over-constrained the validator (for example requiring `reason` to be a
   non-empty string whenever present, or requiring it exactly when `status` is
   `rejected`) would satisfy every frozen criterion and then report
   `approval-count: invalid Relay state` for an ordinary state file. The
   contract states the independence rule explicitly and Fixture A already proves
   the opacity of `action` values, so no product decision is left open and this
   is not blocking. Recommendation the Test-author may consume directly without
   editing the frozen contract: add one additional valid case in
   `app/tests/approval-count.test.js` whose `approvals` array holds a `rejected`
   approval with `"reason": null` alongside a `pending` approval carrying an
   extra `reason` string, asserting the ordinary success envelope.
2. SPEC-WARN: the invalid matrix uses one representative per equivalence class
   for root scalars (S1/S2 stand in for a number, string, or boolean root) and
   for missing collections (S3 stands in for a missing own `events`, `jobs`, or
   `approvals`). This grouping is permitted by the contract and by the shipped
   `job-count` precedent; adding the root-scalar case alone would match the
   shipped `state-summary` suite at negligible cost.
3. SPEC-WARN: every frozen `proposedAt` value that reaches the validator is an
   ISO-8601 instant, so a builder who tightened the rule from "non-empty string"
   to "parseable timestamp" would still pass AC1-AC6. The frozen rule is
   unambiguous, so this is not blocking. Recommendation: let the additional
   valid case from finding 1 carry a non-ISO non-empty `proposedAt` string.
