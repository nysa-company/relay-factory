## Spec'd description

Add `app/tools/job-event-retry-count.js`, a zero-dependency CommonJS command
that reads one persisted Relay state file while Relay is offline, validates
the complete stored job collection, and counts jobs whose stored `eventId`
and nonnegative-integer `retries` both exactly match operator-supplied values.
The result is exactly
`{"jobsWithEventAndRetries":<nonnegative integer count>}`. This gives an
operator a deterministic event-scoped retry count without starting Relay,
changing durable state, or exposing job IDs, statuses, attempt counters,
errors, event payloads, approval content, outbox content, or unrelated state.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/job-event-retry-count.js <state-file> <event-id> <retries>`.
- Exactly three user-supplied positional arguments are accepted.
  `<event-id>` is valid when its UTF-16 string length is greater than zero. It
  is otherwise used verbatim: it is not trimmed, case-folded, decoded,
  prefixed, or Unicode-normalized. A string containing only one U+0020 space
  is therefore a valid event-ID query.
- `<retries>` is valid only when it matches the complete JavaScript regular
  expression `/^(?:0|[1-9][0-9]*)$/u`. This admits `0` and canonical ASCII
  decimal positive integers with no fixed digit ceiling. It rejects the empty
  string, signs, leading zeroes on multi-digit values, whitespace, decimal
  points, exponent notation, separators, non-ASCII digits, and all other
  text. After the grammar check, its mathematical integer value is compared
  exactly with the parsed stored integer value; implementations must not use
  a lossy Number conversion of the query. The frozen stored
  `9007199254740992` value and adjacent zero-match query
  `9007199254740993` make that requirement observable.
- Wrong arity, an empty `<event-id>`, or invalid `<retries>` syntax exits `2`,
  writes zero stdout bytes, writes exactly the following single LF-terminated
  line to stderr, and does not read or create a candidate state path:

  ```text
  usage: node app/tools/job-event-retry-count.js <state-file> <event-id> <retries>
  ```

- After all argument validation, the command synchronously reads
  `<state-file>` directly as UTF-8. Any `readFileSync` failure, including an
  absent path, a directory in place of a regular file, or an OS read denial,
  exits `1`, writes zero stdout bytes, and writes exactly:

  ```text
  job-event-retry-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  job-event-retry-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  job-event-retry-count: invalid Relay state
  ```

- Failure precedence is argument count, event-ID and retry-text validation,
  file read, JSON parse, complete structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, supplied event ID or retry text, OS error, parser text, input
  bytes, stack trace, job field, event field, approval field, outbox field, or
  second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state, exact matching, and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with exactly four own properties: `events`, `jobs`, `approvals`,
and `outbox`, each an array.

Every `jobs` element must be a non-null, non-array object with:

- non-empty string own properties `id` and `eventId`;
- an own `status` property exactly equal to `pending`, `done`, or `dead`;
- own `attempts`, `retries`, and `attemptsSinceRetry` properties whose values
  satisfy `Number.isInteger(value) && value >= 0`; and
- an own `lastError` property equal to `null` or a string, including `""`.

Job IDs must be pairwise distinct across the complete array. Additional job
properties are allowed and ignored. Event, approval, and outbox elements are
wholly opaque; only the fact that their top-level collections are arrays is
validated. A job's `eventId` need not resolve to a stored event. No
relationship is imposed among `status`, the three counters, and `lastError`
beyond each field's individual rule.

The command validates the complete job array and ID uniqueness before
counting. A job contributes exactly one when its stored `eventId` is strictly
equal to the supplied `<event-id>` using case-sensitive JavaScript string
equality and the mathematical integer represented by its stored `retries`
equals the valid canonical integer represented by `<retries>`. Stored string,
boolean, null, fractional, negative, absent, or non-finite retry values make
the entire state invalid rather than matching a query. Neither filter is
trimmed, case-folded, decoded, prefixed, Unicode-normalized, or compared with
JavaScript loose equality. A valid pair with no matches succeeds with count
zero; there is no event lookup and no not-found error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"jobsWithEventAndRetries":<nonnegative integer count>}
```

The supplied filters are not echoed. No stored job ID, event ID, status,
attempt counter, retry counter, `lastError`, additional job field, event,
approval, outbox, or other state content is emitted.
