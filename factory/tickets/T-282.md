## Spec'd description

Add `app/tools/job-event-type-count.js`, a zero-dependency CommonJS command
that reads one persisted Relay state file while Relay is offline, validates
the complete stored event and job collections plus every job's reference into
that event collection, and reports how many jobs reference an event whose own
`type` is exactly equal to a supplied value. The result is exactly
`{"jobsForEventType":<count>}`. This gives operators a deterministic,
cross-collection count without starting Relay, changing durable state, or
exposing event IDs, payloads, timestamps, job IDs, attempts, errors,
approval, or outbox content.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/job-event-type-count.js <state-file> <event-type>`.
- Exactly two user-supplied positional arguments are accepted: the state-file
  path and the event-type query value. Any other arity (zero, one, three, or
  more) exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not read or create a
  candidate state path:

  ```text
  usage: node app/tools/job-event-type-count.js <state-file> <event-type>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8 via `readFileSync` (no prior `statSync` call — an absent
  path, a directory in place of a regular file, or an OS read denial are all
  surfaced by `readFileSync` itself). Any such failure exits `1`, writes zero
  stdout bytes, and writes exactly:

  ```text
  job-event-type-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  job-event-type-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  job-event-type-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation (events, then jobs, then referential resolution),
  then filtering and counting. The event-type query value never participates
  in structural validation and is never itself validated, restricted,
  trimmed, or case-folded; any string, including the empty string, is an
  accepted query value.
- Every error is one fixed line terminated by exactly one LF. No error
  includes the state path, OS error, parser text, input bytes, stack trace,
  event field, job field, approval field, outbox field, query value, or
  second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture
  matrix; if `readFileSync` throws for either, the frozen read-error result
  applies.

### Structurally valid state and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object whose own enumerable key set is **exactly**
`events`, `jobs`, `approvals`, `outbox` (`Object.keys(state).length === 4`)
— an additional top-level property, or a missing one, is invalid. Each of
those four own properties must be an array.

Every `events` element must be a non-null, non-array object with non-empty
string own properties `id`, `type`, and `receivedAt`. Event IDs must be
pairwise distinct across the complete array. The value of `type` and
`receivedAt` are otherwise unconstrained strings (no enum, no ISO-8601
parsing). Additional event properties (for example `payload`) are allowed
and ignored.

Every `jobs` element must be a non-null, non-array object with:

- non-empty string own properties `id` and `eventId`;
- an own `status` property exactly equal to `pending`, `done`, or `dead`;
- non-negative integer own properties `attempts`, `retries`, and
  `attemptsSinceRetry`; and
- an own `lastError` property whose value is `null` or a string.

Job IDs must be pairwise distinct across the complete array. Additional job
properties (for example a diagnostic field) are allowed and ignored.

After every event and every job independently satisfies the rules above and
each collection's IDs are unique, every job's own `eventId` must be
byte-for-byte equal to the `id` of some element of the validated `events`
array. A job whose `eventId` does not resolve to any valid event invalidates
the complete state (this is a global validity failure, not a per-job skip).
There is no requirement that every event be referenced by some job — an
unreferenced, structurally valid event is permitted and contributes to no
count. `approvals` and `outbox` elements are wholly opaque: only the fact
that each top-level collection is an array is validated, and array elements
may be any JSON value, including `null`, a number, or a bare string.

The command validates the complete event array, then the complete job array
plus its referential resolution into that event array, before filtering and
counting. A job contributes exactly one to the count when the `type` of its
referenced event is byte-for-byte, case-sensitively equal to the second
positional argument (`args[1]`). The command does not trim, case-fold,
decode, or Unicode-normalize either the stored event `type` or the query
value.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON
object followed by exactly one LF. Its only key is:

```json
{"jobsForEventType":<nonnegative integer count>}
```

No stored event ID, event type, payload, `receivedAt`, job ID, job status,
attempts, `lastError`, approval, outbox content, additional top-level or
per-record field, or the query value itself is emitted.

## Ambiguity log

1. **Should the parsed state's top-level key set be exact (reject additional
   properties), or allow-and-ignore extras?** Both conventions exist in the
   shipped tools: job-focused tools
   ([`job-count`](../../app/tools/job-count.js),
   [`job-status-count`](../../app/tools/job-status-count.js),
   [`job-error-count`](../../app/tools/job-error-count.js),
   [`job-progress`](../../app/tools/job-progress.js)) require exactly the
   four collection keys, while event/approval/outbox-focused tools allow
   extras. This ticket's counted collection is `jobs`, so it follows the
   job-focused exact-key-set convention (frozen contract, "Structurally
   valid state and successful output"); S3 and S4 freeze the missing-key and
   extra-key negative cases.
2. **What event fields must be validated, given this is the first tool to
   both validate events and cross-reference them from jobs?** Resolved from
   the shipped [`event-type-count`](../../app/tools/event-type-count.js)
   per-event rule (non-empty `id`, `type`, `receivedAt`; unique IDs), reused
   verbatim because this ticket's event validation need (typed lookup by
   job reference) is identical to that command's own validation need
   (typed lookup by direct query).
3. **Must every event be referenced by a job, or may events and jobs each be
   independently over/under-populated?** [`SPEC.md` behavior 2](../../SPEC.md#behavior-spec)
   and [`app/server.js:40-49`](../../app/server.js) enqueue exactly one job
   per accepted event, but nothing in the spec or code forbids an event
   existing without (yet) processing to job creation being visible in an
   arbitrary persisted snapshot, nor does anything require the reverse.
   Resolved by requiring only that every job's `eventId` resolves to a valid
   event; an unreferenced valid event is permitted and contributes to no
   count. Fixture A's fourth event and S39's first event both freeze this
   case.
4. **What happens when a job references a missing or otherwise-invalid
   event?** Resolved using the [`approval-link`](../../app/tools/approval-link.js)
   referential-integrity technique (validate the referenced collection into
   an ID-keyed map first, then require every reference to resolve into that
   map, with a missing resolution invalidating the complete state). S37
   freezes an `eventId` with no matching event ID at all; because event
   validation happens first and completely, a job referencing an
   individually-invalid event record is already excluded by that event's own
   failure (for example S15's empty `type` would independently invalidate
   any state built on it), so no separate fixture class is needed for that
   sub-case.
5. **Is event-type matching case-sensitive, and is the query value
   restricted to a domain?** Resolved from the ticket's "exact and
   case-sensitive" wording and the shipped
