## Spec'd description

Relay can persist a truthy numeric event `type` unchanged:
[`app/server.js`](../../app/server.js) line 40 stores
`type: evt.type || "generic"`, so a `POST /webhook/event` body with
`{id, type, payload}` ([`SPEC.md` behavior 1](../../SPEC.md#behavior-spec))
carrying a non-zero JSON number for `type` (for example `7` or `-0.5`)
persists that number as-is; only a falsy `type` (including `0`) falls back to
`"generic"`. The offline `event-type-count` command
([`app/tools/event-type-count.js`](../../app/tools/event-type-count.js),
established by the Done ticket T-199 and documented as the offline-query
convention in T-203, T-209, T-210, and T-211) instead requires every event's
stored `type` to be a non-empty string during structural validation
(`isNonEmptyOwnString(event, "type")`). A state containing one legitimate
numeric sibling — as `SPEC.md` behavior 7 and conformance cases 1 and 2 make
events an operator-visible, durably persisted collection — therefore fails
validation before the command can count an unrelated string type, blocking a
valid offline query.

Change only the event `type` structural-validation rule: accept a stored
`type` that is either a non-empty string (unchanged) or a JSON number
strictly unequal to `0` (which also excludes JSON `-0`, since `-0 === 0` in
JavaScript). Every other structural rule, the CLI interface, the output
shape, the four fixed error messages, exit codes, and validation precedence
are unchanged. The command-line query argument stays a literal string
(`process.argv` never yields a JS number), and matching stays strict
`===` equality with no parsing or coercion, so a query text `"7"` can never
match a stored number `7` — this falls directly out of JavaScript's type
system and requires no new comparison logic. This mirrors the identical
non-zero JSON-number acceptance rule specified for the sibling `event-count`
command (T-264), applied here to the type-matching command instead of the
total-count command.

### Structurally valid state — the one changed rule

A structurally valid state is unchanged except for the `type` field: a
parsed non-null, non-array JSON object with own `events`, `jobs`,
`approvals`, and `outbox` array properties. Every `events` element must be a
non-null, non-array object with:

- a non-empty string own `id`, pairwise distinct across the array (unchanged);
- a non-empty string own `receivedAt` (unchanged);
- an own `type` that is **either** a non-empty string **or** a JSON number
  strictly unequal to `0` (the changed rule). Concretely, replace the
  existing `isNonEmptyOwnString(event, "type")` gate with:

  ```js
  function isNonZeroOwnNumber(record, key) {
    return (
      Object.hasOwn(record, key) &&
      typeof record[key] === "number" &&
      record[key] !== 0
    );
  }
  // event type gate becomes:
  (isNonEmptyOwnString(event, "type") || isNonZeroOwnNumber(event, "type"))
  ```

  `record[key] !== 0` excludes both `0` and `-0` (JavaScript strict equality
  treats them as equal). Booleans, `null`, objects, and arrays remain invalid
  `type` values, exactly as before.

Job, approval, and outbox elements stay wholly opaque; only their top-level
arrays are validated. The command validates the complete event array and ID
uniqueness before counting, unchanged.

### Matching and successful output (unchanged from T-199)

An event contributes one to the count only when its stored `type` is
strictly `===` equal to the supplied `<event-type>` CLI argument, which is
always a string. No trimming, case-folding, decoding, Unicode-normalizing,
JSON-parsing, or numeric coercion of either side. A numeric-typed event can
never match any query, because `process.argv` values are always strings and
`"7" === 7` is `false` in JavaScript — this is an automatic consequence of
strict equality, not a rule the Builder implements separately. A supplied
type with no matches is a successful zero-count query, never a not-found
error.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON
object plus one LF: `{"eventType":<supplied argument>,"events":<count>}`, key
order `eventType` then `events`, exactly as before.
