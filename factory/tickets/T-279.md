## Spec'd description

Add `app/tools/job-status-error-count.js`, a zero-dependency CommonJS command
that reads one persisted Relay state file while Relay is offline, validates
the complete stored job collection, and reports how many jobs both have a
`status` exactly equal to a supplied literal and have an own `lastError`
whose value is a string with at least one UTF-16 code unit. The result is
exactly `{"jobsWithStatusAndError":<count>}`. This gives operators a
deterministic count without starting Relay, changing durable state, or
exposing job IDs, event links, statuses, attempts, retries, error text,
event details, approval details, outbox details, or unrelated content.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/job-status-error-count.js <state-file> <status>`.
- Exactly two user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not read or create a
  candidate state path:

  ```text
  usage: node app/tools/job-status-error-count.js <state-file> <status>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  job-status-error-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  job-status-error-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  job-status-error-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then filtering and counting.
- Every error is one fixed line terminated by exactly one LF. No error
  includes the state path, queried status, OS error, parser text, input
  bytes, stack trace, job field, event field, approval field, or outbox
  field, or a second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `readFileSync` throws for either, the frozen read-error result applies.

### Structurally valid state and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with **exactly** the own properties `events`, `jobs`,
`approvals`, and `outbox`, all array-valued (`Object.keys(state).length` must
equal `4`; any additional top-level property is invalid).

Every `jobs` element must be a non-null, non-array object with:

- non-empty string own properties `id` and `eventId`;
- an own `status` property exactly equal to `pending`, `done`, or `dead`;
- non-negative integer own properties `attempts`, `retries`, and
  `attemptsSinceRetry` (per `Number.isInteger`); and
- an own `lastError` property whose value is `null` or a string, including
  the empty string.

Job IDs must be pairwise distinct across the complete array. Additional job
properties are allowed and ignored. Event, approval, and outbox elements are
wholly opaque; only the fact that their top-level collections are arrays is
validated. An `eventId` need not resolve to a stored event.

The command validates the complete job array and ID uniqueness before
filtering and counting. A job contributes exactly one to the count only when
both:

- `job.status === <supplied status argument>` (exact, case-sensitive, no
  restriction on the argument's membership in the status enum); and
- it has an own `lastError`, `typeof job.lastError === "string"`, and
  `job.lastError.length > 0`.

The command does not trim, case-fold, decode, or Unicode-normalize a status
or an error. In particular, `""`, `null`, and a non-matching status do not
count, while a whitespace-only error string counts when its status matches.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON
object followed by exactly one LF. Its only key is:

```json
{"jobsWithStatusAndError":<nonnegative integer count>}
```

No stored job ID, `eventId`, status, attempts, retries, error text,
additional job field, event, approval, outbox, or top-level metadata value is
emitted.
