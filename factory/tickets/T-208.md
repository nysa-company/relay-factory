## Spec'd description

Add `app/tools/approval-reason-count.js`, a zero-dependency CommonJS command
that reads one persisted Relay state file while Relay is offline, validates the
complete stored approval collection, and reports how many approvals have an
own `reason` whose value is a string with at least one UTF-16 code unit. The
result is exactly `{"approvalsWithReasons":<count>}`. This gives operators a
deterministic count without starting Relay, changing durable state, or
exposing reasons, approval IDs, job links, actions, statuses, proposal
timestamps, event details, job details, outbox details, or unrelated content.

Product-doc and repository sources:

- [`SPEC.md` behavior 3](../../SPEC.md#behavior-spec) defines a proposed action
  requiring approval and its initial `pending` state.
- [`SPEC.md` behaviors 4 and 5](../../SPEC.md#behavior-spec) define the sent,
  blocked-recipient, and rejected approval outcomes; behavior 5 establishes
  rejection as the operation associated with the selected field.
- [`SPEC.md` behavior 6](../../SPEC.md#behavior-spec) makes the atomically
  persisted state file Relay's durable source, and behavior 7 makes approvals
  operator-visible.
- The current [`app/server.js` state model](../../app/server.js) establishes
  the four stored collections, complete approval core shape, exact status
  enum, and persistence. Its rejection path stores an own `reason` as either
  the supplied string, including `""`, or `null`.
- The protected
  [`reject-reason` acceptance suite](../../app/tests/reject-reason.test.js)
  establishes exact string preservation, the frozen `null` no-reason
  representation, persistence across restart, and no change to an existing
  reason after an invalid second rejection.
- The shipped [`approval-count` command](../../app/tools/approval-count.js)
  and its [acceptance suite](../../app/tests/approval-count.test.js) establish
  the one-path count envelope, complete approval-array validation, unique

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/approval-reason-count.js <state-file>`.
- Exactly one user-supplied positional argument is accepted. Any other arity
  exits `2`, writes zero stdout bytes, writes exactly the following single
  LF-terminated line to stderr, and does not read or create a candidate state
  path:

  ```text
  usage: node app/tools/approval-reason-count.js <state-file>
  ```

- After arity validation, the command synchronously reads `<state-file>`
  directly as UTF-8. Any `readFileSync` failure, including an absent path, a
  directory in place of a regular file, or an OS read denial, exits `1`,
  writes zero stdout bytes, and writes exactly:

  ```text
  approval-reason-count: cannot read state file
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  approval-reason-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules exits
  `1`, writes zero stdout bytes, and writes exactly:

  ```text
  approval-reason-count: invalid Relay state
  ```

- Failure precedence is argument count, file read, JSON parse, complete
  structural validation, then counting.
- Every error is one fixed line terminated by exactly one LF. No error includes
  the state path, OS error, parser text, input bytes, stack trace, approval

### Structurally valid state and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with own `events`, `jobs`, `approvals`, and `outbox` properties
whose values are arrays. Additional top-level properties are allowed and
ignored.

Every `approvals` element must be a non-null, non-array object with:

- non-empty string own properties `id`, `jobId`, and `proposedAt`;
- an own `status` property exactly equal to `pending`, `sent`, `rejected`, or
  `blocked_recipient`;
- an own `action` property that is a non-null, non-array object with own `to`,
  `subject`, and `body` properties; and
- either no own `reason` property, or an own `reason` whose value is `null` or
  a string, including the empty string.

Approval IDs must be pairwise distinct across the complete array. The values
of `action.to`, `action.subject`, and `action.body` are opaque. Additional
action and approval properties are allowed and ignored. Event, job, and outbox
elements are wholly opaque; only the fact that their top-level collections are
arrays is validated. A `jobId` need not resolve to a stored job. No
relationship is imposed among `status`, `action`, `proposedAt`, and `reason`.

The command validates the complete approval array and ID uniqueness before
counting. An approval contributes exactly one to the count only when it has an
own `reason`, `typeof approval.reason === "string"`, and
`approval.reason.length > 0`. The command does not trim, case-fold, decode, or
Unicode-normalize a reason. In particular, `""`, `null`, and an absent
property do not count, while `" "` counts. Status does not affect this
predicate.

Success exits `0`, writes zero stderr bytes, and writes one compact JSON object
followed by exactly one LF. Its only key is:

```json
{"approvalsWithReasons":<nonnegative integer count>}
```

No stored reason, approval ID, `jobId`, action value, status, `proposedAt`,
additional approval field, event, job, outbox, or top-level metadata value is
emitted.
