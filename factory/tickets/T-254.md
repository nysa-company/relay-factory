## Spec'd description

Add `app/tools/job-event-min-attempts-count.js`, a zero-dependency CommonJS
command that reads one persisted Relay state file while Relay is offline,
validates the complete stored job collection, and reports only the count of
jobs whose `eventId` exactly matches a supplied event ID and whose `attempts`
is greater than or equal to a supplied minimum, as
`{"jobsWithEventAndMinimumAttempts":<count>}`. This gives operators a
deterministic, narrow offline retry check without starting Relay, changing
durable state, or exposing job IDs, event links, statuses, counters, errors,
additional job fields, event payloads, approval details, outbox details, or
unrelated stored content.

### Command-line interface and failure precedence

- Repository-root invocation is exactly
  `node app/tools/job-event-min-attempts-count.js <state-file> <event-id> <minimum-attempts>`.
- Exactly three user-supplied positional arguments are accepted. Any other
  arity exits `2`, writes zero stdout bytes, writes exactly the following
  single LF-terminated line to stderr, and does not read or create a
  candidate state path:

  ```text
  usage: node app/tools/job-event-min-attempts-count.js <state-file> <event-id> <minimum-attempts>
  ```

- After arity validation, argument *values* are validated, in this order,
  before any filesystem access:
  1. `<event-id>` must be a non-empty string (any length-1-or-more string is
     accepted; no trimming, casing, or content restriction is applied). A
     zero-length string exits `2`, writes zero stdout bytes, and writes
     exactly:

     ```text
     job-event-min-attempts-count: event ID must be non-empty
     ```

  2. `<minimum-attempts>` must match the canonical non-negative decimal
     integer syntax `^(0|[1-9][0-9]*)$` — ASCII digits only, no sign, no
     leading zero unless the value is exactly `0`, no decimal point, no
     exponent, no surrounding whitespace, no alternate radix, and no other
     non-digit character. A non-matching value exits `2`, writes zero stdout
     bytes, and writes exactly:

     ```text
     job-event-min-attempts-count: minimum attempts must be a canonical non-negative decimal integer
     ```

  When both `<event-id>` and `<minimum-attempts>` are invalid, only the
  event-ID error is produced (event-ID validation runs first and is
  short-circuiting).
- After argument validation, the command reads `<state-file>` via
  `fs.statSync` and (when a regular file) `fs.readFileSync`, both directly as
  UTF-8. A nonexistent path, a directory in place of a regular file, or any
  other `statSync`/`readFileSync` failure exits `1`, writes zero stdout bytes,
  and writes exactly:

  ```text
  job-event-min-attempts-count: state file is unreadable
  ```

- Readable bytes rejected by `JSON.parse` exit `1`, write zero stdout bytes,
  and write exactly:

  ```text
  job-event-min-attempts-count: state file is not valid JSON
  ```

- A parsed value that fails the frozen structurally-valid-state rules (below)
  exits `1`, writes zero stdout bytes, and writes exactly:

  ```text
  job-event-min-attempts-count: state file has invalid Relay state
  ```

- Failure precedence is: argument arity, event-ID value, minimum-attempts
  value, file read, JSON parse, complete structural validation, then
  counting.
- Every error is one fixed line terminated by exactly one LF. No error
  includes the state path, the supplied event ID, the supplied
  minimum-attempts value, an OS error, parser text, input bytes, a stack
  trace, a job field, an event field, an approval field, an outbox field, or
  a second line.
- Acceptance uses absolute temporary paths. Symlink inputs and portable
  simulation of OS permission denial are outside the required fixture matrix;
  if `statSync`/`readFileSync` throws for either, the frozen unreadable-state
  result applies.

### Structurally valid state and successful output

A structurally valid state for this command is a parsed non-null, non-array
JSON object with exactly four own properties: `events`, `jobs`, `approvals`,
and `outbox`, each an array. This is the identical rule shipped in
`app/tools/job-attempts.js` and `app/tools/job-count.js`.

Every `jobs` element must be a non-null, non-array object with:

- non-empty string own properties `id` and `eventId`;
- an own `status` property exactly equal to `pending`, `done`, or `dead`;
- own `attempts`, `retries`, and `attemptsSinceRetry` properties that are
  integers greater than or equal to zero; and
- an own `lastError` property equal to `null` or a string.

Job IDs must be pairwise distinct across the complete array. Additional job
properties are allowed and ignored. Event, approval, and outbox elements are
wholly opaque; only the fact that their top-level collections are arrays is
validated. Event IDs in the `events` collection need not match job `eventId`
values, and no relationship is imposed among `status`, the three counters,
and `lastError` beyond each field's individual rule.

The command validates the complete job array and ID uniqueness before
counting. Counting then filters the validated `jobs` array to elements where
`job.eventId === <event-id>` (exact, case-sensitive, byte comparison) and
`job.attempts >= Number(<minimum-attempts>)` (numeric comparison against the
validated integer `attempts` field; no upper bound is imposed on
`<minimum-attempts>` magnitude). Success exits `0`, writes zero stderr bytes,
and writes one compact JSON object followed by exactly one LF. Its only key
is:

```json
{"jobsWithEventAndMinimumAttempts":<nonnegative integer count>}
```

No stored job ID, `eventId`, status, counter, error, additional job field,
event, approval, or outbox value is emitted. The supplied `<event-id>` and
`<minimum-attempts>` argument values are likewise never echoed.
